## パスキーによるログインと暗号メッセージ

2026-11-28の変更で、通常ログインを認可コード＋PKCE（S256）に統一します。
「パスキーでログイン」から `ASWebAuthenticationSession` で AuthZ を開き、AuthZ に登録済みの
パスキーで認証します。アプリで確認コードを表示したり、承認待ちをポーリングしたりしません。
認証方式の選択は AuthZ が管理し、アプリはパスキーだけに制限する独自のパラメーターを送りません。
通常ログインは `openid profile offline_access` と `prompt=consent`、暗号鍵の変更直前の
再認証は `openid profile` と `max_age=0` を使います。
state・nonce・PKCE の照合、取消・タイムアウト、ログアウト後の遅延応答を検査し、
更新トークンは既存の Keychain に保存します。

暗号メッセージは、設定の「暗号化」でログイン用と同じ AuthZ のパスキーを鍵スロットへ追加し、
同じパスキーの PRF で秘密鍵の保管領域を解錠します。ログインしただけで暗号鍵は解錠しません。
PRF の出力は端末内だけで使い、認証のアサーションや復号用の鍵を AuthZ に送りません。
PRF に対応しない保存先ではリカバリーキーを使います。

本番で有効にするために必要な設定は次のとおりです。

- AuthZ の iOS 公開クライアントで `authorization_code` と `refresh_token` を許可し、
  `works.zli.zoo:/reauth-callback` をリダイレクト URI に登録する。
- App ID `F82XB5KFX2.works.zli.zoo` の Associated Domains を有効にする。
  アプリの `Zoo.entitlements` は `webcredentials:account.zli.works` を指定済み。
- AuthZ の `https://account.zli.works/.well-known/apple-app-site-association` を認証不要の
  HTTP 200・JSON で配信し、`webcredentials.apps` に `F82XB5KFX2.works.zli.zoo` を含める。
- 暗号鍵を変更する再認証のため、zoo2-infra の `OIDC_REAUTH_AUDIENCES` に iOS クライアント ID を含める。
  インフラ設定は zoo2-infra の PR で管理する。

2026-11-28に以下の本番反映と確認を完了しました。

- [zoo2-infra #222](https://github.com/Zli-UoA/zoo2-infra/pull/222)（`4189928`）で
  AASAのアプリIDとiOSの再認証audienceを追加し、AuthZ・ZooのFlux同期成功を確認しました。
- [AuthZ #121](https://github.com/Zli-UoA/AuthZ/pull/121)（`ccb94da`）でAASAの公開と
  Publicクライアントのカスタムスキーム登録に対応し、mainのCIと本番配備が成功しました。
- AuthZ管理画面の既存「Zoo for iOS」に `works.zli.zoo:/reauth-callback` を追加しました。
  既存のHTTPSコールバック、Public種別、S256必須、スコープ、デバイスコード許可、API設定は維持しています。
- AuthZ直配信とApple CDNの
  `https://app-site-association.cdn-apple.com/a/v1/account.zli.works` の両方が
  HTTP 200・JSONで、`webcredentials.apps` に `F82XB5KFX2.works.zli.zoo` を返しました。
- 未認証の認可要求（`prompt=none`、認可コード＋S256、iOS専用クライアント）は
  登録したカスタムスキームへ `login_required` を返し、変更前の `invalid_redirect` は解消しました。

この確認では本人の認可コードやトークンを取得していません。
コード交換とPKCEの検証はローカルのProvider結合テスト、アプリの取消・nonceなどの検査は
iOSシミュレーターのテストで確認しています。本番アカウントでのアプリへのログイン完了、
実機のパスキーPRF、別端末での暗号メッセージの復号は未確認です。
端末内の関連付けキャッシュはApple CDNと別に更新されるため、既存端末では反映を待つ場合があります。

## 実機での動作

SwiftUI の設定画面は、ユーザーが通知を有効にしたときだけ、システム権限を要求します。
「プロフィール」→「設定」で「通知は有効です」と表示されたら、「テスト通知を送る」でそのiPhoneに1件送れます。「テスト通知を送信しました」はAppleが受け付けた状態です。「このiPhoneでテスト通知を受信しました」は、端末に届いた通知と今回の送信IDが一致したときに表示されます。
Debug ビルドは APNs のサンドボックス環境、Release は本番環境を使用します。
Info.plist の値と `aps-environment` エンタイトルメントは同じビルド設定から決まります。
書き出したビルドも含め、署名済みのプロビジョニングプロファイルがこの設定と一致することを確認してください。
APNs 登録は署名した実機で確認する必要があります。
シミュレーターでの配信は、このサーバー経由の通知の受け入れ確認にはなりません。

サーバーは、アプリがバックグラウンドにある場合や終了している場合も iOS が表示できるアラート通知を生成します。
サイレント通知によるバックグラウンド処理は保証していません。
通知をタップすると、認証後に REST API でチャンネルへのアクセスを確かめ、SwiftUI のチャンネルやスレッドを開きます。
アクセスの可否は引き続きバックエンドの参加資格確認で決まります。
通知サービス拡張が、現在のアカウントの端末登録に対応する鍵でプレビューを復号します。チャンネル通知のタイトルは「送信者名 · #チャンネル名」、DMのタイトルは送信者名です。本文はWeb版と同じく先頭240文字までで、リアクションは「リアクション: 」に続けて対象の投稿を表示します。不在着信の本文は「不在着信」です。

暗号化チャンネルでも、現在の通知登録鍵でプレビューを認証でき、通知と暗号文の宛先・チャンネル・メッセージが一致し、保存済みの受信用の鍵で復号できれば本文を表示します。受信用の鍵が未到着・未保存なら「新しいメッセージ」です。古い登録宛ての通知や、アカウント切替などで現在の通知登録鍵を確認できない場合は「Zoo」「新しい通知があります」を表示します。ロック画面で本文を見せるかどうかは、iOSの「設定」→「通知」→「Zoo」→「プレビューを表示」で選べます。

各登録には、解除に使うランダムな 256 ビットの秘密情報を割り当て、リクエスト送信前に端末の Keychain へ保存します。
データベースにはそのハッシュだけを保存します。
アプリは登録と解除を直列化し、通信に失敗しても解除用の秘密情報を保持します。
ログアウト時は端末側の登録を無効にし、サーバー側の登録解除をキューに追加します。
オフラインでのログアウトでは、サーバー側の登録を直ちに削除できるとは限りません。
登録と解除は共通のデータベーストランザクションロックを使用します。
解除記録により、ログアウト後に到着したリクエストが登録を復活させることを防ぎます。
登録リクエストの有効期間は10分です。通信を再試行するときは同じ登録IDと解除情報を使い、9分経過した場合や時計が30秒を超えて戻った場合は送信日時を更新します。同じ端末・アカウントの更新中は通知登録を保持します。
解除記録は 11 分間保持します。未登録の端末から新しい解除記録を作る処理は、全レプリカ合計の有効な記録が 10,000 件に達すると停止します。有効な登録の解除は引き続き受け付けます。
期限切れの記録は、その後の解除処理で削除します。
429 応答を受けた場合は、再試行のために端末の登録情報を保持します。
端末の時計が正しくない場合は、日時の自動設定を有効にしてください。
期限切れの登録情報は、解除に成功した後にだけ更新します。

登録解除は、次にフォアグラウンドで接続したときや起動時に再試行します。有効なアクセストークンは不要です。
古い解除リクエストが遅れて到着しても、新しいアカウントの登録は削除できません。
アプリの再インストールや Keychain の喪失後は、残存する登録をサーバー側で削除する必要がある場合があります。
その登録を使って、端末の所有アカウントを知らないうちに移すことはできません。

## VoIP着信とWatch連携

通常通知とVoIP通知は別の端末トークンを使い、Keychainの登録・解除情報も分離します。
アプリは`GET /api/push/apns/config`で対象環境が有効かを確認し、
VoIPの場合は`voip: true`も確認してから`POST /api/push/apns/subscriptions`へ`kind: "voip"`で登録します。
通常通知には`kind: "alert"`を使い、解除APIは共通の`POST /api/push/apns/revoke`です。
ログアウト時は両方を解除対象とし、通信失敗時はそれぞれの解除情報を保持します。

`SystemCallController`は画面表示前にPushKitを初期化します。受信した着信はCallKitへ報告し、
認証・招待の有効性を確認して応答・拒否を処理します。前面表示中の招待も同じCallKitへ接続します。
ロック中・バックグラウンドの着信には、アプリの通知設定、VoIP登録、サーバーの配信設定が必要です。
設定画面の「テスト通知を送る」は通常通知だけを検証するため、成功してもVoIP着信の確認にはなりません。
VoIP着信では別のアカウントから実際に呼び出し、標準着信画面と音声の送受信を確認します。

Apple Watchへの通知はOSの通知転送設定に従います。Watchアプリを閉じている間も、ペアリング済みiPhoneの
Zooで通知が有効なら、着信通知の詳細に「iPhoneで応答」「拒否」を表示し、操作をiPhoneへ送る実装です。
通知の転送先と振動・音は、端末のロック状態やWatchの通知・触覚・集中モードの設定に従います。
Watchアプリにも着信時の触覚フィードバックと、応答・拒否・ミュート・終了の操作UIを実装しています。
音声はiPhone側で処理し、応答前にiPhoneでマイクの使用を許可しておく必要があります。
応答・拒否・取消・期限切れ・ログアウト後の着信通知を削除し、起動時には前回残った通知も回収します。
2026-11-23にiPhone 16 Pro Max / iOS 27.3で通知転送を確認しましたが、Watch通知からの応答は失敗しました。
Zooを終了しない場合でも、操作のiPhone到着後にCallKitが`Code=6`で応答要求を拒否しています。
そのためWatchからの応答は利用可能な機能として案内せず、iPhoneの標準着信画面を使います。
通知表示まで約10秒の遅延と、iPhoneロック中のWatch通知未着も報告されています。ロックとの因果関係は未確定です。
アプリ終了後の応答も失敗しましたが、招待期限内だったかは未記録です。拒否・その他の通話操作・音声は未検証です。
今回の移行PRでは追加修正と実機試験を見送り、[Issue #674](https://github.com/Zli-UoA/zoo2/issues/674)で追跡します。

   登録の種類と環境、解除用の秘密情報がハッシュ化されていることを確認します。
   生のデバイストークンや解除用の秘密情報をログやスクリーンショットに出さないでください。
4. 端末のアプリをバックグラウンドにして、別のテストアカウントから DM、メンション、スレッド返信を送ります。
   送信者名・チャンネル名・本文のプレビューと、タップ後の遷移先を確認します。
5. アプリを終了した状態でも同じ確認を行います。認証と同期の後に正しく遷移することを確認します。
   チャンネルへのアクセス権を削除し、保護された内容へのアクセスが拒否されることも確認します。
6. オフラインでログアウトしてから再接続し、サーバー側の登録解除を確認します。
   アカウントを切り替え、以前のアカウント宛ての通知から、新しいアカウントでその内容を開けないことを確認します。
7. 配布用プロファイルを使用した TestFlight で、本番環境の配信を再確認します。
   APNs の HTTP 410 応答を受けた無効・期限切れのデバイストークンが削除されることを確認します。
8. 通話を発信し、前面表示・バックグラウンド・ロック中・アプリが起動していない状態での着信と、
   応答・拒否・取消・期限切れ、ミュート・終了、実音声を確認します。通常通知のテストと結果を分けて記録します。
9. ペアリングしたWatchで、アプリを閉じている間の通知転送・振動・通知ボタンからの応答と拒否を確認します。
   Watchアプリ表示中の着信の振動と、応答・拒否・ミュート・終了も確認します。
   iPhoneとの切断・再接続、ログアウト時の表示消去も確認します。

実機と配備の結果は、単体テストやデモ画面のスクリーンショットと分けて記録してください。
これらの確認が完了するまでは、本番運用の準備が整ったと判断しないでください。
