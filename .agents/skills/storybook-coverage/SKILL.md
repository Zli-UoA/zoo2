# Storybookの設計と追加

## 目的と読み始める場所

Storybookは部品の一覧だけでなく、利用者が見る状態と操作を再現するカタログとする。まず `frontend/.storybook/coverage.json`、既存Story、対象実装、`.storybook/decorators.tsx`・`fixtures.ts`・`mock-api.ts` を読む。追加前に「どの実装の、どの表示・操作を確認するか」を決める。

## カテゴリ

| ルート | 対象 | 粒度・例 |
| --- | --- | --- |
| Foundations | 実際のデザイントークンと視覚的な規則 | 色、文字、余白。テーマはツールバーで切り替える |
| Components | ドメインを持たず再利用するUI | Button、Input、確認ダイアログ、設定セクション |
| Features | 利用者の目的に対応する機能の一部分 | Chat/MessageRow、Apps/Catalog、DMs/Create、Workspace/Members |
| Pages | ルート画面と全体レイアウト | Channel、ZooSettings、Notifications、Shell。画面幅と主要パネルの共存を確認 |
| Flows | 複数の操作・状態をまたぐ利用手順 | 管理者権限の変更→確認→反映、Appフォーム入力→送信失敗→再送信 |

タイトルは `<ルート>/<領域>/<対象>` を基本とする。部品名・ディレクトリ名だけで分類せず、確認する責務に合わせる。同じ画面をカテゴリごとに複製しない。単一ボタンのクリックはFeaturesのplayで十分で、Flowsに昇格させない。

## Storyを分ける基準

1 Story = レビューで区別して確認したい、安定して再現できる表示状態または操作結果。行数やファイル数を増やすためのStoryを作らない。

- 通常状態を置く。該当する場合は空、読込中、取得失敗、送信中、送信失敗を追加する。
- 所有者・管理者・一般メンバー、公開未参加・非公開・アーカイブなど、表示・操作が変わる権限境界を優先する。
- 長い本文・名前・URL、絵文字、画像欠損など、レイアウトの境界を含める。
- 開いたメニュー、確認画面、検証エラーなどは実際の操作で到達させる。
- モバイル用Storyは構成が変わる画面に追加する。全Storyに画面幅・全言語・明暗の直積を作らず、グローバルツールバーを使う。特定言語の不具合には専用回帰Storyを置ける。
- 親のStoryで確認できる内部部品は、対象一覧に親Storyと理由を記す。Providerや副作用だけの制御層は、統合テストのパスと除外理由を記す。除外を網羅済みと数えない。

## 実装

- 原則として実コンポーネントを描画する。アプリと異なる偽の空・エラー画面や、見た目だけの代替フォームを作らない。
- コレクションは共通fixture、APIはMSWを使い、外部サービス・本番資格情報に依存しない。既存fixtureを共有し、Story間で変更状態を持ち越さない。
- フローでは実フォームと確認ダイアログを使う。ルーティングを検証する場合は実ルーターを使う。`StoryShell` のローカル状態をブラウザ履歴の検証とみなさない。
- `play` はrole・labelを優先し、非同期結果を待って検証する。固定sleep、空のアサーション、内部stateの直接書換えは避ける。
- 新規Storyは原則 `a11y.test: "error"`。例外は具体的な理由をStoryに残す。既存のtodoを無条件に増やさない。

## 対象一覧と確認

`frontend/.storybook/coverage.json` に対象モジュール・Story・必要な状態を登録する。UIを追加・変更したら対象一覧も更新し、新規モジュールを除外する場合は理由と確認先を明示する。監査は「登録済みの状態が存在するか」を確認するもので、見た目の正しさや全状態の網羅率を保証するものではない。

1. `pnpm --dir frontend check:storybook` でタイトル・対象一覧・状態の欠落を確認する。
2. `pnpm --dir frontend exec vp check` を実行する。
3. `pnpm --dir frontend test:storybook` で実ブラウザのplayとa11yを確認する。
4. `pnpm --dir frontend build-storybook` で公開カタログを生成できることを確認する。
5. レイアウト変更は該当Storyを実ブラウザで確認する。結果には追加した領域・状態・未対応事項を記し、Story数だけを完了根拠にしない。
