# Slack からの取り込みとアカウント連携

Slack のエクスポート ZIP をアップロードすると、Zoo に保存します。保存した ZIP から、チャンネル・メッセージ・スレッド・リアクション・添付ファイルを Zoo に取り込めます。ZIP のアップロードはワークスペース管理者だけが行えます。

- 管理者は、保存した ZIP から任意のチャンネルを取り込めます（この文書の手順）。
- 各メンバーは、Slack アカウントを連携すると、自分が作った**非公開**チャンネルを、ZIP なしで取り込めます（後述の「自分の非公開チャンネルを取り込む（API）」）。公開チャンネルを取り込めるのは管理者だけです（ユーザーが管理者の ZIP から取り込む方式は廃止しました）。
- DM・グループ DM は、どちらの方法でも取り込みません（未対応です）。

Slack 連携の全体像は Zli-UoA/zoo2#115 を参照してください。

## 1. Slack でエクスポートする

1. Slack の「ワークスペースの設定」→「データのインポート/エクスポート」→「エクスポート」を開きます。エクスポートできるのはワークスペースのオーナーと管理者です。
2. 期間を選んでエクスポートを開始し、届いた ZIP をダウンロードします。
3. ZIP を展開せず、そのまま使います。

ZIP には公開チャンネル（`channels.json`）が入ります。プランや設定によっては非公開チャンネル（`groups.json`）も入ります。DM・グループ DM は取り込みません。

## 2. Zoo にアップロードする

1. Web 版の「Zoo設定」→「Slack 取り込み」を開きます。このタブは管理者にだけ表示されます。Android アプリにはありません。
2. 「ZIP を選んでアップロード」でファイルを選びます。ZIP はブラウザからストレージ（R2）へ直接アップロードされます。上限は `SLACK_IMPORT_MAX_ZIP_SIZE`（既定 5 GiB）です。
3. アップロードが終わると、バックエンドが ZIP を解析します。チャンネル数とメッセージ数が表示されるまで待ちます。
4. 解析が終わった ZIP は「取り込み可能」として保存され、管理者が「ZIP を削除」で消すまで残ります。同じワークスペースの新しい ZIP の解析が終わると、古い ZIP は置き換えられます（取り込み中のものは、取り込みが終わってから置き換えます）。

## 3. 取り込むチャンネルを選ぶ

保存した ZIP のカードに、チャンネルの一覧が表示されます。初めはどのチャンネルも「取り込まない」になっています。取り込むチャンネルだけ、取り込み方を次から選びます。

- **新しいチャンネル**：Zoo にチャンネルを作ります。名前は編集できます。`general` などの予約語や既存チャンネルと同じ名前のときは、`slack-` を付けた名前を提案します。取り込んだ管理者もメンバーに入ります。
- **既存のチャンネル**：既存の Zoo チャンネルに過去ログを追加します。Slack の非公開チャンネルは、Zoo の非公開チャンネルにしか取り込めません（メンバー以外に履歴が見えないようにするためです。新しく作る場合も非公開で作ります）。以前に取り込んだチャンネルは同じ取り込み先に固定され、別のチャンネルへは取り込めません（メッセージの ID は Slack のチャンネルと `ts` で決まるため、取り込み先を変えると過去ログが移らないためです）。以前の取り込み先を削除した場合は、過去ログが削除済みのチャンネルに残っているため、そのチャンネルは取り込み直せません（画面では「取り込まない」しか選べません）。暗号化チャンネル（[E2EE](e2ee.md)）には取り込めません（取り込みはメッセージを平文で保存するためです）。取り込み先に指定すると、開始が 400 `E2EE_PLAINTEXT_FORBIDDEN` になります。ジョブの実行中も、取り込み先が暗号化チャンネルなら書き込まずに失敗します。
- **取り込まない**

管理者の取り込み画面には、チャンネルが多いときのために、次の操作があります（React 版の Web だけです）。

- **一括指定**：「すべて新しいチャンネル」「すべて取り込まない」で、全チャンネルの取り込み方をまとめて変えます。以前に取り込んだチャンネルと、取り込み先が削除済みのチャンネルは、同じ取り込み先に固定されているので、「すべて新しいチャンネル」では変わりません。すでに「新しいチャンネル」にしたチャンネルは、編集した名前を保ちます。
- **取り込み後にアーカイブ**：「新しいチャンネル」にしたチャンネルは、チャンネルごとに、または一括で、取り込みが終わった時点でアーカイブできます。既存のチャンネルは、取り込み先でもアーカイブしません。Slack でアーカイブ済みのチャンネルは、指定がなくても、作った取り込み先をアーカイブします。

取り込み先になったチャンネル（新しく作ったものも、既存のものも）には、「Slack から取り込み」の印が付きます。React 版の Web と Compose（Android）の、チャンネル設定の右上に、小さな印「Slack から取り込み・新規作成（最後の取り込み <日付>）」（Slack から取り込んで作ったチャンネル）か「Slack から取り込み・既存（最後の取り込み <日付>）」（既存のチャンネルに取り込んだ）が出ます。管理者の取り込み画面（React 版の Web）でも、以前に取り込んだチャンネルの「取り込み先」に、同じ種類と最後に取り込んだ日付を出します。種類は最初の取り込みのもので、日付は、そのチャンネルの取り込みが終わるたびに更新します（取り込みが途中で失敗したときは更新しません。UTC で保存します。この版より前の取り込みは、メッセージの取り込みが終わったジョブの終了日時から補い、終わったジョブがなければ空にします）（`channels.slack_import_kind`・`slack_imported_at`）。ヘッダーとサイドバーの一覧には出さず、「チャンネルを探す」でも絞り込みません。TUI には、チャンネル設定の画面がないので、反映していません。この版より前に取り込んだチャンネルにも、マイグレーションで印を付けます。

「取り込む」を押すと取り込みが始まり、進み具合が表示されます。ZIP はそのまま残るので、続けて別のチャンネルを選んで取り込めます。以前に取り込んだチャンネルには「取り込み先: #チャンネル名」と表示されます。もう一度取り込んでもメッセージは重複しません。

取り込みの途中で、新しく作るチャンネルと同じ名前のチャンネルが別に作られた場合は、ジョブが「Channel name '…' is already taken」で失敗します（再試行はしません）。名前を変えて、もう一度取り込んでください。

## 取り込みの内容

- 投稿日時、編集日時、スレッド（返信は 1 階層）、リアクションを保ちます。親の投稿が後から取り込まれた場合も、先に入っていた返信はスレッドに戻ります。
- 編集・削除の履歴を含むエクスポート（投稿とは別に、`subtype` が `message_changed`・`message_deleted` の記録が入る形式）では、これらの記録を投稿として取り込みません。`message_changed` は、編集した日時と編集後の本文を持つので、取り込むと投稿が重複し、編集してから削除した投稿の本文も残ってしまいます。`message_deleted` が指す、削除された元の投稿（`original.ts`、または公開されている形式の `original_ts`）は、確認した範囲のエクスポートでは、普通の記録が残っていませんでした。同じ ZIP に残っていた場合は、取り込んだあとに論理削除します（その投稿への返信は、削除された親のスレッドに残り、チャンネル直下には出ません。別の日付のファイルにあれば、削除の記録を読んだときに論理削除します）。以前の取り込みで入れていた分は、保存済みの ZIP から再取り込みしたときに論理削除します。編集の記録の `ts` と同じ `ts` の、本物の投稿が同じファイルにある場合は、その投稿は消しません。同様に、以前の取り込みで、編集の記録を投稿として入れてしまった分も、再取り込みで論理削除します（取り込み済みのチャンネルは、同じ取り込み先を選んで、もう一度取り込んでください）。メッセージ数は、ZIP をアップロードしたときの解析で決まります。同じファイルに普通の記録が残っている削除済みの投稿は、数えて取り込んでから論理削除するので、件数は実際に処理した数と同じです。この修正の前にアップロードした ZIP では、編集・削除の記録を含む件数のまま表示されます（取り込み自体は、正しく完了します）。編集後の本文は、編集の記録からは反映しません（管理者が確認した ZIP では、普通の記録が編集後の最新の本文でした。ほかの ZIP で、普通の記録が古い本文のときは、最新の本文にならない場合があります）。ただし、再取り込みでは既存の投稿の本文を更新しないので、編集前の本文で取り込み済みのチャンネルは、編集前の本文のまま残ります。
- bot の投稿のカード（attachments）は Zoo のカードとして取り込みます。`https` でないリンクや上限を超える文字列は除くか切り詰めます。カードにできない場合も、本文が空にならないよう代わりの文字列を本文に入れます。Zoo ではカードのある投稿は本文を表示しないので、本文とカードの両方がある投稿は、本文も見出し「Slack」のカードとして先頭に入れます。カードの説明は MFM として描画しないので、このカードではリンクを「ラベル (URL)」の形にします。
- Slack の書式は Zoo の本文に変換します。`<@U…>` は `@ユーザー名`、`<#C…|name>` は `#チャンネル名`（取り込み先の今の名前。非公開のチャンネルに取り込んだものは、参加していない人に名前が見えないよう Slack の `name` のまま）、`<https://…|label>` は `[label](https://…)` になります。
- チャンネルへの参加・トピック変更などのシステムメッセージは取り込みません。本文（`text`）も attachments もなく、Block Kit（`blocks`）にだけ内容がある bot の投稿も、いまは取り込みません。本文がなく、ファイルだけの投稿は、添付として取得しないファイル（外部サービスの共有・削除済みなどの取り込めないもの、サイズや形式で取得をスキップするもの、トークンがなくて保留するもの）の名前を本文にして取り込みます。取得する添付は添付として表示するので、名前は本文に入れません（取得してから実際のサイズが上限を超えたと分かった場合は、そのときにファイル名を本文に入れます。取り込み時に補ったファイル名は、後から添付を取得できたときに本文から外します。投稿者が書いた本文は、ファイル名と同じ文字列でも変えません（補った行は `slack_files.in_content` に覚えています）。通信の失敗などで取得に失敗した場合は、添付ファイルを取得し直すまで空の投稿に見えます）。取り込めないファイルしかなく、名前も分からない投稿は取り込みません。その投稿がスレッドの親なら、返信はスレッドにならずチャンネル直下に並びます。
- Zoo に同じ名前のチャンネルがあるなどで `slack-` を付けた名前を候補にするとき、80 文字を超える場合は、元の名前の一部とハッシュにして 80 文字に収めます。
- ZIP の中の JSON ファイル（`users.json` や、チャンネルの 1 日分のファイル）は、1 つあたり 64 MiB までです。バックエンドのメモリの上限（本番は 512 MiB）の中で読むためです。超えるファイルがある ZIP は解析に失敗します。
- 取り込みでは通知・プッシュ通知・App へのイベントを出しません。取り込み先チャンネルの既存メンバーは、取り込んだ過去ログが既読の状態になります。
- 同じエクスポートを何度取り込んでも、メッセージは重複しません（Slack のチャンネル ID と `ts` から ID を決めています）。
- チャンネルごとに最後に取り込んだ `ts` を記録します。これは、差分同期（Zli-UoA/zoo2#292）の起点に使います。
- 「添付ファイルを取得」は、失敗した添付に加えて、サイズの上限（`ATTACHMENT_MAX_FILE_SIZE`）や取得を許可する URL（`SLACK_FILES_BASE_URL`）が理由でスキップした添付も取得し直します。Slack の `url_private_download` が 302 を返す場合は、許可した URL へのリダイレクトだけを最大 3 回まで追従し、Bot トークンは最初の URL と同じオリジンにだけ送ります。形式が非対応のものなど、設定では変わらないスキップは戻しません。
- 既存のチャンネルへ取り込むと、その時点の同期カーソルまで、チャンネルのメンバー全員の既読位置が進みます。取り込み前から未読だった古い投稿も既読になります（取り込みより新しい投稿は未読のまま残ります）。
- ZIP は、管理者が削除したとき、新しい ZIP に置き換わったとき、解析に失敗したとき、アップロードが 24 時間以上終わらないまま残ったときにストレージから削除します。アップロード中に削除したときは、ブラウザのアップロードも止めます。別のタブなどでアップロードが続いて、削除した後に ZIP が置かれた場合に備えて、署名付き URL の期限（`ATTACHMENT_PRESIGNED_PUT_EXPIRY_SECS`）から 1 日たったところで、もう一度削除します。

### Slack ユーザーの扱い

Slack ユーザーは、Zoo 上では「無効化済み」のプレースホルダユーザーとして作ります。作るのは、取り込んだチャンネルのメンバー・投稿者・リアクションした人・本文でメンションされた人だけです。ユーザー名は、実在の Zoo ユーザーと取り合わないよう `slack-` で始めます。プレースホルダはログインできず、チャンネルのメンバー一覧と人数・メンバー追加・メンション・DM の候補には出ません。通知も作りません（取り込んだチャンネルで `@here`・`@channel` を使っても、プレースホルダの数だけ通知が作られることはありません。プレースホルダの投稿へのリアクションも通知しません）。Slack アカウントと Zoo アカウントを連携すると（後述）、プレースホルダの投稿は本人に付け替わります。すでに連携済みのユーザーの投稿は、取り込んだ時点で本人の投稿になります。

### 添付ファイル

Slack のエクスポート ZIP には、添付ファイルの実体が入っていません。Zoo は ZIP に書かれた URL を記録しておき、`SLACK_IMPORT_BOT_TOKEN` が設定されていれば Slack から取得して添付ファイルとして保存します。

- トークンは `files:read` スコープを持つ Slack アプリのトークンです（Bot Token `xoxb-…` またはユーザートークン）。`SLACK_IMPORT_BOT_TOKEN` に加えて、行単位の取得（下記）は、連携したユーザーのトークン（`files:read`）でも取得します。
- `ATTACHMENT_MAX_FILE_SIZE` を超えるファイルと、実行ファイルなど添付できない種類のファイルはスキップします。
- 同じファイルを複数のメッセージで共有している場合は、メッセージごとに添付を作ります。
- トークンが未設定のまま取り込んだ場合、添付ファイルは「未取得」として残ります。トークンを設定してワーカーを再起動すると、完了済みのジョブの未取得の添付は、行単位の取得（下記）が自動で取得します。失敗・スキップした添付を取り直すときは、取り込み結果の「添付ファイルを取得」を使います。履歴に移った過去の取り込みからも取得できます。行単位の取得で取得した分は、そのジョブの `processed_files` にも反映します。管理画面の「添付ファイルを取得」（ジョブの取得）は、行単位の取得が取っている行（リースが有効な行）を飛ばします。
- 取得に 3 回失敗した添付は「取得できませんでした」として件数を表示します。トークンの権限などを直した後、「添付ファイルを取得」で取得し直せます。
- 差分同期（#292）で取り込んだ投稿の添付と、取り消された・失敗した・トークンなしで完了したジョブの添付（ジョブの取得が動かない行）は、ワーカーが `slack_files` の行ごとにリースを取って、1 件ずつ取得します。進行中のジョブ（解析・取り込み・添付の取得）と、開始前のジョブの行は、ジョブの取得に任せます。取得の処理（許可 URL・`ATTACHMENT_MAX_FILE_SIZE`・リダイレクト・保存先）は、ジョブの取得と同じです。
  - 差分同期は、本文のない添付だけの投稿に、取得できるまでファイル名を本文として入れます（`slack_files.in_content`）。取得できると、取り込みと同じく、そのファイル名を本文から外します。
  - 失敗は 3 回まで取り直します。1 回ごとに、10 分 × 失敗回数だけ間を置きます。3 回失敗すると `failed` になり、ファイル名は本文に残ります。Slack が 429 を返したときは、試行に数えず、`Retry-After`（最大 5 分）だけ待ちます。取得の途中でワーカーが落ち続けて、3 回取り直した行も `failed` にします。リースは 10 分です。
  - 削除済みのチャンネルと、暗号化チャンネル（[E2EE](e2ee.md)）の行は取得しません。
  - 行単位の取得は、`SLACK_IMPORT_BOT_TOKEN` があるか、Slack 連携（OAuth と `SLACK_TOKEN_ENCRYPTION_KEY`）が有効なワーカー（`zoo_slack_worker`、または `SLACK_IMPORT_WORKER` が有効な backend）だけが動かします。管理画面の「添付ファイルを取得」は、ジョブの添付だけを対象にします。
  - **取得に使うトークン**: 連携したユーザーのトークン（`files:read` を持つ人）→ Bot トークンの順に、1 件ずつ試します。Bot がチャンネルに参加していないと、Slack は Bot にログイン画面（`*.slack.com` へのリダイレクト）を返し、ファイルは見えません。ユーザーのトークンは、そのチャンネルを読める人の権限で取れます。
    - ユーザーのトークンは、同じワークスペースの連携のうち、`slack_user_links.scopes` に `files:read` がある人だけです。非公開チャンネルは、そのチャンネルのメンバーだけ。前回その Slack チャンネルを読めた人、メンバー、新しい連携の順で、人数では切らずに試します。
    - ユーザーのトークンは、**差分同期の行（`job_id` なし）だけ**に使います。ファイル ID と URL が Slack API の応答に由来するためです。ZIP の取り込みの行は、ファイル ID と URL を ZIP の提供者が決めるので、ユーザーの権限では取らず、Bot トークンだけで取ります（Bot が見えないファイルは取れません。Bot をチャンネルに招待してから取り直します）。差分同期の行でも、URL が `/files-pri/<team>-<file>/` の下（その行のファイル自身）のときだけ使います。トークンは、許可した URL（`SLACK_FILES_BASE_URL`）にだけ送ります。この許可は広げません。
    - Bot トークンがない環境では、ジョブの行は取らず、Bot を設定するまで未取得のまま残します（差分同期の行だけを、ユーザーのトークンで取ります）。
    - 全部のトークンにログイン画面が返ったら、取り直しても変わらないので、1 回で `failed`（`Slack file is not visible to any linked user or the bot`）にします。通信エラーや 5xx が混じるときは、これまでどおり取り直します。429 は、残りのトークンを試さずに待ちます。
    - `files:read` を持つユーザーが、まだ 1 人もいない間（再連携が進むまで）は、差分同期の行のうち Bot で見えないものを `failed` にせず、試行に数えないで、3 時間ごとに取り直します（`error` に `no linked user with files:read yet` が残ります）。ワークスペースに `files:read` を持つ連携が 1 人でもいれば、待ちません（そのチャンネルのメンバーが連携していない非公開チャンネルの行も、`failed` にします）。ユーザーのトークンを使えない行（ZIP の行、URL が別のファイルの行、許可していないワークスペースの行）も、待たずに `failed` にします。トークンを順に試す間は、行のリースを延ばします。
  - ジョブに紐づかない `failed` の行を取り直すには、次の SQL でリースごと戻します。
    ```sql
    UPDATE slack_files SET status='pending',attempts=0,error=NULL,lease_until=NULL,lease_token=NULL
    WHERE status='failed' AND job_id IS NULL;
    ```
    終わったジョブ（`completed`・`failed`・`cancelled`）の行（`job_id` あり）は、ユーザーのトークンでは取れないので、**Bot をそのチャンネルに招待してから**、次の SQL で戻します。Bot が見えないままだと、また `failed` になります。`error` が、Bot にログイン画面を返された失敗のものだけを対象にし、行単位の取得が拾わない行（削除済みか暗号化チャンネル）は戻しません（戻しても、永久に `pending` のままになるため）。管理画面の「添付ファイルを取得」は、ジョブを `fetching_files` に戻し、その間は Bot のトークンだけで取るので、同じ Bot の招待が済んでいれば使えます。
    ```sql
    UPDATE slack_files f SET status='pending',attempts=0,error=NULL,lease_until=NULL,lease_token=NULL
    FROM slack_import_jobs j, channels c
    WHERE f.status='failed' AND f.job_id=j.id AND j.status IN ('completed','failed','cancelled')
      AND c.id=f.channel_id AND c.deleted_at IS NULL AND NOT COALESCE(c.encrypted,false)
      AND (f.error LIKE '%redirected to a URL that is not allowed%' OR f.error LIKE '%login page%'
           OR f.error LIKE '%not visible to any linked user%');
    ```
    順序は、**Slack アプリの manifest を更新（ユーザースコープに `files:read`）→ デプロイ → ユーザーが連携し直す → `slack_user_links.scopes` に `files:read` を持つ人がいることを確認 → SQL** です。連携し直す前に戻しても、取得できません。

## サーバーの設定

マイグレーション `20261109000000_create_slack_import.sql`、`20261109001000_index_slack_files_job.sql`、`20261109002000_slack_import_exports.sql`、`20261109002500_slack_files_in_content.sql` を適用してください。取り込み先のチャンネルに付ける印（`channels.imported_from_slack`）には、`20261111000000_channels_imported_from_slack.sql` も適用してください（既存の取り込み先にも印を付けます）。取り込みの種類と日時（`slack_import_kind`・`slack_imported_at`）には、`20261112000000_channels_slack_import_info.sql` も適用してください（すでに取り込んだチャンネルは、ジョブの指定と記録から補います）。添付の行単位の取得には、`20261123000000_slack_files_lease.sql` も適用してください（`slack_files` にリースの列を足します）。取り込みのワーカーはバックエンド本体で動きます。複数台構成でも、DB のリースで 1 件のジョブを 1 台だけが処理します。処理中の台が止まった場合は、リースが切れてから別の台が続きを処理します。

| 環境変数 | 既定値 | 内容 |
| --- | --- | --- |
| `SLACK_IMPORT_MAX_ZIP_SIZE` | `5368709120`（5 GiB） | アップロードできる ZIP の上限（バイト）。5 GiB を超える値は設定できません |
| `SLACK_IMPORT_BOT_TOKEN` | なし | 添付ファイルを取得するための Slack トークン（`files:read`） |
| `SLACK_FILES_BASE_URL` | `https://files.slack.com/` | 添付ファイルを取得してよい URL。scheme・ホスト・ポートが一致し、パスがこの下にあるものだけを、Bot トークンを付けて取得します |
| `SLACK_IMPORT_TMP_DIR` | OS の一時ディレクトリ（`/tmp`） | ワーカーが ZIP をダウンロードして展開するディレクトリ。ZIP はほかのユーザーから読めないよう `0600` で作ります |

ZIP は添付ファイルと同じバケット（`S3_*`）の `slack-imports/` の下に置きます（削除されるまで残るので、その分のストレージを使います）。ブラウザから直接 PUT するため、バケットの CORS で PUT を許可しておく必要があります（`infra/terraform/r2.tf` で設定済みです）。ワーカーは解析と取り込みのために ZIP を `SLACK_IMPORT_TMP_DIR` へダウンロードするので、書き込みができて ZIP と同じ程度の空き容量があるディレクトリが必要です。Kubernetes でルートファイルシステムを読み取り専用にしている場合は、`emptyDir`（`sizeLimit` を ZIP の上限以上にする）をマウントして指定してください。書き込めないと、解析と取り込みは `SLACK_IMPORT_TMP_DIR` を含むエラーで失敗します。zli.chat の本番と Preview では Zli-UoA/zoo2-infra#122（マージ済み）で、`emptyDir`・`SLACK_IMPORT_TMP_DIR`・`fsGroup` を設定します。この PR を配備する前に、本番と Preview の backend にその設定が反映されていることを確認してください。ワーカーは使っている間 ZIP にロックをかけておき、起動時に、どのプロセスもロックしていない `zoo-slack-import-*.zip` を消します。取り込みの途中でコンテナが再起動しても（`emptyDir` はコンテナの再起動では消えません）、前のプロセスが残した ZIP で容量の上限を超えることはありません。

### 専用のワーカー（`zoo_slack_worker`）

取り込み（解析・取り込み・添付の取得）と差分同期のワーカーは、既定では backend のプロセスの中で動きます。backend の更新や再起動のたびに、処理中のジョブが止まるので、長い取り込みは、専用のプロセスに分けられます。

- バイナリは `zoo_slack_worker`（backend と同じイメージ。Deployment の `command` に `/home/nonroot/zoo_slack_worker` を指定します）。HTTP の API は持たず、`/healthz`（`SLACK_WORKER_PORT`、既定 8082）だけを返します。設定は backend と同じ環境変数です（`DATABASE_URL`、`S3_*`、`SLACK_*`、`ENVIRONMENT` など。`Config::validate` も同じ検査をするので、本番では OIDC の設定も要ります）。`SLACK_IMPORT_TMP_DIR` と `emptyDir` は、専用のワーカーの Pod に付けます。
- backend 側は、環境変数 `SLACK_IMPORT_WORKER=false`（`false`/`0`/`off`/`disabled`/`no`）で、取り込みと差分同期のワーカーを止めます。未設定・空・その他の値は、従来どおり有効です（書き間違いは警告のログが出ます）。起動時に読むので、変えたら再起動してください。
- 管理画面からの操作（ZIP のアップロード、取り込みの開始、取り消し、添付の再取得）は、backend の API がデータベースのジョブの行を変えるだけなので、ワーカーの場所に関係なく、これまでどおり使えます。
- 専用のワーカーと backend のワーカーが同時に動いても、1 つのジョブは `FOR UPDATE SKIP LOCKED` とリースで、1 台だけが進めます。配備の途中で両方が動く期間があっても安全です。
- SIGTERM を受けると、処理中のジョブを手放します。`attempts` は消費せず、`handoffs` を 1 増やし、30 秒後から別のワーカーが取れます。取り込みは、日付ファイルごとに再開位置（`import_progress`）を保存するので、やり直しは、取り込み済みの日付ファイルを飛ばします。
- 配備の順序: (1) このバイナリを含むイメージを配備する（backend の挙動は変わりません）、(2) 専用のワーカーの Deployment を足して、`/healthz` が通り、小さな ZIP が最後まで取り込めることを確認する、(3) backend に `SLACK_IMPORT_WORKER=false` を足して再起動する。戻すときは、この env を外して再起動します。


ZIP はブラウザから署名付き URL に直接 PUT するので、フロントエンドの CSP の `connect-src` に、ストレージの公開オリジン（`CSP_STORAGE_SRC`。添付ファイルと同じ設定）が必要です。公開オリジンが Cloudflare のプロキシ配下だと、プランごとのリクエスト本文の上限（Free・Pro は 100 MB、Business は 200 MB）を超える ZIP はブラウザーから PUT できません。そのような大きな ZIP は、ブラウザーを使わず、管理者が手動でストレージへ直接アップロードします（「大きな ZIP を手動でアップロードする」）。プレースホルダのアイコンは Slack のプロフィール画像の URL（`https://avatars.slack-edge.com/…` など）を使うので、表示するには、その配信元を `CSP_APP_IMAGE_SRC`（`img-src`）に追加します。追加しない場合は、既定のアイコンを表示します。`SLACK_IMPORT_BOT_TOKEN` で添付ファイルを取得する場合は、バックエンドから `files.slack.com`（`SLACK_FILES_BASE_URL` のホスト）へ HTTPS で接続できる必要があります。NetworkPolicy などで外向きの通信を絞っている場合は、許可してください。

### 大きな ZIP を手動でアップロードする

Cloudflare の本文上限を超える ZIP は、ブラウザーではなく、バックエンドが使っているストレージのエンドポイント（`S3_ENDPOINT`。Cloudflare のプロキシを通らない）へ、`kubectl` で Secret から認証情報を読んで直接置きます。

1. 設定画面の「Slack 取り込み」タブで、その ZIP を選んでジョブを作ります。ブラウザーからのアップロードは失敗しますが、ジョブは「アップロード中」のまま残ります。アップロード中のジョブは 24 時間で取り消されるので、手順 4 までを、ジョブを作ってから 24 時間以内に終えてください。`GET /api/admin/slack-imports` で、そのジョブの `id` を確かめます（管理者の Bearer トークンが必要です）。
2. バックエンドが使うストレージの設定を、そのシェルの環境変数に入れます。バックエンドのイメージは distroless で、`kubectl exec` で `sh` や `printenv` を実行できないので、Deployment と Secret から読みます。値は画面に出さず、端末の履歴にも残しません。名前空間・Deployment 名・Secret 名は、環境に合わせてください。

   まず、Deployment の環境変数の定義を確かめます。`S3_ENDPOINT`・`S3_BUCKET` の値と、`S3_ACCESS_KEY_ID`・`S3_SECRET_ACCESS_KEY` が参照する Secret の名前とキーが分かります。Secret の値は出ません。

   ```bash
   kubectl -n zoo2 get deploy backend -o jsonpath='{.spec.template.spec.containers[0].env}'
   ```

   次に、バックエンドの名前 `S3_ACCESS_KEY_ID`・`S3_SECRET_ACCESS_KEY` を、AWS CLI の名前 `AWS_ACCESS_KEY_ID`・`AWS_SECRET_ACCESS_KEY` に読み替えて入れます。`<Secret 名>` と `<キー名>` は、上で確かめた値です。

   ```bash
   export S3_ENDPOINT='<S3_ENDPOINT の値>' S3_BUCKET='<S3_BUCKET の値>'
   export AWS_ACCESS_KEY_ID="$(kubectl -n zoo2 get secret <Secret 名> -o jsonpath='{.data.<S3_ACCESS_KEY_ID のキー名>}' | base64 -d)"
   export AWS_SECRET_ACCESS_KEY="$(kubectl -n zoo2 get secret <Secret 名> -o jsonpath='{.data.<S3_SECRET_ACCESS_KEY のキー名>}' | base64 -d)"
   ```

3. `slack-imports/<ジョブの id>/export.zip` というキーに置きます。`aws s3 cp` は、必要に応じてマルチパートで送ります。`Content-Type` は `application/zip` にします（手順 4 で照合します）。

   ```bash
   AWS_REGION=auto aws s3 cp ./export.zip "s3://$S3_BUCKET/slack-imports/<ジョブの id>/export.zip" --endpoint-url "$S3_ENDPOINT" --content-type application/zip
   ```

4. `POST /api/admin/slack-imports/<ジョブの id>/uploaded` を呼びます。ストレージ上のサイズが、ジョブ作成時に送ったサイズと同じか確かめたうえで、解析が始まります。以降はブラウザーからの場合と同じです。

キーやサイズ、`Content-Type` が違うと、4 の確認で失敗します。置いた ZIP はジョブを削除したときに、通常の ZIP と同じように消えます。

この鍵はバケット全体（添付ファイルを含む）の読み書きに使うもので、Secret を読める人は取り出せます。画面共有や録画の中では実行せず、終わったらそのシェルを閉じて、環境変数を残さないでください。鍵を取り出したくない場合は、手元の CLI などで署名付き PUT URL を作って送る方法もあります。

Preview で使うときは、名前空間・Secret 名・`S3_ENDPOINT` の値が本番と同じとは限らないので、確かめてから読み替えてください。

## Slack アカウントの連携

各ユーザーは、自分の Slack アカウントを Zoo アカウントに連携できます。管理者の作業は、最初に Slack アプリを 1 つ作ることだけです。

### 管理者: Slack アプリを作る

Slack の配布アプリ（Marketplace の審査を通っていないもの）は `conversations.history` などのレート制限が厳しいため、ワークスペースごとに社内アプリ（internal app）を作ります（`conversations.history` / `conversations.replies` は、差分同期（Zli-UoA/zoo2#292）で使います）。

1. 管理者のアクセストークンで `GET /api/admin/slack/manifest` を呼び、レスポンスの `manifest` をコピーします（設定画面には、manifest の欄はありません）。アクセストークンは、管理者でログインしているブラウザーのタブの開発者ツールのコンソールで、次を実行すると取り出せます（OIDC を使う構成の場合。トークンは `sessionStorage` の `zoo.oidc.session` に入っています。有効期限が短いので、取り出したらすぐ使い、どこにも貼らないでください）。

   ```js
   JSON.parse(sessionStorage.getItem("zoo.oidc.session")).tokens.accessToken
   ```

   取り出したトークンで、次のように呼びます。トークンを端末の履歴に残さないよう、`read -rs` で入力します。

   ```bash
   read -rs TOKEN && curl -sf -H "Authorization: Bearer $TOKEN" https://<zoo-backend>/api/admin/slack/manifest | jq .manifest
   ```

   初回は `SLACK_OAUTH_REDIRECT_URL` がまだ設定されていないので、manifest の `redirect_urls` は `https://<zoo-backend>/api/slack/oauth/callback` という仮の値です。貼り付ける前に、`<zoo-backend>` を実際のバックエンドの公開 URL に書き換えてください（Client ID と Client Secret は、アプリを作った後でないと分からないので、環境変数は手順 4 でまとめて設定します）。
2. <https://api.slack.com/apps> で「Create New App」→「From an app manifest」を選び、ワークスペースを選んで manifest を貼り付けます。
3. アプリをワークスペースにインストールし、「Basic Information」の Client ID と Client Secret を控えます。
4. バックエンドに次の環境変数を設定して再起動します。

| 環境変数 | 内容 |
| --- | --- |
| `SLACK_CLIENT_ID` / `SLACK_CLIENT_SECRET` | Slack アプリの Client ID と Client Secret |
| `SLACK_OAUTH_REDIRECT_URL` | `https://<バックエンドの公開URL>/api/slack/oauth/callback`。manifest の `redirect_urls` と一致させます |
| `SLACK_TOKEN_ENCRYPTION_KEY` | ユーザートークンの暗号化と state の署名に使う 32 バイトの鍵（base64）。`openssl rand -base64 32` などで作ります |
| `SLACK_TEAM_ID` | 連携を許可する Slack ワークスペースの ID（`T…`）。任意ですが設定を推奨します。設定・変更する前に別のワークスペースで連携したアカウントは、連携済みとして表示されますが、チャンネルの取り込みには使えません（403 `team_mismatch`）。設定画面の案内に従って解除し、連携し直してもらってください。変更する前に始まった取り込みは、そのまま進みます |
| `SLACK_FRONTEND_URL` | 連携後に戻るフロントエンドのオリジン。フロントとバックエンドが同一オリジンなら不要です |
| `SLACK_APP_ID` | 任意。この Slack アプリの ID（`A…`。「Basic Information」の「App ID」。Secret ではありません）。設定すると、受信口（`POST /api/slack/events`）は、`api_app_id` が違うイベントを、200 を返して何もせずに無視し、取り込み（差分同期・イベント・ZIP）は、`app_id` が一致するメッセージ（このアプリが投稿したもの）を取り込みません。**Slack アプリを作り直して ID が変わったときは、更新してください**（古い値のままだと、新しいアプリのイベントが、エラーなしに無視され、リアルタイムの同期が止まったように見えます）。未設定なら、どちらも行いません |
| `SLACK_SIGNING_SECRET` | 任意。Slack アプリの Signing Secret（「Basic Information」の「App Credentials」）。設定すると、Slack の Events API の受信口（`POST /api/slack/events`）が有効になります（後述の「Events API で、投稿をすぐに同期する」）。未設定なら受信口は 404 で、これまでどおりです。上の 4 つが未設定のまま、これだけを設定すると、設定ミスとして起動時にエラーになります（`zoo_slack_worker` も同じ検査をします） |

`SLACK_CLIENT_ID`・`SLACK_CLIENT_SECRET`・`SLACK_OAUTH_REDIRECT_URL`・`SLACK_TOKEN_ENCRYPTION_KEY` は 4 つそろえて設定してください。一部だけだと起動時にエラーになり、バックエンドが起動しません。デプロイは、マイグレーションを適用する → 4 つの環境変数を同時に設定する → バックエンドを再起動する、の順に行います。

Slack アプリが求めるスコープは、差分同期（#292）とブリッジ（#293・#294）で使うものも含めて、先にまとめて求めます。スコープを足すたびに、連携済みの全ユーザーに連携を解除してから連携し直してもらう必要があるためです。差分同期（#292）は、ユーザートークンで `conversations.info`・`conversations.history`・`conversations.replies`・`users.info` を呼びます。

| 種類 | スコープ | 使う機能 |
| --- | --- | --- |
| ユーザー | `users:read` | 連携時に Slack の表示名を取得します（いまの版で使用） |
| ユーザー | `channels:history` `groups:history` `im:history` `mpim:history` | 差分同期（#292）の `conversations.history` / `conversations.replies`。ブリッジ（#293）の `message.*` の購読 |
| ユーザー | `channels:read` `groups:read` `im:read` `mpim:read` | 参加しているチャンネルの列挙（#292） |
| ユーザー | `reactions:read` | `reaction_added` / `reaction_removed`（#293） |
| ユーザー | `reactions:write` `chat:write` | Zoo の投稿・編集・削除・リアクションを、本人として Slack に反映する（#294） |
| ユーザー | `files:read` | 添付ファイルの取得。Bot が入っていないチャンネルのファイルを、そのチャンネルを読める連携ユーザーの権限で取る（このスコープを足したので、連携済みのユーザーは、連携を解除して連携し直す） |
| Bot | `files:read` | `SLACK_IMPORT_BOT_TOKEN` として、取り込みの添付ファイルを取得する（いまの版で使用） |
| Bot | `chat:write` `chat:write.customize` | Slack と連携していないユーザーの投稿を、Bot が `username` / `icon_url` を付けて代理で投稿する（#294） |

ユーザートークンに履歴スコープを求めるので、連携したユーザーは、自分が参加している会話（非公開チャンネルと DM を含む）の履歴を、Zoo が読めるようにすることに同意することになります。差分同期（#292）は、この履歴スコープで、対応済みのチャンネルの履歴を読みます。

履歴スコープのない、以前の版で連携したユーザーのトークンは、Slack が `missing_scope` を返すので使われません（ほかの連携済みメンバーのトークンで同期します）。連携し直してもらうと使えます。

Bot は、いまはチャンネルに参加しないので、非公開チャンネルや DM の添付は取得できないことがあります（Slack がログイン画面を返すと、添付は `failed` になります。取り込み時の添付は、取得に失敗するとファイル名が本文に入らず、本文のない投稿は空に見えます。差分同期で取り込んだ添付は、取得に失敗しても、補ったファイル名が本文に残ります。Bot で見えないファイルは、`files:read` を持つ連携ユーザーのトークンで取ります。「添付ファイル」の行単位の取得を参照）。#293 の受信口は、ユーザーのイベント（`user_events`）を購読します（Bot は使いません）。Bot の購読（`bot_events`）にする場合は、Bot の履歴スコープとチャンネルへの参加（`channels:join`）が別に必要になります。

すでにこの版より前の manifest でアプリを作っている場合は、アプリの manifest を更新して再インストールし、各ユーザーに連携を解除してから連携し直してもらいます（`slack_user_links.scopes` で、まだのユーザーを判別できます）。以前に認可したユーザーのトークンは、そのままでは古いスコープのままです。以前に広いスコープで認可したユーザーが、狭めたい場合も、連携を解除してから連携し直してもらいます。

#### 鍵を変えるとき・連携をやめるとき

保存したユーザートークンは、連携を解除したときに Slack 側で失効させるためだけに使います。`SLACK_TOKEN_ENCRYPTION_KEY` を変えると、保存済みのトークンを復号できなくなります。そのまま連携を解除すると Zoo の記録が消えるだけで、Slack 側のトークンは有効なまま残ります（バックエンドのログに `team_id` と `slack_user_id` 付きのエラーを出します）。この鍵は連携開始時の state の署名にも使うので、鍵を変えた時点で連携の途中だった人は、もう一度「Slack と連携」からやり直す必要があります。連携の環境変数を外したり、この機能より前の版に戻したりした場合も、`slack_user_links` のトークンは Slack 側で有効なまま残ります。

鍵を変えるときや連携をやめるときは、次のいずれかを行ってください。

- 鍵を変える前に、連携中のユーザー全員に連携を解除してもらいます。解除したユーザーは、鍵を変えた後に連携し直せます。
- <https://api.slack.com/apps> で Zoo のアプリを開き、ワークスペースからアンインストールして、このアプリのトークンをすべて失効させます。Bot Token も失効するので、このアプリの Bot Token を `SLACK_IMPORT_BOT_TOKEN` に使っている場合は、別のトークンに差し替えるか外してください。続けて使う場合はアプリをインストールし直します。連携をやめる場合は、そのあと `DELETE FROM slack_user_links;` を実行してから環境変数を外すか版を戻します。付け替えた投稿と `slack_users` の対応は残るので、再開したあとも、同じ Slack アカウントは同じ Zoo アカウントにだけ連携し直せます。

鍵が漏れたおそれがある場合は、DB の暗号文から元のトークンを取り出せます。必ず最後の方法ですべて失効させてください。

連携の環境変数をすべて外している間は、トークンを失効できないので、連携を解除できません（404）。設定を戻してから解除してください。

### ユーザー: 連携する

1. 「Zoo設定」→「Slack 連携」で「Slack と連携」を押します。
2. Slack で内容を確認して許可すると、Zoo の設定画面に戻り、連携が完了します。
3. 取り込み済みの過去ログにあなたのプレースホルダがあれば、その投稿・リアクション・参加チャンネルがあなたのものになります。取り込んだチャンネルの本文にあるプレースホルダへのメンション（`@slack-…`）も、あなたのユーザー名に書き換わります。書き換えるのは、通知のメンションと同じく `@` の直前が行頭・空白・開き括弧・`。`・`、` などの区切りのものだけです（`あ@slack-…` のように文字に続くものや、メールアドレス・URL の中は書き換えません）。書き換えると本文の上限（40,000 文字）を超える投稿は、本文もカードも書き換えずに残します。本文を入れたカードの説明は、取り込みのときと同じく 4,000 文字で切ります。新しく参加したチャンネルの過去ログは、取り込んだところまで既読の状態になります（取り込みより後の投稿は未読のまま残ります）。

ゲスト（1 チャンネル・複数チャンネルのゲスト）が連携した場合は、投稿・リアクション・添付だけが本人のものになり、参加チャンネルは移りません。ゲストが参加するチャンネルは管理者が決めるためです。連携後の取り込みでも、ゲストを Slack のメンバーとしてチャンネルに足すことはしません。

Android アプリでは、「Slack と連携」を押すと外部のブラウザーで Slack の認可画面が開きます。アプリへ戻る deep link には未対応なので、連携の完了はブラウザー側で行います（ブラウザーでも Zoo にログインしている必要があります）。アプリに戻ると、連携の状態を読み直し、キャンセルした場合も続けて連携をやり直せます。

1 つの Slack アカウントは 1 つの Zoo アカウントにだけ連携できます。連携を解除すると Slack のトークンを無効にして削除しますが、付け替えた投稿は元に戻しません。管理者が鍵を変えた後に解除した場合は、Slack のトークンは無効になりません（「鍵を変えるとき・連携をやめるとき」）。同じ Slack アカウントは、解除後も同じ Zoo アカウントにだけ連携し直せます。

### ユーザー: 自分の非公開チャンネルを取り込む（API）

連携すると、「Slack 連携」タブに「Slack から取り込む」が表示されます。ZIP は使わず、連携した本人のトークンで Slack の API を読み、Slack で自分が作った非公開チャンネルを取り込みます。

- 一覧は `GET /api/slack/private-channels` です。Slack の `users.conversations`（非公開チャンネルだけ）で、自分が参加しているチャンネルを列挙し、作成者（`creator`）が自分のものだけを返します。他の人が作った非公開チャンネルと、DM・グループ DM は出ません。
- 開始は `POST /api/slack/private-channels/import`（`{"slack_channel_id","name"}`。1 回の要求で 1 チャンネルです）です。サーバーが `conversations.info` で、非公開で作成者が本人であることを確かめ直します（満たさなければ 403）。ゲストは、通常のチャンネル作成と同じく取り込めません（403）。
- 取り込むたびに、新しい非公開の Zoo チャンネルを作ります（作成者は本人。名前は画面で直せます。使われている名前には `slack-` を付けた名前を提案します）。既存のチャンネルへの取り込みはできません。ID は Slack のワークスペースとチャンネルの ID から決まり、同じチャンネルを二度取り込むと 409 になります。決定的な ID の他人のチャンネルがすでにあれば、そこへは取り込みません。
- メンバーは `conversations.members` で取得し、未連携の人はプレースホルダとして参加させます（エクスポートの取り込みと同じです。連携すると本人に付け替わります）。名前は `users.info` で調べます（上限 50 人。調べられない人は Slack の ID の名前になります）。
- 履歴は、差分同期（次の節）のエンジンが、同期カーソル（`slack_channels.last_ts`）を `0` にして全履歴から取ります。この最初の同期だけは、返信のあるスレッドを、差分同期の監視範囲（3 日・最大 20 スレッド）に限らず全部取り、終わったときに、既存メンバーの既読位置を取り込んだ履歴の最新まで進めます（過去ログが未読として並ばないようにするため。エクスポートの取り込みと同じです）。メンバー・チャンネルの一覧は、続きのページがある間は取得を続け、上限（1 万件）を超えたときは、不完全なまま確定せずにエラーにします。取り込みを始めたチャンネルだけがこの扱いで、カーソルのないチャンネルを同期が勝手に全履歴で取ることは、これまでどおりありません。ページごとに途中経過を保存するので、止まっても続きから再開します。Slack のレート制限（429）には `Retry-After` に従って待ちます。大きなチャンネルは時間がかかります。
- 進捗は、一覧の `status` で返します（`new`・`queued`・`running`・`done`・`error`・`hidden`）。`hidden` は、取り込み済みで、自分が参加していないチャンネルです（名前と ID は返しません）。取り込みが終わったあとも、新しい投稿は 5 分ごとに同期されます。
- 添付ファイルは、差分同期と同じく、取得できるまでファイル名を本文に残し、ワーカーが Slack から取得して添付にします（「添付ファイル」の行単位の取得）。Bot に見えないファイルは、`files:read` を持つ連携ユーザーのトークンで取ります。どのトークンでも見えないファイルは `failed` になり、ファイル名が本文に残ります。
- 非公開チャンネルの履歴を読むには、連携時に `groups:read` と `groups:history` が必要です。以前の版で連携して、このスコープがない人には、一覧が理由 `missing_scope` を返し、画面で連携し直しを案内します（トークンの失効などでも同じです）。
- `SLACK_TEAM_ID` で許可していないワークスペースの連携では、一覧に何も出ず（`team_mismatch`）、開始は 403 です。

### 仕組み

- Slack から戻るリダイレクト先（`/api/slack/oauth/callback`）ではトークンを交換しません。`code` と `state` を付けて設定画面に戻し、フロントがログイン中のユーザーとして `POST /api/slack/oauth/complete` を呼びます。サーバーは、state に署名された「連携を始めたユーザー」と呼び出したユーザーが一致するときだけ連携します。他人が作った認可 URL を踏まされても、その人の Zoo アカウントに自分の Slack アカウントが連携されることはありません。
- state は 10 分で期限が切れます。
- ユーザートークンは AES-256-GCM で暗号化して `slack_user_links` に保存します。この表は Electric の Shape に含めません。
- 同じ Slack アカウントの連携の保存・解除と、使わないトークンの失効は、アカウントごとのロックで 1 つずつ処理します。Slack は同じアカウントで認可し直すと同じトークンを返すため、連携できなかったときに受け取ったトークンは、そのアカウントの連携に保存されていないことを確かめてから失効させます（別のワークスペースのアカウントでも同じです）。連携を保存する前にもトークンが有効か確かめ、並行した解除などで失効していた場合は、連携せずにエラー（502）を返します。もう一度連携してください。
- 付け替え（連携と、取り込みの最後に行う照合）は、ワークスペースをまたいで 1 つずつ処理します。既存のチャンネルを取り込み先に選べば、別のワークスペースも同じ Zoo チャンネルに取り込めるためです。本文のメンションを書き換えるときは、書き換えるプレースホルダへのメンションを含む投稿だけをロックします。
- 付け替えの間は App へのイベント配送を止めます。

マイグレーション `20261109003000_create_slack_user_links.sql`、`20261109004000_index_slack_reassign.sql` を適用してください。

## 差分同期

エクスポートより後の投稿は、連携済みのユーザーのトークンで、システムが自動的に取り込みます（Zli-UoA/zoo2#292）。連携した直後と、そのあとは 5 分ごとに、対応済みのチャンネル（`slack_channels`）を同期します。`SLACK_CLIENT_ID` などの連携の設定（上の 4 つ）があるときだけ動きます。

- **トークン**: 同じチャンネルは、そのワークスペースの連携済みメンバーのうち 1 人のトークンで取得します。非公開の Zoo チャンネルは、そのメンバーのトークンだけを使い、公開のチャンネルは、メンバーのトークンを先に試します。読めないトークン（チャンネルに参加していない、トークンが失効した、履歴スコープがない）は飛ばして、次のメンバーのトークンで取り直します。誰のトークンでも読めないときは、1 時間後に取り直します。
- **カーソル**: 同期の起点は `slack_channels.last_ts` で、チャンネル単位で共有します（人数分の取得はしません）。`conversations.history` は新しい順に返すので、`last_ts` は同期が最後まで終わったときにだけ、取得した最新の投稿の `ts` まで進めます。
- **スレッド**: 取得した投稿のうちスレッドの親があれば、返信を `conversations.replies` で取得します。返信がまだない投稿も含め、3 日以内の親になりうる投稿（最大 20 件、新しい順）は、新しい返信がないか毎回確かめます（同期のあとで初めて返信が付いても取り込むため）。
- **キューと再開**: チャンネルごとにキュー（`slack_channel_syncs`）の 1 行を持ち、複数台のバックエンドが、`FOR UPDATE SKIP LOCKED` とリースで 1 チャンネルを 1 台だけが進めます。1 ページ（または 1 スレッド）ごとに、書き込みと同じトランザクションで、ページのカーソルと残りのスレッドを保存するので、止まっても続きから再開します。ページのカーソルが期限切れ（`invalid_cursor`）になったときは、保存した位置を捨て、同期カーソルから取り直します。取り込みの書き込みは決定的 ID の `ON CONFLICT DO NOTHING` なので、取り直しや、ZIP の取り込みとの重なりで投稿が重複することはありません。取り込みのジョブが動いているワークスペースは、そのジョブが終わるまで同期を待ちます。
- **429**: `Retry-After` の秒数だけ、そのチャンネルの次の実行を遅らせます（ほかのチャンネルは進みます）。途中経過は保存済みで、失敗の回数には数えません。そのほかの失敗は、30 秒から最大 1 時間まで、回数に応じて待ちを延ばして再実行します。
- **非公開チャンネル**: 取り込み先は、対応付けた Zoo のチャンネルだけです。Slack が非公開（非公開チャンネル・DM）と答えたチャンネルが、公開の Zoo チャンネルに対応付いているときは、取り込みません（`slack_channel_syncs.last_error` に `private_slack_channel_in_public_channel` が残ります）。
- **ブリッジの穴埋め**: ブリッジ（#293）が取りこぼした（ダウンタイムなど）チャンネルは、`slack::sync::request_channel` で、すぐに同期できます。カーソルより後を取り直すだけなので、取り込み済みの投稿とは重複しません。
- **イベントによる前倒し**: Slack の Events API が投稿を知らせたチャンネルは、5 分を待たずに同期します（次の節）。反映するのは、これまでどおり差分同期だけです。
- **待ち（`not_before`）**: 429・失敗・保留（`Park`）のあとの待ちは、`slack_channel_syncs.not_before` に残します。イベントによる前倒しは、この待ちの間は行いません（429 の最中に、イベントのたびに Slack を叩き直さないためです）。
- **対象外（今の版）**: DM・グループ DM の取り込み（チャンネルの作成と、メンバーの対応付けが必要なため）。まだ Zoo のチャンネルと対応付いていない非公開チャンネルは、本人が「Slack 連携」タブから取り込みを始めると同期の対象になります（上の「自分の非公開チャンネルを取り込む（API）」）。取り込み済みの投稿の編集・削除・リアクションの変更は、Events API のイベント（`SLACK_SIGNING_SECRET` が必要）で反映します（「Events API で、投稿をすぐに同期する」）。イベントを使わない構成では、反映されません（`conversations.history` は削除を返さず、取り込み済みの投稿を取り直さないためです）。同期した投稿の添付ファイルは、ワーカーが取得します（「添付ファイル」の行単位の取得）。取得できるまでは、ファイル名を本文に残します。

マイグレーション `20261120000000_slack_channel_syncs.sql` を適用してください。

## Events API で、投稿をすぐに同期する

Slack の Events API は、「このチャンネルを今すぐ同期して」という合図にだけ使います（Zli-UoA/zoo2#293）。**ポーリング（差分同期）が正**で、イベントの本文は見ません。

- **受信口**: `POST /api/slack/events`（バックエンドの公開 URL。認証はなし）。`SLACK_SIGNING_SECRET` があるときだけ有効です。署名（`X-Slack-Signature` の `v0=…`）とタイムスタンプ（現在から前後 5 分以内）を、定数時間の比較で検証します。署名が合わない要求は 401 で、DB には触れません。ボディの上限は 256 KiB です。`url_verification` は、署名が正しければ `challenge` を返します。
- **取り出すもの**: ワークスペース ID とチャンネル ID、確かめ直すメッセージの `ts`、リアクションの名前とした人（Slack の ID）だけです。本文は読み捨て、保存もログにも出しません。合図にするのは、新しい投稿（`message`）、編集・削除（`message_changed` / `message_deleted`）、メッセージへのリアクションの追加・削除（`reaction_added` / `reaction_removed`）です。入退室・トピックなどのシステム通知と、ファイルへのリアクションは無視します。
- **登録のないものは無視**: 許可していないワークスペース（`SLACK_TEAM_ID`）や、Zoo のチャンネルと対応付いていないチャンネルは、何も書かずに 200 を返します。
- **合図**: `slack_channel_wakes` に、チャンネルごとに 1 行（`first_at`・`last_at`）を書き、すぐ 200 を返します（Slack は 3 秒以内の応答を求めます）。再送（`X-Slack-Retry-Num`）や同じ内容の重複は、同じ行への UPSERT なので、結果が変わりません。DB の書き込みに失敗したら 500 を返し、Slack の再送（最大 3 回）に任せます。`slack_channel_syncs` の行は、同期のトランザクションが長く握るので、受信口はそこを更新しません。
- **起こし方**: 同期のワーカーは、最初の合図から **3 秒**（続けて届くイベントを 1 回にまとめる）たち、前回の同期の終わりから **30 秒**以上空いたチャンネルを、定期の実行（5 分）を待たずに取ります。新しい同期を始めるときに、合図の行を消します。同期の途中（ページの再開）では消さず、途中より新しい投稿は、同期が終わったあとの次の同期で取ります。同時に 2 つの同期が走らないことは、これまでのリースが守ります。ワーカーは 1 プロセスで順に進めるので、ほかのチャンネルの期限が過ぎていれば、その後ろになります。
- **API の呼び出しを抑える**: 合図で起きる同期は、直近 5 分以内に「監視中のスレッドを全部取り直す同期」（`slack_channel_syncs.swept_at`）を始めていれば、スレッドの総なめを省き、今回の履歴で見つけた新しい投稿のスレッドだけを取ります（前回までのスレッドは、次の全部取り直しのために `known_threads` に残します）。全部取り直す同期は、定期の実行か、5 分以上たったあとの合図の同期で、少なくとも 5 分に 1 回は起きます。最初の同期（`!synced`・API 取り込みの最初）は、いつも全部取ります。これで、活発なチャンネルでも `conversations.replies` の呼び出しは、これまでの定期の同期と同じ程度です。軽い同期は、前回までの同期で返信を取ったスレッド（`known_threads`）の親が、カーソルを進めないせいで履歴に何度も出てきても、取り直しません（新しい返信は、次の全部取り直しか、返信のイベントで取ります。返信のイベントは、そのメッセージ 1 件を直接取り込みます（後述の「編集・削除・リアクション・範囲外のスレッドの返信」）。ほかのスレッドの返信は、次の全部取り直しまで反映されません）。軽い同期は、監視中のスレッドの返信を取っていないので、**終わっても同期カーソル（`slack_channels.last_ts`）を進めません**（`slack_channel_syncs.run_light`）。進めると、次の全部取り直しが返信を新しいカーソルから取り、その前に付いた返信が範囲から外れるためです。履歴の取り直しは、決定的 ID で重複しません。
- **取りこぼし**: 停止中や、再送の上限を超えて届かなかったイベントの投稿は、5 分ごとのポーリングが拾います。1 日以上たった合図の行は捨てます。


### 編集・削除・リアクション・範囲外のスレッドの返信

差分同期の履歴は新しい投稿しか返さず、取り込み済みの投稿を取り直さないので、編集・削除・リアクションの削除は、イベントで知るしかありません。ただし、**イベントの内容は信用しません。** 受信口は、確かめ直すメッセージ 1 件の指定（`slack_message_hints`。`message_ts`・種類・リアクションの名前と人・スレッドの親の `ts`）だけを残します。差分同期は、新しい同期の始まりに、そのメッセージを Slack API で取り直し、Zoo を API の今の状態に合わせます。順序の入れ替わり・重複・再送があっても、結果は同じです。1 回の同期で取り直すのは最大 10 件で、90 秒を超えたら次の同期に回します（残りがあれば、次の同期をすぐに起こします）。

- **すでに Zoo にあるメッセージだけを変えます。** 例外は、スレッドの返信（`reply`。差分同期の監視範囲の 3 日・20 件の外のスレッドも取り込みます）です。Zoo にないメッセージへの編集・削除・リアクションは何もしません（日付を区切った ZIP の取り込みより前の投稿を、文脈なしに入れないためです）。
- **編集**（`message_changed`）: 本文とカードを、取り込みと同じ変換で作り直し、違うときだけ更新します（`revision` を 1 上げ、`updated_at` に編集の日時を入れます）。人の投稿は、Slack の `edited` があり、その日時が Zoo の `updated_at` より新しいときだけです（リンクの展開などの変更や、Zoo で編集された本文を古い状態で戻すことを避けます）。bot の投稿は `edited` がなくても、表示内容が違えば更新します。
- **削除**（`message_deleted`・tombstone）: API が成功して「ない」と答えたとき、または tombstone のときに、`deleted_at` を入れます（Zoo のユーザーの削除と同じです。返信は、親が消えてもスレッドに残ります）。API がまだメッセージを返すときは、ヒントを残して試行回数を増やし、あとの同期で取り直します（上限 5 回・24 時間）。
- **リアクション**: 追加は、API の状態にあるものを入れます（すでにあるものは変えません）。削除は、**正規化した絵文字**（肌色の違いは 1 つにまとまります）で比べ、API の状態にその人がいないと確かめてから、`(message_id, user_id, emoji)` の 1 行だけを消します。`users` が一部しか返らない（`count` のほうが多い）ときは `reactions.get`（`full=true`）で確かめ、確かめられなければ消さずに、ヒントを残します。Slack に無いリアクションをすべて消すことはしません（Zoo で付けたものが、Slack に届く前に消えないためです）。
- **スレッドの返信へのリアクション**: イベントに親の `ts` がないので、まず履歴で探し、見つからなければ `conversations.replies` に、そのメッセージの `ts` を渡して探します（Slack の API は、スレッドの親でも返信でも `ts` に受け付けます）。この経路は、実機で確かめます。
- **暗号化チャンネル**は、差分同期の対象にしません（平文の書き込みを DB が拒否するためです）。
- ヒントは、24 時間たつか、試行が 5 回に達すると捨てます（約 30 秒ごとの掃除）。取りこぼした編集・削除は、次の「直近 24 時間の再確認」で拾います。

マイグレーション `20261125001000_slack_message_hints.sql`（`slack_message_hints`）を適用してください。

### 直近 24 時間の再確認（取りこぼしの保険）

イベントを取りこぼす（再送の上限を超えた、受信口の停止中など）と、編集や削除は、5 分のポーリングだけでは反映されません。そこで、同期の始まりに、**30 分に 1 回**（`slack_channel_syncs.rechecked_at`）、直近 24 時間の履歴を取り直して、Zoo と突き合わせます（`recheck.rs`）。履歴のページだけを呼ぶので、1 チャンネルあたり最大 5 回です（スレッドの返信は見ません）。

- **編集・リアクションの追加**: すでに Zoo にある投稿に、ヒントと同じ規則で反映します。リアクションの削除は、反映しません（Zoo で付けたリアクションを、Slack に届く前に消さないためです）。
- **削除**: `tombstone` は削除します。さらに、差分同期・イベントで取り込んだ投稿（`slack_message_map` の `origin='slack'`。取り込みのときに残し、3 日で掃除します）のうち、Slack でスレッドの返信でない投稿が履歴から消えていれば、削除します（対応表には、返信を残しません。履歴は返信を返さないので、返信を「消えた」と誤って判定しないためです。親を Zoo で結び付けられなかった返信も、同じです）。Zoo で作った投稿や、ZIP で取り込んだ投稿は、対応表にないので、消えたと見なしません。
- **安全のための条件**: 履歴を最後まで（5 ページ・1000 件まで）取れたときだけ、「消えた」を判定します。履歴が空や一部しか返らないときの大量の削除を防ぐため、候補の半数を超え、かつ 3 件以上が消えたように見えるときは、削除せずにログ（`Slack recheck found too many missing posts`）に残します。
- イベントを使わない構成（`SLACK_SIGNING_SECRET` なし）でも、再確認は動きます。

マイグレーション `20261125003000_slack_recheck.sql`（`slack_channel_syncs.rechecked_at`）を適用してください。

### 取り込んだ投稿の対応表（`slack_message_map`）

差分同期・イベントで取り込んだ Slack の投稿を、`slack_message_map`（`team_id`・`slack_channel_id`・`ts`・`message_id`・`origin`）に残します。上の「直近 24 時間の再確認」が、Slack の履歴から消えた投稿を見つけるのに使います（Slack でスレッドの返信でない投稿だけを残し、3 日で掃除します。ZIP の取り込みは残しません）。`message_id` は一意で、投稿が消えると行も消えます。

マイグレーション `20261125002000_slack_message_map.sql`（`slack_message_map`）を適用してください。

### Slack アプリの設定

`SLACK_SIGNING_SECRET` を設定すると、`GET /api/admin/slack/manifest` の manifest に `settings.event_subscriptions`（`request_url` は `SLACK_OAUTH_REDIRECT_URL` と同じ公開 URL の `/api/slack/events`、`user_events` は `message.channels`・`message.groups`・`reaction_added`・`reaction_removed`）が入ります。ユーザーのイベント（`user_events`）は、連携したユーザーが参加しているチャンネルの投稿が届く想定です（公開チャンネルでどこまで届くかは、実機で確かめます。届かないチャンネルも、ポーリングが拾います）。差分同期と同じ履歴スコープ（`channels:history`・`groups:history`）を使うので、**スコープは増えず、連携済みのユーザーが連携し直す必要はありません。** DM・グループ DM は、取り込み自体が未対応なので購読しません。

1. バックエンドを配備し、`SLACK_SIGNING_SECRET` を設定します（先に設定すると、Slack の request URL の検証（`url_verification`）が通ります）。
2. 管理者の手順（上の「Slack アプリを作る」）と同じ方法で manifest を取り直し、Slack の「App Manifest」に貼って保存します。保存したら、「Event Subscriptions」で request URL が「Verified」になっていることを確認します（`manifest` の `request_url` は、Slack の画面で検証が要ります）。
3. 試験用のチャンネルに投稿して、数秒〜数十秒で Zoo に出ることを確認します。

イベントを使わなくても、同期は 5 分ごとに動きます。イベントが届かない間も、ポーリングで新しい投稿は反映されます。

配備の途中（旧バージョンのワーカーと新しいワーカーが同時に動く間）は、旧ワーカーが 429 のあとに書く待ちは `available_at` だけで、`not_before` を持ちません。そのため、新しいワーカーが合図で、その待ちより早く 1 回だけ取り直すことがあります（Slack が再び 429 を返せば、新しいワーカーが `not_before` を書きます）。入れ替えが終われば起きません。

マイグレーション `20261124000000_slack_event_wakes.sql`（`slack_channel_wakes` と `slack_channel_syncs.not_before`・`swept_at`・`run_light`）を適用してください。適用の時点で次の実行が先になっている項目は、その日時を `not_before` に引き継ぎます（429 などの待ちの途中で適用しても、合図で前倒ししません）。
