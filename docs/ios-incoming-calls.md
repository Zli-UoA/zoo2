# iOSの着信

iOSはPushKitで受信した通話招待をCallKitへ即時報告する。標準の着信画面で応答・拒否でき、アプリの前面表示中にも同じ着信音を使う。WebRTCの音声はCallKitの音声セッション有効化後に開始する。

iOS 26.4以降はPushKitのmetadata.mustReportに従い、旧delegateでは毎回CallKitへ報告する。報告必須の重複は同じUUIDで報告し、重複エラーで元の通話を終了しない。[Appleの報告義務と重複通知の説明](https://developer.apple.com/forums/thread/734922)に基づく。

## 登録と送信

既存の `/api/push/apns/subscriptions` に `kind: "voip"` を追加する。省略は従来の `alert`。クライアントは `/api/push/apns/config` の `voip: true` を確認してから登録し、旧サーバーへの誤登録を防ぐ。VoIPトークンは通常のAPNsトークンとは別物で、IDは `SHA256("voip:" + environment + ":" + token)` とする。通常通知のIDは変えない。DBスキーマと解除APIは共通で、登録上限20件には両方を数える（通常通知と通話通知の両方を使う場合は10台）。同一の生トークンを両用途に登録しない。

VoIP登録へ通常のメッセージやテスト通知は送らない。着信だけ `apns-topic: works.zli.zoo.voip`、`apns-push-type: voip`、優先度10、expiration 0で送る。既存のAPNs署名鍵はこのtopicを送信できる権限が必要。追加のSecretやDBマイグレーションは不要。配備は既存のGitOps手順に従う。

招待ID、宛先ID、チャンネルID、招待者ID、発信者名、元の有効期限を送る。端末ごとに送信直前の招待状態・所有者・解除情報・閲覧権限・DNDを照合し、期限切れ・取消済み・退会後の着信は送らない。取消・他端末での応答は既存のcall_invites Shapeで同期し、端末でも元の有効期限で着信を終了する。取消だけのVoIP pushは送らない。

VoIP通知が先に届き、初回Shapeにその招待がない場合だけ、宛先本人が `GET /api/call-invites/{id}` で `pending` を確認する。レプリカ遅延で通常の着信を消したり、初回同期より前の取消を鳴らし続けたりしないための照合であり、定期ポーリングは追加しない。同じ着信の進行中の照合を共有し、応答・終了・ログアウトで中断する。このAPIは宛先と閲覧権限を確認し、別人・期限切れ・取消・閲覧不可の場合は `pending: false` だけを返す。

## SQLの設計と探索上限

総登録数をS、全招待数をI、全利用者数をU、全チャンネル数をC、会員行数をM、宛先の登録数をD（D≤20）とする。招待ごとに宛先の登録を既存user_id索引で1回取得し、各VoIP端末について `CALL_PAYLOAD_SQL` を1回発行する。登録取得はO(log S + D)、本文の認可はO(log I + log S + log U + log C + log M)、返却最大1行。各主キー・会員複合主キー・DNDのuser_id主キーから最大1行ずつ参照し、ソート・全履歴展開・追加の更新はない。状態確認の `PENDING_INVITATION_SQL` も招待・利用者・チャンネル・会員の各キー最大1行だけを参照し、APIごと1 SQL、返却最大1行。端末登録・解除のSQLと排他制御は既存のまま。

Webは既存のWeb Pushと通話画面を継続する。Android・TUI・デスクトップにはiOS固有のPushKit登録やCallKit表示は追加しない。共有の通話・認証・Shapeの既存API契約は変えず、iOSの到着順序の照合用GETだけを追加する。

## 検証結果（2026-11-19）

PostgreSQL 16.15の専用ローカルDBで、関連テーブル各30万件・100万件の探索上限を検証した。宛先には上限の20登録、他ユーザーには1登録ずつを置き、無関係の招待履歴は別ユーザーに集中させた。検索列の型・一意性・索引を再現した検証用schemaを使い、本番データには接続していない。今回追加するSQLは読み取りだけで、トリガーや書き込みは変更していない。

着信・解除情報不一致・招待なし・登録20件・登録なし・招待状態・別人の招待の7条件について、custom/generic plan、単独30回・8接続各30回を実行し、合計7,560回すべてで走査上限を満たした。APIのページングはなく、深いページは該当しない。初回も除外せず、実行計画・行数×loops・除外行・論理ブロックを保存した。端末認可のdeviceはMATERIALIZED CTEで先に主キー1行へ限定し、プランナーがuser_id側の20行を読まないようにした。
