# マルチテナント対応

ワークスペースをテナントとして扱います。ユーザーと OIDC Identity は全体で共通で、ユーザーは複数のワークスペースに所属できます。チャンネル、メッセージ、リアクション、チャンネル所属、管理者ロールはワークスペース単位です。プロフィールとユーザー名はアカウント全体で共通です。

## 利用方法

ログイン後、画面上部からワークスペースを作成・切替できます。作成者はそのワークスペースの管理者になります。管理者は「メンバーを追加」から、Zoo にログイン済みのアカウントを正確なユーザー名で追加できます。追加されたユーザーは再読込するとワークスペースを選べます。

新規 OIDC ユーザーは、ログインだけでは既存ワークスペースに参加しません。ワークスペースを作成するか、管理者によるメンバー追加が必要です。開発専用の `POST /api/users` は、従来のローカル開発・テスト用に既定ワークスペースへの所属も作成します。本番ではこのエンドポイントは無効です。

切替先はタブごとの `sessionStorage` に保存します。切替時はトップページへ再読み込みし、前のワークスペースのチャンネルURL、Electric購読、楽観更新、メモリ上のコレクションを破棄します。OIDC のアクセストークンもメモリ保持のため、再読込後は既存の IdP セッションで再認証します。

## API と認可

既存 REST / Shape API に `X-Tenant-ID: <workspace UUID>` を付けます。このヘッダーは選択先の指定に使い、毎回、認証ユーザーの `tenant_users` 所属をDBで確認します。所属のないワークスペースや別ワークスペースのリソースは `404`、不正なUUIDは `400` です。チャンネルの公開範囲と管理権限の既存ルールは、選択したワークスペース内で適用します。

ヘッダーを省略すると既定の `00000000-0000-0000-0000-000000000001` を選択します。この場合も所属確認が必須です。別ワークスペースへの自動フォールバックはありません。

| API | 動作 |
| --- | --- |
| `GET /api/tenants` | 認証ユーザーが所属するワークスペースを返す |
| `POST /api/tenants` | `{ "name": "チーム名" }` で作成し、作成者を所属・管理者として登録する |
| `POST /api/tenants/members` | 管理者が選択中のワークスペースに `{ "user_name": "alice" }` のアカウントを追加する |
| `GET /api/users` と `GET /api/users/{id}` | 選択中のワークスペースの所属ユーザーに限定する |
| `GET/PATCH /api/users/me` | ワークスペース未所属でも本人の共通プロフィールを取得・編集する |

書き込みレスポンスは既存の `{ data, txid }` 形式です。所属済みアカウントの再追加は更新なしとして `txid: null` を返します。テナント作成と所属・管理者登録は同じトランザクションで行います。

Electric Shape はサーバー側で全テーブルにテナント条件を付けます。ユーザーは `tenant_users` のサブクエリで絞ります。クライアントからの `table`、`where`、`params` は転送しません。全 Shape に `Cache-Control: private, no-cache` と `Vary: Authorization, X-Dev-User, X-Tenant-ID` を設定します。チャンネル名の一意性はテナント内で保証し、複合外部キーでテナントをまたぐ参照も拒否します。

`VITE_SHAPE_MODE=direct` は従来どおり開発専用の認可なし経路です。マルチテナント運用では `proxy` を使用し、Electric をクライアントから直接到達できる場所に公開しない構成にします。

## 移行・デプロイ

`20261020090000_multi_tenancy.sql` は既存のユーザー・データ・管理者ロールを「Zoo」という既定ワークスペースに移します。既存のIDは保持します。ワークスペースの削除、所属解除、管理者の追加・変更は、この変更のAPIには含みません。

1. DBのバックアップを取得し、旧フロントエンド・バックエンドへのトラフィックを止めます。
2. `make migrate` でマイグレーションを適用します。
3. フロントエンドとバックエンドを両方更新して起動します。

旧バックエンドにはテナント認可がないため、新旧バージョンを混在稼働させないでください。追加した `tenant_id` に書き込み時の既定値はなく、新しい書き込みは必ず明示的にテナントを指定します。

## 検証

`backend/tests/multi_tenant_test.rs` は、本物の PostgreSQL と Electric を使い、複数テナントへの所属、同名チャンネル、API全操作の境界、テナントごとの管理権限、ユーザー一覧、Shapeの実データ、SQLパラメータ上書きの拒否、DB複合外部キーを検証します。`make test-e2e` で既存の統合テストと一緒に実行できます。

フロントエンドの `src/lib/tenant.test.ts` は選択の保存、切替時の画面破棄、RESTとElectricのリクエストが同じテナントに固定されることを検証します。
