# Home・連合通知の取得量とスケール検証

## 取得の設計

Home、Local、Social、投稿者ページは、本文を全件展開してからページを切り出さない。`home_page.sql` が日時・IDの降順インデックスから候補を選び、ページ内のキーだけを `home_timeline.sql` で表示用DTOにする。公開範囲・チャンネル・ゲスト・受信者・フォロー・ブロック・削除の判定と、通常投稿／リポストの条件は共通SQLに置く。クライアントのAPI・DTO・リクエスト数は増やさない。

- 通常は50件、指定上限は500件。`OFFSET` は使わず、日時と完全なentry IDの組で過去方向へ進む。リポストの `repost:` 接頭辞、同時刻の文字列順、マイクロ秒精度を維持する。カーソル自体も閲覧条件を確認する。
- 自分の投稿、自分への返信、公開ローカル投稿、フォロー中の各actorからの受信投稿、自分へのリモート返信、各種リポストを別々の順序付きストリームにする。各ストリームから最大1ページだけ取り、重複を除いて全体の先頭を選ぶ。
- 受信者テーブルにactor・日時・返信先が自分か・削除状態を保持する。フォロー解除済みactorの大量の受信履歴を読み飛ばす必要はない。ゲストは自分・返信・参加チャンネルから取り、参加先がないゲストのために全投稿を走査しない。公開一覧用の部分インデックスには非公開履歴を入れない。
- 本文、親プレビュー、絵文字、引用、画像、リアクションは選択後に構築する。公開プロフィールとOutboxも、絵文字一覧・添付情報をページ単位で取得する。公開プロフィール専用の部分インデックスは、非連合投稿の履歴も除く。
- 単一投稿の本文候補は対象と親。スレッドの祖先は最大100段、会話IDの探索は最大「返却上限+101件」、本文の返却は従来どおり最大500件。会話IDの再帰は重複を除いて循環を止め、消費側のLIMITで探索を止める。非常に大きい会話では祖先を含む幅優先の候補集合の中を既存のツリー順で返す。全返信を一度に表示する仕様ではない。
- 返信数は親インデックスから直接の返信を調べ、従来の閲覧判定を適用して正確に数える。件数のために全返信の本文をmaterializeしない。連合通知は所有者・日時・IDの部分インデックスで最大101件を先に選び、表示情報を後から組み立てる。

総投稿件数に依存する全件materialize・全履歴ソートを除く設計であり、あらゆるデータ分布で一定時間を保証するものではない。フォロー先・参加チャンネルの数、候補に占める閲覧不可の割合、表示対象への実際の返信・リアクション・リポスト数に応じた処理は残る。例えば公開チャンネルが非公開に変わった履歴は、最終の閲覧判定で除外するため候補を余分に調べることがある。

## DB移行と旧アプリとの互換性

`20261128000001_home_timeline_seek.sql` は既存列を削除・変更しない。追加列は定数DEFAULT付きNOT NULLで、旧アプリの列指定INSERTを維持する。トリガーが新規受信・元投稿のactor／日時／親／削除変更・後着したローカル親・親の所有者変更・リポスト更新を追従する。読み取り時は常に正規の閲覧条件も適用する。

受信INSERTは元投稿を `FOR SHARE` で読み、元投稿の変更と順序をそろえる。親の後着と受信INSERTの競合には1,024分割のトランザクションadvisory lockを使う。分割数を固定し、大量INSERTで投稿件数分のadvisory lockを消費しない。通常の書き込みと同様、多行の競合時にはPostgreSQLによるデッドロック検出の対象になる。

既存受信者の補完は1,000行ずつコミットし、元投稿→親のロック→受信者の順で処理する。インデックスは `CONCURRENTLY` で構築し、補完後に統計を更新する。列追加時の短いDDLロックと、補完バッチ中の対象行の更新待ちはあるため、書き込み負荷も監視して適用する。

空DBへの全マイグレーションとschema.sqlの適用結果をpg_dumpで比較し、一致を確認した。Atlasのvalidate、既存スキーマからbaselineを設定した実際のapply、旧形式INSERTの既存行補完、親INSERTと受信INSERTの同時実行も検証している。

## 計測

ローカルPostgreSQL 16、JIT無効。件数の3分の1がローカル投稿、残りが20 actorのリモート投稿で、1利用者が全actorをフォローし全リモート投稿を受信する。本文は各640文字。空の利用者・ゲスト、フォロー解除後、深いページ、ローカル／リモート投稿者も確認する。テストは実行時間を合否の条件にせず、投稿／受信者走査量の上限、ページ件数、ソートのディスク退避がないことを検証する。

修正前の通常Homeは30万投稿でSQL実行 **2,495.8ms**、計画 **7.9ms**。全件を表示用baseへ展開していた。

修正後の観測値（候補ID選択のSQLのみ、単位ms。中央値ではなく各テスト実行の観測値）:

| ケース | 30万件 実行 | 100万件 実行 |
| --- | ---: | ---: |
| Home先頭50件 | 51.9 | 22.5 |
| Homeの深いページ | 22.9 | 23.7 |
| Local | 2.6 | 3.5 |
| Social | 21.7 | 25.6 |
| ローカル投稿者 | 3.5 | 3.9 |
| リモート投稿者 | 3.5 | 5.0 |

30万件の計画時間は約27〜128ms（先頭の初回は127.6ms）、100万件では29〜225ms（別の検証処理との同時実行を含む）。50件のDTO構築は別に約6〜8ms。負荷・キャッシュ状態による変動があり、取得API全体や実機FPSの値ではない。

30万件の全Homeハンドラー（Axum、DBプール待ち、ページ選択、DTO補完、JSON生成を含む、ネットワークを除く）を開発ビルドで8同時・計24回実行した結果は、p50 **187.6ms**、p95 **631.9ms**、最大 **641.6ms**。本番でのレイテンシ保証やAndroidの描画速度の測定には置き換えられない。

30万件の連合通知でも、先頭101件がSQL実行1.16ms、20万件先のカーソルでの101件が1.44ms。notification_eventsの読み取りは101件（カーソル確認を含む場合102件）で、通知履歴全体を先に展開していない。

極端な返信集中も別に検証した。100万投稿中、1投稿に33,333件の直接返信を付けた場合、単一投稿のSQL実行790ms、スレッド1,158ms。対象以外の会話を展開せず、本文候補は601件以内で、返信数も正確なまま返す。ただし正確な返信数の計算時間は実際の返信数に比例して残る。

## 再実行

通常の開発環境で、**使い捨てのマイグレーション済みDB**を `DATABASE_URL` に設定する。`ACTIVITYPUB_BASE_URL=https://zoo.example.com` も設定する。

```sh
cargo test --manifest-path backend/Cargo.toml --test home_query_test --test home_test --test activitypub_test
cargo test --manifest-path backend/Cargo.toml --test home_scale_test -- --ignored --nocapture
SCALE_POSTS=1000000 cargo test --manifest-path backend/Cargo.toml --test home_scale_test -- --ignored --nocapture
SCALE_HTTP=1 cargo test --manifest-path backend/Cargo.toml --test home_scale_test -- --ignored --nocapture
```

通常のスケールテストはトランザクションをrollbackする。`SCALE_HTTP=1` は別接続からハンドラーを試すためfixtureをcommitし、終了時に削除する。異常終了時はfixtureが残るため、必ず使い捨てDBを使う。CPU・メモリ・PostgreSQL設定、フォロー数、本文・返信・リアクションの分布を本番とそろえた負荷試験は別途必要になる。
