# Home・連合通知の取得量とスケール検証

## 実行計画による必須条件と時間の参考値

[SQLの設計と性能基準](query-design.md) に従い、探索量・中間行・ソート・再帰に上限を置き、30万件と100万件で比較する。依頼者の方針変更により、100msは参考値とし、経過時間だけでCIの合否を決めない。初回の準備・計画・実行・ロック待ち、接続待ち、SQL往復、API全体の時間は引き続き測定する。

レビュー対応前の計測では最大74.88msで通過した実行と、100msを超えた実行があった。現在の合否はこれらの時間ではなく、以下の探索上限と異なる規模での比較によって判定する。

| 対象 | 実際に検証する処理量 |
| --- | --- |
| 候補キー選択 | 固定fixture F=20、K=50／500について各関係の合計走査・中間行・ソート入力を4×(2F+7)×K以下にする。フォロー先の投稿／リポストと自分・返信・公開などのストリーム、および閲覧判定の点検索を含む予算。Nを上限に使わない。 |
| DTO生成 | 投稿と親を含むK=2／500／601について、各関係の走査・中間行・ソート入力を32K以下にする。32はfixtureの返信actorグループ20と投稿・親・装飾の点検索を含む予算であり、一般のF・Gを定数扱いする式ではない。複数の閲覧判定で再利用するフォロー集合の合計走査は、別に8K(F+1)以下とする。 |
| 集中リアクション・リポスト | 1投稿に3万／10万件。単一投稿の元テーブル走査は各関係100行以下、ページ全体でも4K+16以下。現在のブロック・選択状態・非公開の閲覧者別件数も確認する。 |
| スレッド | 再帰候補601件、返却500件、同じ親のプレビュー生成1回。受信履歴を直接返信件数分走査しない。 |
| 書き込み | 親の計画は各関係16行以下。トリガーを有効にし、親に含まれる論理バッファアクセスと競合時の整合性も検証する。 |
| 規模間比較 | K・F・グループ数をそろえた16条件すべてで、100万件時の各関係走査量・最大中間行・ソート入力・再帰が30万件時の2倍＋64行以内。総履歴3.3倍への比例増加を検出する。索引高・丸め・計画切替の余地を残す。 |
| I/O・退避 | hit＋readの論理バッファアクセスは2倍＋256ブロック以内。キャッシュ状態の違う物理readだけで判定しない。全条件で一時ファイルへの書き出し0。 |

これらは特定のfixtureに対する回帰検査であり、任意の分布に対するBig-Oの証明ではない。設計の変数・最悪時の条件と実測を併せて確認する。実行計画と処理量のJSONはartifactに保存する。

## 検証結果

[実行計画の比較CI](https://github.com/Zli-UoA/zoo2/actions/runs/43863997974)は16条件・計8,640サンプルの上限検査と、30万→100万件の比較に成功した。各関係の走査行数合計は全16条件で同じだった。主な条件を以下に示す。行数は返却行数ではなく、関係ごとのActual Rowsと除外行にloopsを掛けて合計した値である。

| 条件 | 30万件の走査行数合計 | 100万件の走査行数合計 | 論理ブロック 30万→100万 |
| --- | ---: | ---: | ---: |
| Home先頭50件 | 1,425 | 1,425 | 1,578→1,634 |
| Home上限500件のキー選択 | 12,225 | 12,225 | 14,203→14,709 |
| 500件ページのDTO生成 | 10,716 | 10,716 | 26,695→29,238 |
| 単一投稿のDTO生成 | 131 | 131 | 84→93 |
| 別の閲覧者の単一投稿 | 106 | 106 | 75→84 |
| スレッド500件のDTO生成 | 9,887 | 9,887 | 28,868→33,577 |
| リアクションINSERT（トリガー込み） | 1 | 1 | 11→12 |
| リポスト公開範囲変更（トリガー込み） | 2 | 2 | 17→18 |

3万→10万件の集中データでも、単一投稿が元のリアクションを読む行数は4→4、元のリポストは1→1だった。再帰候補は601件以内、一時ファイル書き出しは全条件で0。生の計画と処理量はartifactの各規模の `*-plans/` と `plan-comparison.txt` に保存している。

時間の参考値は全SQLサンプルの最大130.13ms。初回準備・計画・実行・ロック待ちを含み、100ms超過も記録する。経過時間だけで合否を決めない現在の方針に従い、探索量と規模間比較で判定した。

## データと計測条件

PostgreSQL 16、JIT無効。GitHub Actionsのubuntu-24.04の独立したジョブ内で、ビルド完了後に他の負荷試験を並行させず測定する。CPU・メモリ・PostgreSQL設定とログは `home-query-budget` artifactに保存する。環境共有によるCPU停止の影響が大きい開発用コンテナーでの時間計測を、専用ジョブの結果と混ぜない。

件数の3分の1を1利用者のローカル投稿、残りを20 actorのリモート投稿とし、その1利用者が全actorをフォロー・受信する偏った分布を使う。本文は各640文字。1投稿への直接返信は30万件で10,000件、100万件で33,333件。空の利用者・ゲスト、フォロー解除後、閲覧不可・不正なカーソル、深いページ、ローカル／リモート投稿者も構造検証する。無関係なリポスト3万件と対象へのリアクション5千件は別の回帰テストで検証する。

初回は各接続でprepared statementを準備し、サーバー内で測った準備時間と `EXPLAIN (ANALYZE,TIMING OFF,FORMAT JSON)` のPlanning Time＋Execution Timeを合算する。`TIMING OFF` はノードごとの計時負荷だけを除き、SQL全体の実行とロック待ちは測る。初回の遅い値を捨てない。候補選択は実際のアプリと同じcustom plan、範囲を限定したDTO生成はgeneric planを使う。

Homeは実装と同じ2接続の同時実行枠に対して8クライアントで試す。接続・実行枠待ちはSQL時間へ混ぜず別に報告する。更新トリガーはHomeの制限を使わず8接続で競合させる。受信INSERTとリモート投稿のsoft deleteをトリガー込みで実行し、毎回rollbackして同じ実際の変更を繰り返す。SQLの往復時間（診断用EXPLAIN JSONの転送を含む）とAPI全体の応答時間も別に記録する。

## 取得の設計とオーダー

総投稿数N、受信履歴R、フォロー先F、参加先H、ページ件数K、閲覧判定を通過するまでの候補数C、直接返信数D、親に属する集計キー数G、対象へのリアクション数A・リポスト数Pを区別する。LIMIT Kだけを探索上限としない。

- Home・Local・Social・投稿者ページは `home_page.sql` が日時・IDの降順インデックスから候補キーを先に選び、`home_timeline.sql` が選択済みの最大K件と親だけをDTOにする。通常50件、上限500件。API当たり候補選択1回＋DTO生成1回、単一投稿・スレッドではDTO生成1回。ページ単位の装飾を含め、行ごとの追加API・SQLは発行しない。
- 自分・自分への返信・公開ローカル・各フォロー先・リポストを順序付きストリームに分け、各ストリーム最大K件から選ぶ。keysetは日時と完全なentry IDを使い、同時刻・マイクロ秒・`repost:`の順序も維持する。フォロー先ごとの探索はO(F×(log R+C))、参加先もHに依存し、F・Hを定数扱いしない。候補の結合・ソートは各ストリームから得た件数に限定する。
- 受信者にactor・日時・親・自分への返信・削除状態を保持する。フォロー解除済みactorの受信履歴や、公開一覧のための非公開履歴を読み飛ばさない。閲覧条件・ゲスト・受信者・フォロー・ブロック・削除は共通SQLで維持し、DTO生成時も正規の条件を適用する。
- 単一投稿の本文候補は対象と親。スレッドの祖先は100段、会話IDの探索は返却上限＋101件、DTO返却は500件まで。循環・重複を排除し、再帰の全展開前に消費側LIMITで止める。巨大会話では祖先を含む幅優先の候補集合を既存のツリー順で返す。
- リモート返信数はO(log R+G)の差分カウンター検索とactor単位の権限確認へ変更し、D件の本文・受信行を再集計しない。ローカル返信は親インデックスで対象D件だけを共通権限条件から数える。リアクション・リポストは差分集計を使い、対象へのA・P件を表示時に列挙しない。自分の選択状態と現在のブロック・宛先も索引で確認する。
- 親プレビューは同じ親につき一度だけ生成。画像・添付・絵文字はページ単位で取得し、NSFWチャンネルも表示する投稿・親のIDだけを主キー検索する。全NSFWチャンネルの読み取りを行わない。
- 連合通知は所有者・日時・IDの部分インデックスで最大101件を先に選んで装飾する。30万通知で先頭1.16ms、20万件先のカーソル1.44ms、読み取り101行（カーソル確認込み102行）だった。通知の表示範囲更新も同じ所有者・閲覧条件を使う。

フォロー数・参加先数・本文量・対象へのリアクション数・閲覧不可候補の割合は別の負荷要因であり、総投稿件数Nだけから一定時間を保証しない。公開チャンネルが非公開に変わった場合などは正規の閲覧判定までに候補を余分に調べることがある。分布・上限の変更時は本基準で再検証する。

## 返信数・計画・JSONの軽量化

33,333件の返信を表示するたびに数える方式を廃止し、`apub_reply_counts` に受信者・親・actorごとの件数を差分で維持する。受信INSERT、削除、親・actor・受信者の変更、soft delete／復元は同じトランザクションのトリガーで更新する。閲覧時は現在のフォロー・ブロック・親の所有者を確認して合算するため、権限変更時に古い表示件数を流用しない。処理量は直接返信数Dではなく、その親のactor別集計グループ数Gに依存する。ローカル返信の閲覧判定は従来どおり維持する。

既存行の補完では先に差分トリガーを有効化する。既存キーを主キー順で登録し、100キーずつカウンターをロックしてから受信者の確定済み行を数え直す。並行writerはカウンター更新が終わるまでcommitできないので、snapshotに含まれなかった変更は後から差分適用され、二重計上・欠落を防ぐ。0件のキーも同期のため保持する。移行中の暫定値は新アプリへの切替前に補完する。

Homeの候補選択では、フォロー中の配信先・自分への返信フラグ・削除状態を維持した受信者インデックスからキーだけを読む。本文DTOの取得時にも正規の閲覧判定を適用する。timeline・guest・author・cursor・threadの有無はSQLの有限のバリアントとして決め、利用者ID・投稿ID・カーソルは引き続きバインドする。候補選択は利用者・投稿者の件数差が大きいためcustom planを使い、空の利用者やリモート投稿者を全履歴走査へ誤推定するgeneric planを避ける。選択済みキーに限定したDTO生成はgeneric planで計画を再利用する。日時・IDによるkeysetの精度・順序は維持する。

入力されたID配列は一度だけJSONから展開して共有する。行ごとにtext→jsonb変換と配列長確認を繰り返すO(K²)の処理を除き、上限500件のページDTOも時間基準と展開回数で検証する。500行の表示用JSONはDB内のjsonb再変換・連結を減らし、内部の行データと表示用の集計をRust側で合成する。HTTPのDTO形式は変えない。親プレビュー・返信数との突合も相関した繰り返し走査からJOINへ変更する。ワークスペース絵文字の一覧と別名はページ内で一度だけ展開して共有し、各ローカル投稿から同じSQL関数で一覧を読み直さない。コロンが2つない本文は絵文字照合自体を省く。候補がある本文の照合は一覧サイズE・本文長Lにも依存するため、O(E+K×E×L)を評価する。

Homeの同時DB読み取りはプロセス当たり2件に制限し、待機中は接続・トランザクションを取得しない。通常のDBプール上限10は維持する。これにより、S3送信中の画像アップロードなど別の経路が必要とする接続を減らさずにHomeのCPU競合を抑える。総接続数は既存の `DB_MAX_POOL_SIZE` とレプリカ数でも見積もる。

| 対象 | 問題と修正 |
| --- | --- |
| リポスト解決 | `repost:` をDB列へ結合して検索していた全件走査と、全リポストに対する本文候補の照合を廃止。入力IDを分解し、activity_idの主キーから最大K件だけ取得する。本文構築時のO(R × K)の照合をO(K log R)の検索へ置き換える。 |
| 件数・選択状態 | リアクションは入力元・値・絵文字の差分集計から現在のブロック分を減算。リポストは公開分・自分の非公開分・受信した非公開分を重複なく合算し、A・P件を列挙しない。対象外の自分の全リポストをhashed SubPlanで展開しない。 |
| 返信数 | リモート返信は受信者・親・actor別の差分カウンターを合算する。対象への直接返信件数Dを毎回走査する処理を、親に属する集計キー数Gに応じた処理へ変更。現在のフォロー・ブロック・親の所有者は表示時に確認する。ローカル返信は親インデックスと共通の閲覧条件で集計する。 |
| スレッド | 内側のUNIONの重複除去がLIMIT前に全返信を読み切る処理を、UNION ALLと外側の循環・重複排除へ変更。祖先・子孫情報は行ごとの相関サブクエリをJOINへ置き換える。同じ親のプレビューJSONも一度だけ構築する。閲覧不可の候補が多い場合は、許可されたID件数とは別に候補の走査量も増える。 |
| 外部キー | remote_posts.actor_id、remote_recipients.user_id、follows.actor_id、deliveries.actor_idに先頭列が合う全行インデックスを追加。削除済み受信者を除く部分インデックスではカバーできなかった確認・削除も対象にする。各INSERT／DELETEへの維持費用と容量は増える。 |
| 移行バッチ | 初回と以降のSQLを分け、汎用実行計画でもkeysetの範囲探索を維持。advisory lockは元の親IDではなく実際のstripe番号順で取得する。 |

`20261128020002_activitypub_foreign_key_indexes.sql` の追加インデックスはCONCURRENTLYで構築する。`20261128020001` はこのPRで追加した未マージの移行なので、そのバッチ処理を修正した。mainの適用済み移行は変更していない。

追加の回帰検証

- 無関係なリポスト3万件と対象への5千件のリアクションを用意し、通常投稿・リポスト・フォローしていないactorのリポストを確認。リポストの読み取りは最大10行、リアクションも対象の集計キーと点検索に収まり、件数・選択状態・ブロックされたactorの除外も維持する。
- 外部キーの先頭列をカバーする有効な全行インデックスをカタログで確認。
- 強制generic planで受信者20万件の18万件先を取得する診断では、旧条件が181,006行を調べ31.75ms、修正した範囲条件は1,000行・0.30ms。Atlasで旧スキーマから実際に移行し、6,000行・複数バッチの補完も強制generic planで検証した。
- 100万投稿の会話でも、返信集計が無関係な受信履歴を走査しないこと、同じ親のプレビューを一度しか構築しないことを実行計画で検証する。

## DB移行と旧アプリとの互換性

`20261128020001_home_timeline_seek.sql` は既存列を削除・変更しない。追加列は定数DEFAULT付きNOT NULLで、旧アプリの列指定INSERTを維持する。トリガーが新規受信・元投稿のactor／日時／親／削除変更・後着したローカル親・親の所有者変更・リポスト更新を追従する。読み取り時は常に正規の閲覧条件も適用する。

受信INSERTは元投稿を `FOR SHARE` で読み、元投稿の変更と順序をそろえる。親の後着と受信INSERTの競合には1,024分割のトランザクションadvisory lockを使う。分割数を固定し、大量INSERTで投稿件数分のadvisory lockを消費しない。通常の書き込みと同様、多行の競合時にはPostgreSQLによるデッドロック検出の対象になる。

既存受信者の補完は1,000行ずつコミットし、元投稿→親のロック→受信者の順で処理する。インデックスは `CONCURRENTLY` で構築し、補完後に統計を更新する。列追加時の短いDDLロックと、補完バッチ中の対象行の更新待ちはあるため、書き込み負荷も監視して適用する。

空DBへの全マイグレーションとschema.sqlの適用結果をpg_dumpで比較し、一致を確認した。Atlasのvalidate、既存スキーマからbaselineを設定した実際のapply、旧形式INSERTの既存行補完、親INSERTと受信INSERTの同時実行も検証している。

## CIの強制と再実行

`.github/workflows/ci-home-query-budget.yaml` は30万件・100万件を別DBに作成し、読み取り12条件（別の閲覧者、先頭50件・上限500件のキー選択、500件のページDTO、深いページ、Local、Social、ローカル／リモート投稿者、空のguest、単一投稿、スレッド）とトリガー付き書き込み4条件（受信INSERT、soft delete、リアクションINSERT、リポストの公開範囲変更）を測る。各条件は単独30回、8クライアントで240回。2規模で合計8,640回。すべてのサンプルで探索上限を検証し、2規模の実測走査量・論理バッファアクセスも比較する。上限超過・履歴への比例増加・退避はCIを失敗させ、100ms超過だけでは失敗させない。マージキューの `all-passed` にも依存させ、失敗時は必須ステータスも失敗にする。実行計画の走査量・再帰候補数・ディスク退避も時間とは別に検証する。API全体の8同時・24回の計測も同じfixtureで実行する。

通常の開発環境で、使い捨てのマイグレーション済みDBを `DATABASE_URL` に設定する。`ACTIVITYPUB_BASE_URL=https://zoo.example.com` も設定する。

```sh
cargo test --manifest-path backend/Cargo.toml --test home_query_test --test home_test --test activitypub_test
SCALE_POSTS=300000 SCALE_BUDGET=1 cargo test --manifest-path backend/Cargo.toml --test home_scale_test timeline_work_is_bounded -- --ignored --nocapture
# 別の使い捨てDBを使う
SCALE_POSTS=1000000 SCALE_BUDGET=1 cargo test --manifest-path backend/Cargo.toml --test home_scale_test timeline_work_is_bounded -- --ignored --nocapture
cargo test --manifest-path backend/Cargo.toml --test home_scale_test persisted_home_handler_budget -- --ignored --nocapture
```

`SCALE_BUDGET=1` は独立接続でfixtureを読むためcommitする。通常の構造テストはrollbackする。異常終了時にもfixtureが残るため、必ず使い捨てDBを使う。残したfixtureの再検証は `persisted_query_budget -- --ignored --nocapture` を指定する。

DB内の100msとAPI全体の100msは別の指標である。APIはDB待ち・複数のSQL・DTO補完・JSON生成を含む。専用ジョブのdebugビルド・8同時24回（ネットワークを除く）では、30万件がp50 212.2ms／p95 394.2ms／最大400.7ms、100万件が225.3ms／421.8ms／428.4msだった。artifactの `300000-http.log` と `1000000-http.log` に保存する。Android実機FPSの計測には置き換えない。

本番への反映はPRのマージ・通常のDB移行とデプロイで行う。追加インデックスの容量・書き込み費用、カウンターへの集中更新、補完時のロックも監視する。本番のCPU・メモリ・フォロー数・チャンネル数・本文量・権限分布に合わせた負荷試験でも、対象件数に基づく探索量を確認する。

## レビュー対応：リアクション・リポストの集中

総リアクション数A・リポスト数Pを表示時に列挙しない。リアクションは投稿・入力元・リアクション値・絵文字記述のグループGを差分更新し、ブロック済みactor Bだけを現在の索引から減算する。自分の選択状態は投稿・利用者の索引で取得する。最初の可視リアクションの時刻はグループ・日時の索引から1件を取り、ブロックされた候補だけ読み飛ばす。読み取りはO(K×(log A+G+B log A))を目標とし、G・Bを定数扱いしない。通常の追加／削除は最大2個の集計キーを同じ順序で更新し、O(log G)とする。

公開／localリポストは投稿別の全体件数、自分の非公開分は所有者・投稿の索引、その他の非公開受信分は受信者・投稿別の差分件数から合算する。公開範囲・宛先・所有者変更を同一トランザクションで追従し、公開分・自分の分・受信分を重複計上しない。O(log P+log R)で検索し、P件の列挙を行わない。既存件数の補完はキーを先に作り、カウンターをロックしてから数え直し、並行書き込みの差分を失わない。

30万／100万投稿に加え、1投稿へ3万／10万件のリアクションとリポストを集中させ、初回・8並列・選択状態・ブロック・私有の宛先と書き込み側も再検証する。新しい集計を含む完全なSQLで探索上限と規模間比較を検証する。

集中データの大量投入時だけ既存履歴の生成としてトリガーを無効にし、正規の集計値を構築する。計測する書き込みではすべてのトリガーを有効にする。8並列のリアクションは8利用者から同一投稿へ追加し、リポスト公開範囲は同一行を競合更新する。件数・選択状態・ブロック・別の受信者についてDTOと実行計画を確認する。

mainの新しい移行を取り込んだため、このPRの実装は `20261128020001`〜`20261128020004` に振り直した。旧previewで0文適用のまま失敗した `20261128000003` は、移行用entrypointが一時ディレクトリの `SELECT 1` で再開してから新番号へ進む。旧番号のファイルを正規ディレクトリに残すと最新mainからの移行が非線形として拒否されるため、正規の移行には含めない。実装は新番号へ移し、既存列・索引・関数・トリガーを再適用できる形にした。mainの適用済み移行は変更しない。旧previewの失敗状態からの再開と、最新mainの適用済み履歴からの移行をそれぞれAtlasで検証する。

1リポストの受信者数をSとすると、公開範囲・所有者・投稿先の変更では必要なS行のメタデータと私有カウンターを更新する。書き込みはO(S log R)にも依存するため、総投稿Nや対象リポストPへの依存と区別する。CIの公開範囲変更はS=2で競合させ、所有者・投稿先・受信者変更と削除時の正確な件数も回帰テストで確認する。

## Home画像の削除キューの移行

旧ワーカーでは1分に1回、回収候補を最大100件取得する。以下は候補取得SQLを、障害時のS3試行やトランザクションの意図的な待機と分けて計測した結果。

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
SELECT json_build_object('id',id)::text
FROM home_image_deletions ORDER BY created_at LIMIT 100 FOR UPDATE SKIP LOCKED;
```

使い捨ての PostgreSQL 16.16 で、マイグレーション `20261205000000` の直後と `20261205000001` の直後を計測した。CPUは Intel Xeon Platinum 8573C の5論理CPU、メモリは17 GiB。PostgreSQL は `shared_buffers=128MB`、`work_mem=4MB`、`jit=on`、`max_connections=100`。各条件の投入後に `ANALYZE` を実行し、キャッシュ消去は行っていない。保留行はすべて回収可能行より古く、同じ利用者に属する。

```sql
-- 使い捨ての検証DBでのみ実行する。`:pending` は300000または1000000、`:ready` は0または1000。
TRUNCATE home_image_deletion_queue;
INSERT INTO home_image_deletion_queue(id,uploader_id,file_size,created_at)
SELECT 'pending-'||i,'existing',100,timestamptz '2026-11-01 00:00 UTC'+i*interval '1 second'
FROM generate_series(1,:pending) AS i;
INSERT INTO home_image_deletion_queue(id,uploader_id,file_size,legacy_write_pending)
SELECT 'ready-'||i,'existing',100,false FROM generate_series(1,:ready) AS i;
ANALYZE home_image_deletion_queue;
```

単独で30回、同時実行では独立した8接続で各30回を計測した。再実行する際は、同時接続で0.20秒ごとに上記SQLをトランザクション内で実行し、各試行の開始から0.15秒の時点までロックを保持してロールバックする。開始時刻は全接続で統一する。表の初回は各接続の初回のうち最も遅い値。時刻は準備済みの接続におけるDB内の計画時間と実行時間の和で、接続確立・SQL往復・測定用のロック保持時間・S3アクセスは含まない。回収候補の取得はHTTP APIを発行しない。

走査はスキャンノードの `(Actual Rows + Rows Removed by Filter + Rows Removed by Index Recheck) × Actual Loops`。フィルタ・再検査による除外とソート入力は全条件で0行だった。移行途中は `One-Time Filter` が偽になるためスキャンの実行回数も0。移行後は `home_image_deletions_legacy_gc_created` の範囲条件が保留行を除外し、8接続では最大700行のロックをスキップした。同じ条件で保留を30万件から100万件に増やしても、走査行数の最大値は同じで、共有バッファの増加は1ページだった。索引のサイズは30万件で約1.9 MB、100万件で約6.5 MBだった。

移行途中の回収検索の走査は0行。移行後の探索は、全キュー行数をN、取得上限をK=100、先行ロックでスキップした回収可能行をLとして O(log N + K + L)。保留行は範囲外で、先行ロックによる走査だけが増える。式インデックスはキューへの挿入・削除ごとに維持される。旧版の容量集計は移行途中も保留行を含み、実際のDBドライバを使う `home_image_upload_failure_and_interruption_leave_durable_cleanup` で確認できる。
