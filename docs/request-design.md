# リクエストと接続の設計

## 基本方針

画像などのファイル本体は必要に応じて個別取得する。それ以外の表示用データは少数の取得・同期経路へまとめ、画面や部品が増えるたびにAPIリクエストや常設接続を増やさない。

初回取得、過去ページの取得、利用者の操作による書き込み、認証更新は必要な通信として扱う。リクエスト数を減らすために、権限確認や更新の正しさを省略しない。

- 既存のShapeや表示用DTOに含まれるデータを、別のREST APIで取り直さない。チャンネルの投稿者・リアクション（連合を含む）・添付メタデータ・返信数は `messages.display_data` を表示の正本とする。書き込みの楽観更新と同期確認に必要なコレクションは区別する。
- 同じ認証・用途のライブ接続は共有する。部品ごとにWebSocketやSSEを開かない。異なる権限・データ範囲のShapeを無理に混ぜない。
- 同じデータを使う通知バッジと画面などは、取得結果・ページング・既読状態まで共有する。カスタムhookの関数が共通でも、呼び出すたびに副作用を作る構成は共有とみなさない。
- 取得中の更新通知はまとめ、完了後に必要な再取得を1回行う。同じ対象の新しい通知が来ただけで通信を中断・再開しない。対象・アカウントの切替やアンマウントでは中断する。
- ポーリングを新設する前に既存の同期・更新通知を使えないか確認する。必要な場合は理由、対象、頻度、停止条件を説明する。完了前に次の取得を始めず、非表示タブでは停止し、復帰時に更新する。変化や稼働対象がない間は間隔を延ばす。
- キャッシュと進行中の取得は、認証・ワークスペース・対象に応じた範囲で共有する。設定や利用者の違うデータを混ぜない。共有する通信を1つの部品のアンマウントだけで中断しない。
- 一覧の各行から同じ絵文字一覧やURLメタデータを取り直さない。画像本体の取得と、その前段のメタデータAPIは区別する。

## 確認方法

初期表示、同じデータを使う複数部品の同時表示、画面の往復、更新通知の連続、遅い応答、タブの非表示と復帰、対象・アカウント切替を確認する。リクエスト数・接続数をテストで検証し、表示結果だけのテストで済ませない。

## 現在の通信経路と整理内容

| 対象 | 経路・対応 |
| --- | --- |
| チャンネル本文・連合リアクション | `messages` Shapeの `display_data`。Reactからの `federated-reactions` REST取得を廃止。旧APIは他クライアントとの互換用に維持する。 |
| 添付メタデータ | `display_data.attachments`。別Shapeは表示データのない旧キャッシュの補完に限定する。画像・ファイル本体は個別取得する。 |
| ローカルリアクション | 表示は `display_data.reactions`。既存の `message_reactions` Shapeは楽観的な追加・解除とtxid照合のため維持する。 |
| Home・ActivityPubのライブ通知 | シェルごとに1本の `/api/home/live` WebSocketを共有。通知を1秒間隔で集約し、非表示タブのライブ再取得を停止する。 |
| チャンネル・DMのピン留め | シェルごとに `/api/shapes/user_pinned_channels`（Electric、`liveSse`、永続化）を1本購読し、本人の行だけを配る。並びの版は `GET /api/channel-pins` と書き込みの応答で管理し、起動時、Electric が他の端末の変更を知らせたとき、および 409 の競合のときに取り直す。ポーリングは増やさない。 |
| 通知 | アカウントごとに1つのProviderでバッジ・画面の取得と既読状態を共有。ライブ再取得を5秒間隔で集約し、取得・追加ページの処理を直列化する。 |
| 通話の招待 | シェルごとに `/api/shapes/call_invites`（Electric、`liveSse`）を 1 本購読する。自分が呼んだ・呼ばれた呼び出し中の行だけ（通常は 0〜数行）で、永続化しない。ポーリングは増やさない。着信は Shape の行から作り、期限の表示は行ごとのタイマー 1 つで更新する。 |
| Homeの設定・フォロー一覧、プロフィール | 設定・フォロー一覧は60秒、プロフィールは30秒の間隔でライブ再取得を集約し、前の応答を待つ。AndroidのActivityPub有効状態は認証済みセッションの起動時に取得し、取得に失敗した場合はオンラインまたは前面への復帰時に再試行する。フォローなどの操作後は即時反映する。Home本文の更新も取得中は予約する。 |
| アプリのprivate UI | サーバーから利用者向け更新通知がないためポーリングを維持。2〜30秒へ待機時の間隔を延ばし、コマンド・アクション後は即時取得と短期間の監視に戻す。 |
| アプリの公開surface・接続状態 | 表示中だけ2〜30秒のポーリング。取得を重ねず、非表示では停止する。 |
| 入力中表示 | 専用pushがないため取得は1.5〜5秒。入力者がいる間は1.5秒、待機中は間隔を延ばす。入力開始・タブ復帰時は即時取得。送信の2秒間隔はサーバーの短いリースを維持するため残す。本文や下書きは送らない。 |
| 通話一覧 | 表示中の10秒ポーリング。非表示で停止し、取得の重なりを防ぐ。通話中のシグナリング・リース更新は別の必要な通信として維持する。 |
| チャンネル未読 | 非アクティブな全チャンネルの本文購読を開く代わりに、既存の10秒取得と既読操作後の更新を維持する。非表示では取得しない。 |
| 絵文字一覧 | 設定ごとに進行中の取得を共有し、成功した値を60秒再利用する。各行のマウントで再取得しない。管理画面で変更したときは明示的に無効化する。 |
| アカウント絵文字・メンション用プロフィール | `/api/emoji-accounts` は既存の本文DTOにないディレクトリ情報として取得する。Reactは設定ごとに結果・取得・60秒の更新タイマーを共有し、60秒以内の再マウントでは再取得しない。AndroidはSessionのキャッシュと逐次取得を使い、非表示・オフラインで停止する。TUI・GPUIは既存の絵文字取得ゲートへ統合し、フォーカス中だけ60秒ごとに取得する。TauriのLeptos UIもフォーカス中だけ60秒の期限を確認し、進行中の取得を重ねず、セッション切替前の結果を捨てる。 |
| 添付URL | 設定・添付IDごとに期限付き結果と進行中の取得を共有する。同じ画像が一覧とスレッドにあってもURL発行APIは重複させない。 |
| スレッド一覧 | Reactは設定・アカウント・範囲ごとに結果とページングを共有し、変更がなければ60秒以内の再マウントでは再取得しない。購読停止中の書き込みも変更世代として記録し、再展開時に更新する。アクティブ一覧はサーバーの専用pushがないため60秒更新する。アーカイブ履歴の一覧・検索UIは設けず、投稿の返信を開く操作から閲覧する。TUIも60秒更新を維持し、操作後の更新とページ取得を範囲ごとに直列化・集約する。いずれも非表示では開始しない。Reactは最後の購読解除・非表示で中断し、復帰で更新する。閉じたスレッドの本文取得は行わない。 |
| ネイティブの添付メタデータ・URL | GPUIも `messages.display_data.attachments` を使い、添付専用Shapeの常設購読を廃止する。30秒のローカル期限確認はフォーカス中の描画対象だけを確認し、期限が近いURLだけ再発行する。画像本体は個別取得する。 |
| TauriのDND・自動更新 | OS通知の抑制にはウィンドウを閉じた間もDNDの設定が必要なため、プロフィールをセッションにつき起動時と5分ごとに逐次取得する。ログアウト・セッション切替で停止する。自動更新は有効な配布ビルドだけ起動30秒後と6時間ごとに逐次確認し、設定で無効化できる。専用の常設接続は増やさない。 |
| Presence・Bubble Chat | 短いリースと入力共有に必要な既存通信。Presenceは表示中だけ30秒更新。Bubble Chatは表示中の逐次ポーリングと入力送信の間引きを維持する。 |
| Slack取り込み進捗 | 取り込み中に限った既存ポーリングを維持する。 |

アプリUI・入力中表示などのポーリングを完全に除くには、権限を守った利用者／チャンネル単位のpushが必要。Homeの全体更新通知へ入力イベントなどを混ぜると全利用者の再取得を増やすため、その代用にはしない。今後の追加は少数の共有接続へ対象を購読する設計を優先する。

## プラットフォームごとの適用

この方針はReact、Androidの共通Kotlin、TUI、デスクトップに適用する。あるクライアントだけを修正して共通化済みとせず、同じ機能がある各実装を確認する。API・Shape・DBの形式や認可条件は変更しない。

| 実装 | 対応 |
| --- | --- |
| React | 上記の共有Provider、ライブ接続の共有、再取得の集約、ポーリングの停止と間隔調整、メタデータ取得の共有。 |
| Android | Sessionにある共有通知状態とHomeLiveの1接続を維持。連合リアクションのREST別取得を廃止し、`display_data` を使う。通知・Home・プロフィールは取得中の更新を予約し、Homeのフォロー一覧を60秒、プロフィールを30秒、ライブ通知を1秒単位で集約する。Home本文の取得は5秒の同じゲートにまとめる。surface・アプリ接続は2〜30秒、typingは1.5〜5秒へ待機時の間隔を延ばし、非表示・オフラインで停止する。絵文字一覧はSessionの60秒キャッシュを共有する。 |
| TUI・デスクトップ | 共通の `client-types`（`client-core` からも再公開）がメッセージに同梱されたローカル・連合リアクションを読み取り、リアクション用Shapeの追加購読を廃止。読み取りAPIに10秒の上限を設ける。入力中の更新は進行中の更新があれば間引き、停止は前の送信を待って順序を守る。共通の `PollGate` でtyping・未読・絵文字取得を逐次実行し、typingは待機時に最大5秒へ間隔を延ばす。フォーカス喪失中のポーリングと自動既読を停止し、復帰・対象切替・入力開始時に更新を要求する。チャンネル切替では以前の本文購読を解放する。 |

TUI・デスクトップにはHome・ActivityPub通知・アプリsurfaceの画面がないため、それらのために新しいAPI取得や接続は追加しない。Rustのリアクション変更は本文の同期で反映され、React・Androidで残す楽観書き込み用Shapeと用途が異なる。旧クライアント用の互換APIは維持する。

スレッドの個人参加状態は既存のメッセージShapeにないため、閲覧中のスレッドだけ `/api/threads/{id}` で取得する。Reactは設定・利用者・スレッドIDごとに取得とタイマーを共有し、表示中60秒、非表示・未購読時停止、復帰時更新とする。投稿後の通知は取得中に集約し、参加・退出の応答は再取得せず反映する。アカウントをまたぐ操作結果は一覧へ適用しない。Androidも表示中の1ペインだけ60秒で取得し、操作と取得を直列化する。本文・返信数は既存の同期データを使う。

## Home の仮想スクロールと更新範囲

React の Home は可変高さの行を TanStack Virtual で実測し、表示範囲の前後6行を描画する。読み込み済みの末尾10件に近づいた時点で、既存の `before` カーソルを使って次の50件を先読みする。取得は直列にし、最終ページ・エラー・非表示では自動取得を止める。先読みの失敗状態は先頭・表示範囲の更新とは分けて保持し、先読みの明示的な再試行成功またはTLの再読込まで自動取得を再開しない。エラー時は既存の「過去の投稿を読む」から再試行できる。

ライブ通知と表示範囲の移動による再確認は5秒間隔の同じゲートへ集約する。ライブ通知では先頭50件を取得し、それに含まれない表示範囲の entry ID を `POST /api/home/entries` で一括確認する。表示範囲の移動だけなら先頭を取り直さず、表示範囲だけを一括確認する。直近の先頭取得で確認済みの範囲へ移動しただけなら追加取得しない。最大100件で、本文や画像URLを行ごとに取得しない。長いリモートIDを含むため、ID一覧はURLではなくJSON本文で送る。サーバーは通常の一覧と同じタイムライン・投稿者・公開範囲の条件を適用し、削除済み・閲覧不可の項目を返さない。通常投稿とリポストは `entry_id` で区別する。

過去に読み込んだ全件は再取得せず、表示範囲に入ったときに編集・削除・公開範囲の変更を再確認する。新着と既存の先頭に重なりがない場合、途中の閲覧位置では現在の履歴を保持し、先頭へ戻ったときに最新の一覧へ切り替える。手動更新とタイムライン切替は先頭から読み直す。本文の仮想化・先読みはReactの変更であり、共有APIの既存の応答形式は変更しない。Androidも `LazyColumn` の末尾10項目に近づくと50件ずつ先読みし、ライブ更新は先頭50件と表示中の最大100件だけを確認する。過去ページの取得と更新を直列化し、先読み失敗後は明示的な再試行まで自動取得を止める。TUI・GPUIにはHome画面がないため、今回のために取得処理を追加しない。
## Home の引用投稿

引用先URIと表示用の引用元はHomeのDTOに含める。サーバーはページ内の投稿・返信親の引用を1つのDBクエリでまとめ、公開範囲・削除・ブロック・取得元検証を確認する。ローカル引用元はURIからIDを取り出し、home_posts.idの主キーへ直接結合する。画像のメタデータ補完もページ全体で行う。クライアントは引用カードごとのAPIや常設接続を作らず、既存のHomeライブ再取得で更新する。引用元の署名付きHTTPS取得は、コミット後にDBで配信先権限・引用先・未取得かを確認してからバックグラウンド処理へ渡し、同時4件・1段・最大20秒に限定する。Inboxの同時実行枠とは分け、処理枠が埋まっているときは待機タスクを増やさない。失敗や処理枠上限による未取得分は、後続のCreate・Update・Announceで再度試みる。通常URLには既存のSummaly取得共有・キャッシュを利用し、引用先は除外する。

Reactでは、投稿を開く前のTLをワークスペース・アカウント・履歴エントリ・タイムラインごとにタブのメモリへ最大8件保存する。各履歴は最大1,000投稿かつJSONのUTF-16換算で4MiB以下に制限する。超過した履歴は途中を切り取らず保存自体を省き、戻った際は先頭から再取得する。投稿一覧、ページ末尾、実測した行の高さ、閲覧中の行とその表示位置を復元するため、詳細から戻っても読み込み済み履歴を先頭から取り直さない。端末ストレージへ本文は保存しない。削除成功時は関連するキャッシュから通常投稿とリポストを取り除き、古い進行中の取得を中断して投稿の復活を防ぐ。TL上の削除ではページを遷移せず、閲覧位置を維持する。個別ページの対象投稿を削除した場合はアプリ内の直前の画面へ戻り、戻り先がない直リンクでは `/home` へ置き換える。

投稿メニューは本文の長さに左右されない右上へ置き、メニュー操作が投稿カードのクリックへ伝わらないようにする。途中を閲覧中の新着は位置を変えず、先頭へ戻るボタンから開ける。コピーと削除の成功は既存の通知UIで知らせ、削除失敗時は確認画面にエラーと再試行操作を残す。

表示範囲の一括確認だけに失敗した場合は、取得できた先頭の更新を反映し、確認できなかった既存行は削除しない。失敗は表示するが、先読み専用の失敗状態にはしないため、次のページは取得できる。

`/api/home/entries` は通常投稿・リポストから対象の投稿IDを引き、表示判定の前に対象とその親・返信へ絞る。投稿者ページも、その投稿者のIDを先に集めて同じ範囲へ絞る。範囲を引いた後の主キー参照はLATERALとOFFSET 0で保ち、推定件数により全投稿へ公開範囲の判定が走る計画を避ける。公開範囲・ブロック・引用の条件は通常一覧と共通のまま維持する。件数制限は表示件数に対するもので、非常に大きい会話・投稿者履歴の探索量自体には上限を設けていない。

## Home の単一投稿・スレッド取得

`/api/home/{id}` と `/api/home/{id}/thread` は、まず主キーと既存の返信親インデックスで会話に関係する投稿IDを集め、その範囲に既存の公開範囲・チャンネル・受信者・ブロック・削除の条件を適用する。ID探索自体は閲覧許可を与えない。循環はIDの重複排除で停止する。親のプレビューと返信数に必要な投稿も範囲に含め、描画の深さと件数の上限は既存のまま保つ。

スレッド取得は同じSQLの結果に要求された投稿が含まれることを確認し、見つからない場合は404を返す。存在確認のために本文・リアクション・引用などを二度取得しない。通常のタイムラインには会話の絞り込みを加えない。ReactとAndroidは既存の同じAPIから改善を受け、追加の通信や接続は不要。Home画面のないTUI・GPUIの取得経路は変えない。

## 通知とAndroidの表示キャッシュ

Web・Androidの連合通知は、ライブ更新ごとに読み込み済みの全ページを再取得しない。先頭100件と、そこに含まれない表示中の通知を `POST /api/activitypub/notifications/entries` で最大100件確認する。後者は一覧と同じ所有者・投稿の閲覧条件を使い、返されなかった表示中の通知を取り除く。既存の末尾カーソルを維持し、過去ページの取得と再確認を直列化する。非表示では新しい取得を始めず、アカウント切替で進行中の処理と表示範囲を分離する。

通知のSQLは `notification_events` の所有者・作成日時・IDのインデックスで最大101件を選んでから、本文・アバター・絵文字を組み立てる。ページを確定する前に全通知をJSON化しない。Androidの自動既読は100msの間に見えたIDをまとめ、既存の `/api/notifications/read` へ最大500件ずつ送る。通知一覧のグループ化と並べ替えは入力が変わったときだけ行い、スクロール位置の変化では繰り返さない。

AndroidはHomeの投稿・末尾・閲覧位置をSession内で最大8画面、1画面1,000件・4MiBまで保持する。直近の先頭確認から30秒以内の画面往復では、新しい先頭取得を省き、ライブ通知と表示中の範囲の再確認で更新する。ログアウト・別アカウントには引き継がず、削除した投稿を含むキャッシュは破棄する。ディスクの画像キャッシュに加え、Session内のデコード済み画像も最大64MiB・256件のLRUに保持し、同じURLの取得とデコードを共有する。失敗は次回に再試行でき、Session終了で破棄する。

ユーザーページで既知のリモートアカウントを開くときは、保存済みプロフィールを表示し、署名鍵キャッシュの期限切れを理由に相手サーバーの応答を待たない。未取得アカウントの解決と、Inbox・署名鍵の更新方針は従来どおり維持する。


## Summalyの表示キャッシュ

Web・Androidとも、Summalyの取得に成功したカードをクライアントのメモリに最大256件保持する。同じサービス・URLの取得は共有し、直近の取得・再確認から5分以内なら再取得しない。5分経過後もキャッシュを捨てず、再表示時には取得済みの内容を即表示し、表示中・オンラインの場合だけ裏で再確認する。成功時は同じURLを表示するカードを更新し、失敗時も前のタイトル・説明・画像を残す。更新に失敗した場合も5分は再試行を抑え、画面の往復による集中取得を避ける。

定期ポーリングは追加しない。全表示先が非表示・破棄された場合は進行中の共有取得を中断するが、成功済みのキャッシュは保持する。中断した更新は再表示時に再開できる。Webは既存の同時4件・再試行上限を維持し、AndroidはSession単位で保持する。TUI・GPUIにはSummalyによるプレビュー取得がないため、新しい取得経路は加えない。

## Homeのページ選択とDBの取得量

Home・Local・Social・投稿者ページは、順序付きインデックスから最大1ページ分の候補キーを選んでからDTOを組み立てる。過去ページは日時とentry IDのkeysetで進み、総投稿件数に比例する表示用baseの構築をしない。単一投稿・スレッドも本文候補を限定し、返信数は直接の返信だけを閲覧判定して数える。クライアントの追加リクエストは作らない。移行方法、権限・データ分布に伴う処理量の限界、30万／100万件の再現方法は [Homeのスケール検証](home-performance.md) に記載する。

## Home から個別投稿への遷移

Reactは投稿本文・日時・取得済みの返信先リンクを開く際、既知の投稿DTOを既存の上限付きメモリキャッシュへ渡す。APIサーバー・利用者単位に分離し、個別画面は本文を即表示して、既存のスレッド取得経路で本文・返信・リアクションを更新する。スレッド取得が失敗しても本文を残し、403・404では取得済みの投稿も取り除く。追加の取得経路・ポーリング・ライブ接続は増やさない。ブラウザ履歴や永続ストレージへ投稿DTOは保存しない。

Androidも本文・日時・取得済みの返信先リンクで、Session内の上限付きHomeキャッシュへDTOを渡す。個別画面の生成時に一度だけ受け取り、古いスレッドのキャッシュより優先して本文を即表示する。受け渡したDTOは確認済みと扱わず、表示中・オンラインの場合だけ既存の取得経路でスレッドを更新する。取得失敗時は本文を保持し、403・404なら本文と関連キャッシュを取り除く。タップがスクロールや子要素の操作で取り消された場合は受け渡さない。Session終了で破棄し、アカウント間で共有しない。APIの変更・取得経路・接続の追加はない。TUI・GPUIにはHome画面がなく、今回のための実装・取得は追加しない。
