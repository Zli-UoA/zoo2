# リクエストと接続の設計

## 基本方針

画像などのファイル本体は必要に応じて個別取得する。それ以外の表示用データは少数の取得・同期経路へまとめ、画面や部品が増えるたびにAPIリクエストや常設接続を増やさない。

初回取得、過去ページの取得、利用者の操作による書き込み、認証更新は必要な通信として扱う。リクエスト数を減らすために、権限確認や更新の正しさを省略しない。

- 既存のShapeや表示用DTOに含まれるデータを、別のREST APIで取り直さない。チャンネルの投稿者・リアクション（連合を含む）・添付メタデータ・返信数は `messages.display_data` を表示の正本とする。書き込みの楽観更新と同期確認に必要なコレクションは区別する。
- 同じ認証・用途のライブ接続は共有する。部品ごとにWebSocketやSSEを開かない。異なる権限・データ範囲のShapeを無理に混ぜない。
- 同じデータを使う通知バッジと画面などは、取得結果・ページング・既読状態まで共有する。カスタムhookの関数が共通でも、呼び出すたびに副作用を作る構成は共有とみなさない。
- 取得中の更新通知はまとめ、完了後に必要な再取得を1回行う。同じ対象の新しい通知が来ただけで通信を中断・再開しない。対象・アカウントの切替やアンマウントでは中断する。
- ポーリングを新設する前に既存の同期・更新通知を使えないか確認する。必要な場合は理由、対象、頻度、停止条件を説明する。完了前に次の取得を始めず、非表示タブでは停止し、復帰時に更新する。変化や稼働対象がない間は間隔を延ばす。
- キャッシュと進行中の取得は、認証・ワークスペース・対象に応じた範囲で共有する。設定や利用者の違うデータを混ぜない。共有する通信を1つの部品のアンマウントだけで中断しない。
- 一覧の各行から同じ絵文字一覧やURLメタデータを取り直さない。画像本体の取得と、その前段のメタデータAPIは区別する。

## 確認方法

初期表示、同じデータを使う複数部品の同時表示、画面の往復、更新通知の連続、遅い応答、タブの非表示と復帰、対象・アカウント切替を確認する。リクエスト数・接続数をテストで検証し、表示結果だけのテストで済ませない。

## 現在の通信経路と整理内容

| 対象 | 経路・対応 |
| --- | --- |
| チャンネル本文・連合リアクション | `messages` Shapeの `display_data`。Reactからの `federated-reactions` REST取得を廃止。旧APIは他クライアントとの互換用に維持する。 |
| 添付メタデータ | `display_data.attachments`。別Shapeは表示データのない旧キャッシュの補完に限定する。画像・ファイル本体は個別取得する。 |
| ローカルリアクション | 表示は `display_data.reactions`。既存の `message_reactions` Shapeは楽観的な追加・解除とtxid照合のため維持する。 |
| Home・ActivityPubのライブ通知 | シェルごとに1本の `/api/home/live` WebSocketを共有。通知を1秒間隔で集約し、非表示タブのライブ再取得を停止する。 |
| Androidの連合先カラー | ホーム・投稿詳細・プロフィールに出るホストを重複排除し、12件ずつ既存のZoo APIへ取得する。セッションで結果を共有し、非表示・オフラインでは開始しない。Zoo側は連合先の公開メタデータのみを参照し、件数・並行数・応答サイズ・期限を制限する。 |
| チャンネル・DMのピン留め | シェルごとに `/api/shapes/user_pinned_channels`（Electric、`liveSse`、永続化）を1本購読し、本人の行だけを配る。並びの版は `GET /api/channel-pins` と書き込みの応答で管理し、起動時、Electric が他の端末の変更を知らせたとき、および 409 の競合のときに取り直す。ポーリングは増やさない。 |
| 通知 | アカウントごとに1つのProviderでバッジ・画面の取得と既読状態を共有。ライブ再取得を5秒間隔で集約し、取得・追加ページの処理を直列化する。 |
| メッセージリンクの埋め込み | 本文中のチャンネル・メッセージのリンクは、Summalyへ送らず、`messages` Shape（on-demand）のsubset snapshotで、リンク先の1件だけを取る。同じ(チャンネル, メッセージ)を指すリンクの短い表示・カード・別の投稿は、ライブクエリを1つ共有し、取得は1件につき1回（`useLinkedMessageRows`）。リアクション・添付のShapeは購読しない。チャンネルの一覧（見られるチャンネル）にないリンク先は、取得しない。スレッド・キャッチアップ・Homeは画面外の行もマウントし、チャンネルの仮想化した一覧も画面外の行を先に描くので、投稿のカード（外部のURLのカードを含む）も本文中の短い表示も、画面の上下200px以内に近づいてから取り（`useNearViewport`）、取得したリンク先は、画面から離れても購読を保つ（表示が枠へ戻らないように。リンク先が変わったら、新しいリンク先はまた近くに来るまで取らない）。暗号化の格下げの判定に使う「同じチャンネルの暗号文のある行」は、読み込み済みの行を見るだけで、行を取る要求を増やさない（行を取らずに変更だけを購読する。購読はコレクションの同期を始めるので、メッセージを取得する問い合わせと同じチャンネルのときだけ使い、チャンネルだけを指すリンクは `messages` を同期しない）。サーバーのエラー（5xx）やオフラインは `useLiveQuery` の状態に出ないので、取得を始めて10秒たっても終わらないときは、枠をやめて「読み込めませんでした」と書く（再試行は Electric クライアントに任せる）。再試行されない失敗（4xx）は、チャンネルの `messages` コレクションと、それを使う問い合わせが `error` になり、同じ表示にする。失敗した問い合わせは描画のたびに作り直さず、購読者がいなくなって片付く（既定で5秒）まで共有する。片付いたあとの購読は問い合わせを作り直すが、`messages` コレクションが失敗のままなら、要求を出さずにまた失敗する。取り直すのは、ページの再読み込みか、そのコレクションを使う表示（リンク・チャンネル画面）がなくなって5分（`gcTime` の既定）たち、片付いたあとの購読。コレクションはアプリで共有するので、リンクの取得が先に失敗したチャンネルを開いた場合も、片付くまでは読み込みの失敗になり、チャンネル画面の「再試行」（再読み込み）で回復する。TUI は、開いているチャンネルのリンク先は同期済みの行だけを使い（追加の取得はしない。同期が終わっても行がなければ、見られないものとする）、ほかのチャンネルのリンク先は、描画した範囲と前後の半画面のメッセージのものを、チャンネルごとに1本の `messages` シェイプ（`log=changes_only`）を共有して subset snapshot（`id = $1`）で1件ずつ取る（`electric::spawn_linked`）。取得した行の削除・編集は live で届く。リンクが画面の近くになくなって30秒で購読を閉じ、購読を閉じたチャンネルの結果は256件まで覚える。通信エラーと5xxは間隔を空けて再試行し、10秒で「読み込めませんでした」と書く。4xx は待たずに同じ表示にして購読を止める。デスクトップ版の Leptos の画面も同じ規則で、購読の共有と解放は TUI と共有する（`electric::LinkedCache`）。取得は Rust 側が行う。WebView は、画面の近くの投稿のリンク先（開いているチャンネルと、一覧にないチャンネルを除く）が変わったときだけ、`zoo_watch_links` で全件を入れ替える（前の呼び出しが終わってから次を送る）。結果は `zoo://linked` で返す。Rust 側は定期的には起きず、取得の時間切れと購読を閉じる時刻にだけ同期する。 |
| 通話の招待 | シェルごとに `/api/shapes/call_invites`（Electric、`liveSse`）を 1 本購読する。自分が呼んだ・呼ばれた呼び出し中の行だけ（通常は 0〜数行）で、永続化しない。ポーリングは増やさない。着信は Shape の行から作り、期限の表示は行ごとのタイマー 1 つで更新する。 |
| Homeの設定・フォロー一覧、プロフィール | 設定・フォロー一覧は60秒、プロフィールは30秒の間隔でライブ再取得を集約し、前の応答を待つ。フォローなどの操作後は即時反映する。Home本文の更新も取得中は予約する。 |
| アプリのprivate UI | サーバーから利用者向け更新通知がないためポーリングを維持。2〜30秒へ待機時の間隔を延ばし、コマンド・アクション後は即時取得と短期間の監視に戻す。 |
| アプリの公開surface・接続状態 | 表示中だけ2〜30秒のポーリング。取得を重ねず、非表示では停止する。 |
| 入力中表示 | 専用pushがないため取得は1.5〜5秒。入力者がいる間は1.5秒、待機中は間隔を延ばす。入力開始・タブ復帰時は即時取得。送信の2秒間隔はサーバーの短いリースを維持するため残す。本文や下書きは送らない。 |
| 通話一覧 | 表示中の10秒ポーリング。非表示で停止し、取得の重なりを防ぐ。通話中のシグナリング・リース更新は別の必要な通信として維持する。 |
| チャンネル未読 | 非アクティブな全チャンネルの本文購読を開く代わりに、アカウントごとに1つの共有Providerが軽量な `GET /api/channel-read-states`（`has_unread` のみ）の10秒取得と既読操作後の更新を維持する。左レールとサイドバーはこの1本を共有し、取得中・非表示の更新はまとめて1回だけ再取得する。キャッチアップは画面を開いたときと明示的な更新のときだけ同じAPIへ `?details=1` を付けて件数・最古時刻を1回取得し、キューを固定する。ポーリングで詳細を取り直さず、本文は表示中の1会話だけを購読して次へ進むと解放する。 |
| 絵文字一覧 | 設定ごとに進行中の取得を共有し、成功した値を60秒再利用する。各行のマウントで再取得しない。管理画面で変更したときは明示的に無効化する。 |
| アカウント絵文字・メンション用プロフィール | `/api/emoji-accounts` は既存の本文DTOにないディレクトリ情報として取得する。Reactは設定ごとに結果・取得・60秒の更新タイマーを共有し、60秒以内の再マウントでは再取得しない。AndroidはSessionのキャッシュと逐次取得を使い、非表示・オフラインで停止する。TUIは既存の絵文字取得ゲートへ統合し、フォーカス中だけ60秒ごとに取得する。TauriのLeptos UIもフォーカス中だけ60秒の期限を確認し、進行中の取得を重ねず、セッション切替前の結果を捨てる。 |
| 添付URL | 設定・添付IDごとに期限付き結果と進行中の取得を共有する。同じ画像が一覧とスレッドにあってもURL発行APIは重複させない。保存（ダウンロード）は中止と進捗を保存だけに効かせるため、進行中のプレビューの本文取得とは合流せず、本文だけを別に取得する。URL発行APIの結果は共有する。 |
| スレッド一覧 | Reactは設定・アカウント・範囲ごとに結果とページングを共有し、変更がなければ60秒以内の再マウントでは再取得しない。購読停止中の書き込みも変更世代として記録し、再展開時に更新する。アクティブ一覧はサーバーの専用pushがないため60秒更新する。アーカイブ履歴の一覧・検索UIは設けず、投稿の返信を開く操作から閲覧する。TUIも60秒更新を維持し、操作後の更新とページ取得を範囲ごとに直列化・集約する。いずれも非表示では開始しない。Reactは最後の購読解除・非表示で中断し、復帰で更新する。閉じたスレッドの本文取得は行わない。 |
| TauriのDND・自動更新 | OS通知の抑制にはウィンドウを閉じた間もDNDの設定が必要なため、プロフィールをセッションにつき起動時と5分ごとに逐次取得する。ログアウト・セッション切替で停止する。自動更新は有効な配布ビルドだけ起動30秒後と6時間ごとに逐次確認し、設定で無効化できる。専用の常設接続は増やさない。 |
| Presence・Bubble Chat | 短いリースと入力共有に必要な既存通信。Presenceは表示中だけ30秒更新。Bubble Chatは表示中の逐次ポーリングと入力送信の間引きを維持する。 |
| Slack取り込み進捗 | 取り込み中に限った既存ポーリングを維持する。 |

アプリUI・入力中表示などのポーリングを完全に除くには、権限を守った利用者／チャンネル単位のpushが必要。Homeの全体更新通知へ入力イベントなどを混ぜると全利用者の再取得を増やすため、その代用にはしない。今後の追加は少数の共有接続へ対象を購読する設計を優先する。

## プラットフォームごとの適用

この方針はReact、Androidの共通Kotlin、TUI、デスクトップに適用する。あるクライアントだけを修正して共通化済みとせず、同じ機能がある各実装を確認する（API・Shape・DBの形式や認可条件を変更しない方針。なお、#690 で新設した `forwarded_message_ids` の未対応クライアント展開は #698 で別管理する）。

| 実装 | 対応 |
| --- | --- |
| React | 上記の共有Provider、ライブ接続の共有、再取得の集約、ポーリングの停止と間隔調整、メタデータ取得の共有。 |
| Android | Sessionにある共有通知状態とHomeLiveの1接続を維持。連合リアクションのREST別取得を廃止し、`display_data` を使う。通知・Home・プロフィールは取得中の更新を予約し、Homeの制御情報を60秒、プロフィールを30秒、ライブ通知を1秒単位で集約する。Home本文の取得は5秒の同じゲートにまとめる。surface・アプリ接続は2〜30秒、typingは1.5〜5秒へ待機時の間隔を延ばし、非表示・オフラインで停止する。絵文字一覧はSessionの60秒キャッシュを共有する。 |
| TUI | 共通の `client-types`（`client-core` からも再公開）がメッセージに同梱されたローカル・連合リアクションを読み取り、リアクション用Shapeの追加購読を廃止。読み取りAPIに10秒の上限を設ける。入力中の更新は進行中の更新があれば間引き、停止は前の送信を待って順序を守る。共通の `PollGate` でtyping・未読・絵文字取得を逐次実行し、typingは待機時に最大5秒へ間隔を延ばす。フォーカス喪失中のポーリングと自動既読を停止し、復帰・対象切替・入力開始時に更新を要求する。チャンネル切替では以前の本文購読を解放する。 |

TUIにはHome・ActivityPub通知・アプリsurfaceの画面がないため、それらのために新しいAPI取得や接続は追加しない。Rustのリアクション変更は本文の同期で反映され、React・Androidで残す楽観書き込み用Shapeと用途が異なる。旧クライアント用の互換APIは維持する。

スレッドの個人参加状態は既存のメッセージShapeにないため、閲覧中のスレッドだけ `/api/threads/{id}` で取得する。この応答は、参加状態に加えて、参加人数と参加者の一覧（先頭から最大50人）も返す。一覧を開かなくても、60秒ごとの取得のたびに、参加行の数Pに比例する読み取り（参加者ごとの `users`・`channel_user` の主キー参照）が走る。Pは、退出済みの行も含む、そのスレッドの全参加行の数（`thread_participants` の主キーの範囲走査は、退出済みの行も読み、人数と一覧にだけ載せない。`users` と `channel_user` の参照は、退出していない行の分だけ）。一覧だけを別の取得に分けず、1回の取得にまとめる。理由は、人数と一覧を同じ時点の値にそろえることと、取得の回数を増やさないこと。許容するPは、退出済みを含めて10,000までで、SQLだけの測定（`thread_participants_scale_test`、PostgreSQL 18、U=30万〜300万、P=10,000）では、単独で p50 約0.28〜0.43秒・p95 約0.29〜0.46秒、8同時で p50 約1.0〜1.3秒・p95 約1.2〜1.5秒（hit＋read は、U=30万で約65,000、U=100万以上で約75,000ブロック。このPは、退出500・無効化500・チャンネルから外れた500を含む。退出済みの行が大半を占めるスレッド（P=10,000、うち退出9,500、参加中500）も測り、hit＋read は約3,900〜4,400ブロック（U=30万で約3,900、100万以上で約4,400）、単独で約20ms。`users` と `channel_user` の参照が参加中の500行だけで済み、退出済みの9,500行は範囲走査で読むだけなので、同じPなら、参加中が多いスレッドより軽い）。これを超える規模のスレッドを想定する場合は、一覧を開いたときの取得に分けるか、参加人数だけの集計を別に持つ設計に変える。参加者を表示しないAndroid・TUIは、`?participants=none` で人数と一覧を省き、`tracked` だけを1回の索引参照で受け取るので、この読み取りは走らない。ただし、付けるのは、このPRで更新した版のクライアントだけで、配布済みの旧版（Android・TUI）は付けないため、更新するまでは、旧版の取得も、Webと同じにPに比例する。Reactは設定・利用者・スレッドIDごとに取得とタイマーを共有し、表示中60秒、非表示・未購読時停止、復帰時更新とする。投稿後の通知は取得中に集約し、参加・退出の応答は再取得せず反映する。アカウントをまたぐ操作結果は一覧へ適用しない。Androidも表示中の1ペインだけ60秒で取得し、操作と取得を直列化する。本文・返信数は既存の同期データを使う。

参加者一覧の測定は、次の2つのテストで再現する（どちらも `#[ignore]`。`DATABASE_URL` と `ACTIVITYPUB_BASE_URL` を指定し、`session_replication_role` を変えられるロールで、`cargo test --manifest-path backend/Cargo.toml --test <名前> -- --ignored --nocapture` を実行する）。ここに載せる時間は、すべて手元の1台（WSL2・PostgreSQL 18.7・同一ホスト・最適化なしのビルド）の値で、本番（PostgreSQL 16.15）の値ではない。環境で大きく変わり（別の環境のPostgreSQL 16.15で同じAPI計測を実行したところ、単独の取得は p50 約43 msで、約5分の1だった）、同じ環境でも実行ごとに2〜5割ずれる。そのため、許容するPの根拠は、環境に依らない探索量（hit＋readのブロック数と、各テーブルの読む行数）に置き、時間は目安にとどめる。`thread_participants_scale_test` はSQLだけを測る（上の値。サーバーが同じホストのときは、CPU時間も測る）。`SCALE_USERS`（`users` の件数）、`SCALE_HISTORY`（無関係な参加行の件数。省略すると `SCALE_USERS` と同じ）はどちらも30万以上、`SCALE_PLAN_DIR` は実行計画の出力先で、移行済みの使い捨てDBで実行する。どちらのテストも、参加者のIDは、`users` の全域に重複なく散らす（`support/spread.rs`。黄金比に近い刻みで、先頭からP件が全域に均等に入る）。CIの `query-budget` は `SCALE_USERS` だけを変えて（30万・100万）測り、`SCALE_HISTORY` を指定しないため、次の分離の値は、CIでは再現されない。P=10,000の一覧（hit＋read）は、U=30万・履歴30万で 65,360、U=30万・履歴300万で 65,432、U=100万・履歴100万で 74,912、U=300万・履歴30万で 74,893、U=300万・履歴300万で 74,876で、履歴だけを10倍にしても仕事量は変わらず（+72）、Uを大きくすると、30万から100万の間で約15%増え（1キーあたり 6.9 → 7.9ブロック。索引の段が増えた分と見ているが、段数は確認していない）、300万まで増えない。CIと同じPostgreSQL 16（16.11。同じホストの別クラスタ）で `query-budget` 相当（U=30万・100万）を測ると、hit＋readは 65,413 → 65,418 で増えず、比較スクリプトも通った。実行時間は約0.06〜0.11秒で、PG18.7のクラスタの約1/3〜1/6だった（版・ビルド・プランの形のどれによるかは、切り分けていない）。`thread_participants_api_latency_test` は、ルーター・接続待ち・SQL往復・JSON・ロック待ちを含むAPI全体を、P≈10,000のスレッドで各30回測る。`API_LATENCY_USERS`（`users` の件数。省略するとP。P以上）で `users` の大きさを変える。結果は次のとおり（ms。p50／p95／最大。退出・参加は p50）。

## Home の仮想スクロールと更新範囲

React の Home は可変高さの行を TanStack Virtual で実測し、表示範囲の前後6行を描画する。読み込み済みの末尾10件に近づいた時点で、既存の `before` カーソルを使って次の50件を先読みする。取得は直列にし、最終ページ・エラー・非表示では自動取得を止める。先読みの失敗状態は先頭・表示範囲の更新とは分けて保持し、先読みの明示的な再試行成功またはTLの再読込まで自動取得を再開しない。エラー時は既存の「過去の投稿を読む」から再試行できる。

ライブ通知と表示範囲の移動による再確認は5秒間隔の同じゲートへ集約する。ライブ通知では先頭50件を取得し、それに含まれない表示範囲の entry ID を `POST /api/home/entries` で一括確認する。表示範囲の移動だけなら先頭を取り直さず、表示範囲だけを一括確認する。直近の先頭取得で確認済みの範囲へ移動しただけなら追加取得しない。最大100件で、本文や画像URLを行ごとに取得しない。長いリモートIDを含むため、ID一覧はURLではなくJSON本文で送る。サーバーは通常の一覧と同じタイムライン・投稿者・公開範囲の条件を適用し、削除済み・閲覧不可の項目を返さない。通常投稿とリポストは `entry_id` で区別する。

過去に読み込んだ全件は再取得せず、表示範囲に入ったときに編集・削除・公開範囲の変更を再確認する。新着と既存の先頭に重なりがない場合、途中の閲覧位置では現在の履歴を保持し、先頭へ戻ったときに最新の一覧へ切り替える。手動更新とタイムライン切替は先頭から読み直す。本文の仮想化・先読みはReactの変更であり、共有APIの既存の応答形式は変更しない。Androidも `LazyColumn` の末尾10項目に近づくと50件ずつ先読みし、ライブ更新は先頭50件と表示中の最大100件だけを確認する。過去ページの取得と更新を直列化し、先読み失敗後は明示的な再試行まで自動取得を止める。TUIにはHome画面がないため、今回のために取得処理を追加しない。
## Home の引用投稿

引用先URIと表示用の引用元はHomeのDTOに含める。サーバーはページ内の投稿・返信親の引用を1つのDBクエリでまとめ、公開範囲・削除・ブロック・取得元検証を確認する。ローカル引用元はURIからIDを取り出し、home_posts.idの主キーへ直接結合する。画像のメタデータ補完もページ全体で行う。クライアントは引用カードごとのAPIや常設接続を作らず、既存のHomeライブ再取得で更新する。引用元の署名付きHTTPS取得は、コミット後にDBで配信先権限・引用先・未取得かを確認してからバックグラウンド処理へ渡し、同時4件・1段・最大20秒に限定する。Inboxの同時実行枠とは分け、処理枠が埋まっているときは待機タスクを増やさない。失敗や処理枠上限による未取得分は、後続のCreate・Update・Announceで再度試みる。通常URLには既存のSummaly取得共有・キャッシュを利用し、引用先は除外する。

Reactでは、投稿を開く前のTLをワークスペース・アカウント・履歴エントリ・タイムラインごとにタブのメモリへ最大8件保存する。各履歴は最大1,000投稿かつJSONのUTF-16換算で4MiB以下に制限する。超過した履歴は途中を切り取らず保存自体を省き、戻った際は先頭から再取得する。投稿一覧、ページ末尾、実測した行の高さ、閲覧中の行とその表示位置を復元するため、詳細から戻っても読み込み済み履歴を先頭から取り直さない。端末ストレージへ本文は保存しない。削除成功時は関連するキャッシュから通常投稿とリポストを取り除き、古い進行中の取得を中断して投稿の復活を防ぐ。TL上の削除ではページを遷移せず、閲覧位置を維持する。個別ページの対象投稿を削除した場合はアプリ内の直前の画面へ戻り、戻り先がない直リンクでは `/home` へ置き換える。

投稿メニューは本文の長さに左右されない右上へ置き、メニュー操作が投稿カードのクリックへ伝わらないようにする。途中を閲覧中の新着は位置を変えず、先頭へ戻るボタンから開ける。コピーと削除の成功は既存の通知UIで知らせ、削除失敗時は確認画面にエラーと再試行操作を残す。

表示範囲の一括確認だけに失敗した場合は、取得できた先頭の更新を反映し、確認できなかった既存行は削除しない。失敗は表示するが、先読み専用の失敗状態にはしないため、次のページは取得できる。

`/api/home/entries` は通常投稿・リポストから対象の投稿IDを引き、表示判定の前に対象とその親・返信へ絞る。投稿者ページも、その投稿者のIDを先に集めて同じ範囲へ絞る。範囲を引いた後の主キー参照はLATERALとOFFSET 0で保ち、推定件数により全投稿へ公開範囲の判定が走る計画を避ける。公開範囲・ブロック・引用の条件は通常一覧と共通のまま維持する。件数制限は表示件数に対するもので、非常に大きい会話・投稿者履歴の探索量自体には上限を設けていない。

## Home の単一投稿・スレッド取得

`/api/home/{id}` と `/api/home/{id}/thread` は、まず主キーと既存の返信親インデックスで会話に関係する投稿IDを集め、その範囲に既存の公開範囲・チャンネル・受信者・ブロック・削除の条件を適用する。ID探索自体は閲覧許可を与えない。循環はIDの重複排除で停止する。親のプレビューと返信数に必要な投稿も範囲に含め、描画の深さと件数の上限は既存のまま保つ。

スレッド取得は同じSQLの結果に要求された投稿が含まれることを確認し、見つからない場合は404を返す。存在確認のために本文・リアクション・引用などを二度取得しない。通常のタイムラインには会話の絞り込みを加えない。ReactとAndroidは既存の同じAPIから改善を受け、追加の通信や接続は不要。Home画面のないTUIの取得経路は変えない。

## 通知とAndroidの表示キャッシュ

Web・Androidの連合通知は、ライブ更新ごとに読み込み済みの全ページを再取得しない。先頭100件と、そこに含まれない表示中の通知を `POST /api/activitypub/notifications/entries` で最大100件確認する。後者は一覧と同じ所有者・投稿の閲覧条件を使い、返されなかった表示中の通知を取り除く。既存の末尾カーソルを維持し、過去ページの取得と再確認を直列化する。非表示では新しい取得を始めず、アカウント切替で進行中の処理と表示範囲を分離する。

通知のSQLは `notification_events` の所有者・作成日時・IDのインデックスで最大101件を選んでから、本文・アバター・絵文字を組み立てる。ページを確定する前に全通知をJSON化しない。Androidの自動既読は100msの間に見えたIDをまとめ、既存の `/api/notifications/read` へ最大500件ずつ送る。通知一覧のグループ化と並べ替えは入力が変わったときだけ行い、スクロール位置の変化では繰り返さない。

AndroidはHomeの投稿・末尾・閲覧位置をSession内で最大8画面、1画面1,000件・4MiBまで保持する。直近の先頭確認から30秒以内の画面往復では、新しい先頭取得を省き、ライブ通知と表示中の範囲の再確認で更新する。ログアウト・別アカウントには引き継がず、削除した投稿を含むキャッシュは破棄する。ディスクの画像キャッシュに加え、Session内のデコード済み画像も最大64MiB・256件のLRUに保持し、同じURLの取得とデコードを共有する。失敗は次回に再試行でき、Session終了で破棄する。

ユーザーページで既知のリモートアカウントを開くときは、保存済みプロフィールを表示し、署名鍵キャッシュの期限切れを理由に相手サーバーの応答を待たない。未取得アカウントの解決と、Inbox・署名鍵の更新方針は従来どおり維持する。


## Summalyの表示キャッシュ

Web・Androidとも、Summalyの取得に成功したカードをクライアントのメモリに最大256件保持する。同じサービス・URLの取得は共有し、直近の取得・再確認から5分以内なら再取得しない。5分経過後もキャッシュを捨てず、再表示時には取得済みの内容を即表示し、表示中・オンラインの場合だけ裏で再確認する。成功時は同じURLを表示するカードを更新し、失敗時も前のタイトル・説明・画像を残す。更新に失敗した場合も5分は再試行を抑え、画面の往復による集中取得を避ける。

定期ポーリングは追加しない。全表示先が非表示・破棄された場合は進行中の共有取得を中断するが、成功済みのキャッシュは保持する。中断した更新は再表示時に再開できる。Webは既存の同時4件・再試行上限を維持し、AndroidはSession単位で保持する。TUIにはSummalyによるプレビュー取得がないため、新しい取得経路は加えない。

## Homeのページ選択とDBの取得量

Home・Local・Social・投稿者ページは、順序付きインデックスから最大1ページ分の候補キーを選んでからDTOを組み立てる。過去ページは日時とentry IDのkeysetで進み、総投稿件数に比例する表示用baseの構築をしない。単一投稿・スレッドも本文候補を限定し、返信数は直接の返信だけを閲覧判定して数える。クライアントの追加リクエストは作らない。移行方法、権限・データ分布に伴う処理量の限界、30万／100万件の再現方法は [Homeのスケール検証](home-performance.md) に記載する。

## Home から個別投稿への遷移

Reactは投稿本文・日時・取得済みの返信先リンクを開く際、既知の投稿DTOを既存の上限付きメモリキャッシュへ渡す。APIサーバー・利用者単位に分離し、個別画面は本文を即表示して、既存のスレッド取得経路で本文・返信・リアクションを更新する。スレッド取得が失敗しても本文を残し、403・404では取得済みの投稿も取り除く。追加の取得経路・ポーリング・ライブ接続は増やさない。ブラウザ履歴や永続ストレージへ投稿DTOは保存しない。

Androidも本文・日時・取得済みの返信先リンクで、Session内の上限付きHomeキャッシュへDTOを渡す。個別画面の生成時に一度だけ受け取り、古いスレッドのキャッシュより優先して本文を即表示する。受け渡したDTOは確認済みと扱わず、表示中・オンラインの場合だけ既存の取得経路でスレッドを更新する。取得失敗時は本文を保持し、403・404なら本文と関連キャッシュを取り除く。タップがスクロールや子要素の操作で取り消された場合は受け渡さない。Session終了で破棄し、アカウント間で共有しない。APIの変更・取得経路・接続の追加はない。TUIにはHome画面がなく、今回のための実装・取得は追加しない。

## メッセージ転送（引用）元の一括解決

Electric の `messages` Shape には転送元の本文や送信元チャンネル名を含めず、ID 配列の `forwarded_message_ids`（`jsonb`）だけを流す。閲覧時は `POST /api/messages/forwards/resolve`（`Cache-Control: no-store`）で解決し、クライアント側（React）では 20ms の待機ウィンドウで最大 100 件ごとに一括化し、進行中・解決済みの ID を `${apiBaseUrl}\0${currentUserId}` 単位で重複排除・キャッシュする。解決結果にはステータスに応じた有効期限（`ok`: 60 秒、`unavailable`: 30 秒、`deleted`: 300 秒）を持たせ、タブ再表示（`visibilitychange`）時に期限切れエントリを破棄して再取得するほか、開いたままの可視タブでも表示中エントリの最短有効期限に合わせた単一タイマーで期限切れ時に自動破棄・再検証する。あわせて自タブでの編集・削除操作時にも該当 ID のキャッシュを即座に破棄する。タブが非表示（`hidden`）のあいだは要求を送り出さず可視復帰時に送り、失敗時はキャッシュを汚染せず再試行できるようにする。

バックエンドは入力された ID 配列から各テーブルの主キー（`messages`・`channels`・`users`・`slack_forward_targets(message_id)`・`slack_channels(team_id, slack_channel_id)`）と `idx_channel_user_channel_id (channel_id, user_id)` を使って `messages`・`channels`・`users`・`channel_user`・`slack_forward_targets`・`slack_channels` を O(K log N) で参照し、公開／非公開・DM・ゲスト・Bot 参加・E2EE 除外・論理削除の権限判定を行う。閲覧権限のないチャンネル・未取り込みチャンネル・暗号化チャンネル・存在しない ID については削除済みかどうかも含めてすべて `unavailable` とし、権限のあるチャンネル内の削除済み投稿のみ `deleted` を返す（存在オラクル防止）。入れ子転送の解決は 1 段までとし、解決結果の `has_forwards` が真のときは元投稿へのリンクだけを表示する。`POST /api/apps/v1/messages`（App API）は未対応（`400 Bad Request`）とする。React Web（`frontend/src`）と Web Push（転送のみの通知を代替文言で表現）を先行対応とし、`frontend-compose`（Android）・`desktop-tauri`（`desktop-tauri/ui`）・`tui` での対応は #698 へ切り出す（#698 完了前に Web の転送 UI を機能フラグで隠さず先行リリースする判断とし、未対応クライアントで Web 投稿・Slack 取り込みの本文が空の転送投稿を開いた場合はコメントのみ／発言者と時刻のみの行として表示される点をリリース上の既知事項として扱う。また過去転送のバックフィル CLI の `--apply` 実行は #698 反映後に行う）。
