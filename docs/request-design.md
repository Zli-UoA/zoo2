# リクエストと接続の設計

## 基本方針

画像などのファイル本体は必要に応じて個別取得する。それ以外の表示用データは少数の取得・同期経路へまとめ、画面や部品が増えるたびにAPIリクエストや常設接続を増やさない。

初回取得、過去ページの取得、利用者の操作による書き込み、認証更新は必要な通信として扱う。リクエスト数を減らすために、権限確認や更新の正しさを省略しない。

- 既存のShapeや表示用DTOに含まれるデータを、別のREST APIで取り直さない。チャンネルの投稿者・リアクション（連合を含む）・添付メタデータ・返信数は `messages.display_data` を表示の正本とする。書き込みの楽観更新と同期確認に必要なコレクションは区別する。
- 同じ認証・用途のライブ接続は共有する。部品ごとにWebSocketやSSEを開かない。異なる権限・データ範囲のShapeを無理に混ぜない。
- 同じデータを使う通知バッジと画面などは、取得結果・ページング・既読状態まで共有する。カスタムhookの関数が共通でも、呼び出すたびに副作用を作る構成は共有とみなさない。
- 取得中の更新通知はまとめ、完了後に必要な再取得を1回行う。同じ対象の新しい通知が来ただけで通信を中断・再開しない。対象・アカウントの切替やアンマウントでは中断する。
- ポーリングを新設する前に既存の同期・更新通知を使えないか確認する。必要な場合は理由、対象、頻度、停止条件を説明する。完了前に次の取得を始めず、非表示タブでは停止し、復帰時に更新する。変化や稼働対象がない間は間隔を延ばす。
- キャッシュと進行中の取得は、認証・ワークスペース・対象に応じた範囲で共有する。設定や利用者の違うデータを混ぜない。共有する通信を1つの部品のアンマウントだけで中断しない。
- 一覧の各行から同じ絵文字一覧やURLメタデータを取り直さない。画像本体の取得と、その前段のメタデータAPIは区別する。

## 確認方法

初期表示、同じデータを使う複数部品の同時表示、画面の往復、更新通知の連続、遅い応答、タブの非表示と復帰、対象・アカウント切替を確認する。リクエスト数・接続数をテストで検証し、表示結果だけのテストで済ませない。

## 現在の通信経路と整理内容

| 対象 | 経路・対応 |
| --- | --- |
| チャンネル本文・連合リアクション | `messages` Shapeの `display_data`。Reactからの `federated-reactions` REST取得を廃止。旧APIは他クライアントとの互換用に維持する。 |
| 添付メタデータ | `display_data.attachments`。別Shapeは表示データのない旧キャッシュの補完に限定する。画像・ファイル本体は個別取得する。 |
| ローカルリアクション | 表示は `display_data.reactions`。既存の `message_reactions` Shapeは楽観的な追加・解除とtxid照合のため維持する。 |
| Home・ActivityPubのライブ通知 | シェルごとに1本の `/api/home/live` WebSocketを共有。通知を1秒間隔で集約し、非表示タブのライブ再取得を停止する。 |
| 通知 | アカウントごとに1つのProviderでバッジ・画面の取得と既読状態を共有。ライブ再取得を5秒間隔で集約し、取得・追加ページの処理を直列化する。 |
| Homeの設定・フォロー一覧、プロフィール | ライブ再取得を5秒間隔で集約し、前の応答を待つ。Home本文の更新も取得中は予約する。 |
| アプリのprivate UI | サーバーから利用者向け更新通知がないためポーリングを維持。2〜30秒へ待機時の間隔を延ばし、コマンド・アクション後は即時取得と短期間の監視に戻す。 |
| アプリの公開surface・接続状態 | 表示中だけ2〜30秒のポーリング。取得を重ねず、非表示では停止する。 |
| 入力中表示 | 専用pushがないため取得は1.5〜5秒。入力者がいる間は1.5秒、待機中は間隔を延ばす。入力開始・タブ復帰時は即時取得。送信の2秒間隔はサーバーの短いリースを維持するため残す。本文や下書きは送らない。 |
| 通話一覧 | 表示中の10秒ポーリング。非表示で停止し、取得の重なりを防ぐ。通話中のシグナリング・リース更新は別の必要な通信として維持する。 |
| チャンネル未読 | 非アクティブな全チャンネルの本文購読を開く代わりに、既存の10秒取得と既読操作後の更新を維持する。非表示では取得しない。 |
| 絵文字一覧 | 設定ごとに進行中の取得を共有し、成功した値を60秒再利用する。各行のマウントで再取得しない。管理画面で変更したときは明示的に無効化する。 |
| 添付URL | 設定・添付IDごとに期限付き結果と進行中の取得を共有する。同じ画像が一覧とスレッドにあってもURL発行APIは重複させない。 |
| Presence・Bubble Chat | 短いリースと入力共有に必要な既存通信。Presenceは表示中だけ30秒更新。Bubble Chatは表示中の逐次ポーリングと入力送信の間引きを維持する。 |
| Slack取り込み進捗 | 取り込み中に限った既存ポーリングを維持する。 |

アプリUI・入力中表示などのポーリングを完全に除くには、権限を守った利用者／チャンネル単位のpushが必要。Homeの全体更新通知へ入力イベントなどを混ぜると全利用者の再取得を増やすため、その代用にはしない。今後の追加は少数の共有接続へ対象を購読する設計を優先する。

## プラットフォームごとの適用

この方針はReact、Androidの共通Kotlin、TUI、デスクトップに適用する。あるクライアントだけを修正して共通化済みとせず、同じ機能がある各実装を確認する。API・Shape・DBの形式や認可条件は変更しない。

| 実装 | 対応 |
| --- | --- |
| React | 上記の共有Provider、ライブ接続の共有、再取得の集約、ポーリングの停止と間隔調整、メタデータ取得の共有。 |
| Android | Sessionにある共有通知状態とHomeLiveの1接続を維持。連合リアクションのREST別取得を廃止し、`display_data` を使う。通知・Home・プロフィールは取得中の更新を予約し、Homeの制御情報・プロフィールを5秒、ライブ通知を1秒単位で集約する。surface・アプリ接続は2〜30秒、typingは1.5〜5秒へ待機時の間隔を延ばし、非表示・オフラインで停止する。絵文字一覧はSessionの60秒キャッシュを共有する。 |
| TUI・デスクトップ | 共通の `client-types`（`client-core` からも再公開）がメッセージに同梱されたローカル・連合リアクションを読み取り、リアクション用Shapeの追加購読を廃止。読み取りAPIに10秒の上限を設ける。入力中の更新は進行中の更新があれば間引き、停止は前の送信を待って順序を守る。共通の `PollGate` でtyping・未読・絵文字取得を逐次実行し、typingは待機時に最大5秒へ間隔を延ばす。フォーカス喪失中のポーリングと自動既読を停止し、復帰・対象切替・入力開始時に更新を要求する。チャンネル切替では以前の本文購読を解放する。 |

TUI・デスクトップにはHome・ActivityPub通知・アプリsurfaceの画面がないため、それらのために新しいAPI取得や接続は追加しない。Rustのリアクション変更は本文の同期で反映され、React・Androidで残す楽観書き込み用Shapeと用途が異なる。旧クライアント用の互換APIは維持する。
