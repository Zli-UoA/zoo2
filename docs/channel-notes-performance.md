# チャンネルノートの取得・書き込み・期限切れ削除の探索量

## 設計時の変数と上限

無関係なノート履歴を N、対象チャンネルの有効ノート数を K（API 上限 500）、対象チャンネルの期限内の削除済みノート数を D、期限切れノートの削除バッチを B、cleanup が 1 回で調べるチャンネル数を C とする。K・D は固定し、N を 30 万件・100 万件へ増やして比較する。

| 処理 | 探索の上限 | 主な索引 |
| --- | --- | --- |
| 一覧・単一取得 | O(log N + K)。`channel_id` と `deleted_at IS NULL` に限定 | `idx_channel_notes_channel_position`、主キー |
| 作成 | 位置の最大値 O(log K + 1) と INSERT 1 行。E2EE trigger は `channels` の主キー | 有効ノートの部分索引、`Channel_pkey` |
| 更新・削除 | 主キーと `channel_id` で 1 行。generic plan でも K 行以内 | 主キー、`channel_id` 索引 |
| 復元 | 削除済みノート D 行以内を探し、位置を後ろへずらす K 行以内 | `idx_channel_notes_expired`、有効ノートの部分索引 |
| 並べ替え | 有効ノート K 行の位置更新 | 有効ノートの部分索引 |
| 期限切れ削除 | 1 回の page は C=100 チャンネル、店舗の存在確認は D 行以内、削除は B=100 行以内。カーソルで回転 | `idx_channel_notes_expired` |
| 暗号化 trigger | 対象チャンネルの有効・復元可能ノート D 行以内 | `idx_channel_notes_channel_updated` |

N はどの処理の探索上限にも入れない。無関係なチャンネルのノートは `channel_id` の索引範囲外であり、一覧・書き込み・削除の対象にならない。API は有効ノートが 500 件に達している状態の作成・復元を `409 Conflict` で拒否するため、K の最悪値は 500 件である。以下の 50 件計測は代表値で、一覧・並べ替え・復元の計算量は O(K) のまま 500 件で上限になる。

## 検証結果

PostgreSQL 16.15、JIT 無効。ローカルの使い捨て DB で、Rust の統合テストから `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, FORMAT JSON)` を実行した。SQL の計測は単独 30 回（custom plan）と 8 同時×30 回（`force_generic_plan`）で、初回も捨てない。API は実際の Axum Router を in-process で呼び、認証・プール待ち・トランザクション・シリアライズを含む。HTTP ネットワークとブラウザー描画は含まない。debug build の参考値である。

### fixture

- 対象チャンネル: 有効 50 件（API 上限 K=500 の代表値）、空 0 件、削除済み 100 件（24 時間以内 50 件、期限切れ 50 件）。
- 無関係な履歴: 別チャンネルに N=300,000 / 1,000,000 件のノート。10% は期限切れ、残りは有効。
- API 書き込み用に UUID のノートを 16 件作成し、8 同時の更新・削除・復元で共有する。
- 計測対象の INSERT/UPDATE/DELETE は本番 trigger を有効にする。fixture の大量投入だけ trigger を外す。

### SQL の走査量と論理バッファ

行数は関係ごとの Actual Rows と除外行に loops を掛けた合計。論理バッファは hit+read。値は全サンプルの最大。

| 条件 | 30 万件 行数 / ブロック | 100 万件 行数 / ブロック |
| --- | ---: | ---: |
| 一覧（50 件） | 50 / 5 | 50 / 5 |
| 一覧（空） | 0 / 3 | 0 / 3 |
| 削除済み一覧（24 時間以内 50 件） | 50 / 12 | 50 / 13 |
| 単一取得 | 1 / 4 | 1 / 4 |
| 作成位置の最大値 | 1 / 4 | 1 / 4 |
| 更新（trigger 込み） | 2 / 183 | 2 / 185 |
| 削除（trigger 込み） | 2 / 185 | 2 / 185 |
| 復元（位置ずらし含む） | 51 / 180 | 51 / 180 |
| 並べ替え 1 行（trigger 込み） | 1 / 184 | 1 / 193 |
| cleanup page（100 チャンネル） | 200 / 404 | 200 / 404 |
| cleanup delete（100 行まで） | 100 / 305 | 100 / 306 |
| 平文 trigger の channels 点検索 | 1 / 4 | 1 / 4 |
| 暗号化 trigger の存在確認 | 1 / 376 | 1 / 333 |

実行計画の形は、一覧が `idx_channel_notes_channel_position` の Index Scan、削除済み一覧が `idx_channel_notes_deleted_at`、cleanup の存在確認が `idx_channel_notes_expired`、暗号化 trigger が `idx_channel_notes_channel_updated` の Index Scan で、いずれも対象チャンネルの索引範囲で止まる。無関係な N 件を全件走査する Seq Scan はない。

N が 3.3 倍になっても、全条件で走査行数は同じで、論理バッファの差は索引の高さ・ページ配置による数ブロック以内だった。更新・削除・並べ替えの 180 前後のブロックは、対象チャンネルの 50 件の索引・ヒープ更新と trigger の点検索であり、無関係な N 件の履歴ではない。復元の 51 行は対象チャンネルの削除済み 50 件を期限順に確認した値で、N には依存しない。cleanup は 1 回の page が 100 チャンネル、存在確認が 100 件、削除が最大 100 行で、worker 全体でも 500 チャンネルずつ回転する。暗号化 trigger の存在確認は対象チャンネルの 50 件を `channel_id` の索引で調べる。暗号化 trigger の 333〜376 ブロックは、索引・ヒープのキャッシュ状態と対象チャンネルの 50 件の確認による観測値で、N が増えても同じ範囲に収まる。

## 再実行

空の使い捨て DB を規模ごとに用意し、全 migration を適用してから実行する。fixture は COMMIT するため、同じ DB で再実行しない。

```sh
psql "$ADMIN_DATABASE_URL" -c 'CREATE DATABASE notes_scale_300k'
atlas migrate apply --dir file://infra/db/migrations \
  --url "postgres://.../notes_scale_300k?sslmode=disable"
DATABASE_URL="postgres://.../notes_scale_300k?sslmode=disable" \
  SCALE_NOTES=300000 SCALE_PLAN_DIR=performance-results/notes-300000 \
  cargo test --manifest-path backend/Cargo.toml --test channel_notes_scale_test \
  channel_notes_work_is_bounded_by_channel_notes_not_history -- --ignored --nocapture
DATABASE_URL="postgres://.../notes_scale_300k?sslmode=disable" \
  SCALE_PLAN_DIR=performance-results/notes-300000 \
  cargo test --manifest-path backend/Cargo.toml --test channel_notes_scale_test \
  persisted_channel_notes_api_budget -- --ignored --nocapture
# 100 万件は別の空 DB を作り、SCALE_NOTES=1000000 で同じ 2 コマンドを実行する。
```

`channel_notes_work_is_bounded_by_channel_notes_not_history` は対象チャンネルと無関係履歴を作り、SQL の走査行数・中間行・ソート入力・論理バッファを検証して `work.json` を保存する。`persisted_channel_notes_api_budget` は同じ DB の fixture を使い、単独 30 回・8 同時 240 回の API 時間と cleanup の実行時間を `api.json` に保存する。どちらも探索量の上限超過・履歴への比例増加・ディスク退避で失敗する。時間は記録するだけで合否に使わない。
