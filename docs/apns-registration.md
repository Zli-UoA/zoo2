# iPhoneの通知登録の競合

通常通知とVoIP着信の登録IDは、環境と端末トークンのSHA-256から作る。VoIPだけに `voip:` の接頭辞を付ける。IDを用途別にした一方、DBの `UNIQUE(device_token, environment)` は用途を含まなかったため、同じ値を別用途で登録すると409になり、同じ登録情報での再試行も失敗していた。

一意索引に、IDがVoIPの生成規約と一致するかを加える。通常通知とVoIPは同じトークン・環境でも共存し、同用途の重複は引き続き拒否する。トークンは16進文字列、環境はASCIIの固定値なので、SHA-256への入力は既存のUTF-8によるID生成と同じバイト列になる。

登録ID・所有者・解除情報は変更せず、既存行も削除しない。VoIP対応済みの移行前サーバーも同じID規約で読み書きしており、用途カラムの既定値や後付けの更新には依存しない。API・レスポンス・認可・登録上限・解除・Appleからの失効処理は維持する。Web・Android・TUIにはAPNs/PushKitの端末登録がないため、クライアントの変更は不要。

## 計算量と探索上限

全登録数をN、対象ユーザーの登録数をD（API経由で最大20）、解除記録数をRとする（未登録の解除要求には10,000件の受付上限があるが、正規の解除は別なので全体の定数上限とは扱わない）。登録処理のSQLと回数は変えない。主キーによる登録・解除記録の確認は各O(log N)、O(log R)で、登録は最大1行、解除記録は2つのIDに限定する。登録上限の確認は既存のuser_id索引によるO(log N + D)、返却は最大20行。更新・登録・解除は1行。新しい式索引は最大512文字のトークンから定数回のハッシュ計算とB-tree更新を行い、通常時に無関係な登録全件を走査しない。ページングや深いページは該当しない。

移行時だけ、全件の索引構築が必要になる。新しい索引を先に作り、成功後に古い制約を外す。新索引が区別する範囲は古い制約より細かいため、古い制約を満たす既存データが新索引の重複で失敗することはない。移行時の書き込み・DDLロックと、30万件・100万件での通常時の書き込みコストを別に検証する。

設計は[PostgreSQLの式索引](https://www.postgresql.org/docs/16/indexes-expressional.html)、[索引の並行構築](https://www.postgresql.org/docs/16/sql-createindex.html)、[Supabaseの複合索引の指針](https://github.com/supabase/agent-skills/blob/main/skills/supabase-postgres-best-practices/references/query-composite-indexes.md)と照合する。認可の検索は引き続きIDとuser_idの索引で行い、新索引は用途別の一意性の維持に使う。新たな通信・ポーリング・接続は追加しない。

## 移行の失敗と再開

`CREATE UNIQUE INDEX CONCURRENTLY` が中断されると、同名の無効な索引が残ることがある。新索引の作成に失敗した時点では旧制約が残り、既存の登録は維持される。`IF NOT EXISTS` で失敗を無視すると無効な索引を完成扱いしてしまうため、使用しない。

移行の失敗時は、まず読み取りで状態を確認する。

```sql
SELECT EXISTS (
  SELECT 1 FROM pg_constraint
  WHERE conrelid = 'apns_subscriptions'::regclass
    AND conname = 'apns_subscriptions_device_token_environment_key'
    AND contype = 'u'
) AS old_constraint_exists,
(SELECT indisvalid FROM pg_index
 WHERE indexrelid = to_regclass('apns_subscriptions_token_environment_kind_key')
   AND indrelid = 'apns_subscriptions'::regclass) AS new_index_valid;
```

- `old_constraint_exists=true` かつ `new_index_valid=false` のときだけ、無効な索引を `DROP INDEX CONCURRENTLY apns_subscriptions_token_environment_kind_key` で除去してからAtlasを再実行する。クラスタや本番DBを直接変更せず、状態の再確認とこの除去を行う復旧Jobをzoo2-infraのPRでレビューし、GitOpsで適用する。復旧中は別のマイグレーションJobを同時に走らせない。
- 新索引が存在しなければ除去は不要。Atlasを再実行する。
- 新索引が有効なら削除しない。Atlasの履歴と失敗した文を確認し、旧制約の削除から再開する。旧制約がなく新索引も無効な状態は、この移行の通常の失敗経路ではないため、自動復旧しない。

VoIP対応済みの移行前サーバーも新索引で動くため、アプリだけのロールバックは可能。用途が異なる同一トークンの登録が共存した後は旧一意制約を戻せないため、DBの逆向き移行は行わない。

根拠は[PostgreSQLの並行索引構築の失敗処理](https://www.postgresql.org/docs/16/sql-createindex.html)と[Atlasの失敗した移行の再開](https://www.atlasgo.io/versioned/troubleshoot)。性能テストでは構築中のタイムアウトを故障として注入し、旧制約と無効な索引の残存、単純再試行の失敗、無効索引の除去後の移行成功を確認する。

## 回帰テストと適用確認

`backend/tests/apns_kind_test.rs` は実際のRouterとPostgreSQLで次を確認する。署名鍵は子プロセス用に使い捨てで生成し、Appleへの通知は送らない。

- 旧制約では同一トークンの別用途登録が409になり、実際のマイグレーション適用後に200になる。既存行の全フィールドは移行前後で一致する。
- sandbox・production、登録順の入れ替え、512文字のトークン、8同時の新規登録と再試行で用途ごとに1行を保つ。
- 所有者・解除情報の不一致は拒否し、一方の解除がもう一方に影響しない。解除済みの古い要求で登録を復活させない。
- 非正規の別IDを使った同用途の重複も新索引で拒否する。

ローカルではAtlas v1.3.0で旧スキーマから実際に移行し、`schema.sql` を投入したDBとのスキーマ差分がないことを確認した。Docker・Nixがないため、`make migrate-diff` は実行環境不足で停止した。代わりに同版AtlasとネイティブPostgreSQL 16.15で移行前後の差分を生成し、索引を先に並行構築する順序へ調整した。ER図も同じAtlasで検査し、`infra/db/erd.sh` の分割・描画関数で再生成して全ファイルの一致を確認した。Dockerを使う正規の検査はPRのCIで確認する。

画面の409だけでは実機で競合した制約名までは分からない。修正後も競合した場合に区別できるよう、サーバーは登録用途・環境・既知の制約名だけを記録する。トークン・登録ID・ユーザーID・解除情報・DBエラー本文は追加ログに含めない。

## 性能検証

2026-11-20、Apple M4（10コア・32GiB）、macOS 27.0.1、PostgreSQL 16.15で測定。`shared_buffers=128MiB`、`work_mem=4MiB`、`effective_cache_size=4GiB`、`max_connections=100`、`random_page_cost=4`、`effective_io_concurrency=0`、`default_statistics_target=100`、JIT無効。各fixture後にANALYZEし、OS・DBキャッシュは強制破棄していない。初回も結果に含める。

正式なスキーマを読み込んだ隔離schemaで、30万件・100万件の登録を作る。対象ユーザーの20件は同じに保ち、無関係な利用者を増やす。SQLはcustom/generic両計画、1・8同時、6操作を各30回測定する。索引の維持費用を含めるため、追加・更新・解除は実行してからロールバックする。移行前の索引でも単独測定を行う。APIはRouter・開発用認証・実DBプール経由で、両用途の登録・再登録・解除を1・8同時、各30回測る。外部HTTP、JWT検証、Appleへの送信は測定範囲外で、プール待ちはAPI時間に含む。

登録・更新・解除の対象は最大1行、空の照会は0行、ユーザーの登録照会は最大20行とし、毎回の計画で走査行数×loopsと除外行を確認する。SQL・接続数・計画方式別の最大論理ブロック数を規模間で比較し、100万件が30万件の2倍+16を超えたら失敗にする。索引高・ページ分割・HOT更新の違いを許容しつつ、無関係な登録全件の走査を検出する。ページ分割の発生回は一定ではないため、同じ回数目同士の比較はしない。時間だけでは合否を決めない。

新規登録は既存の6 SQL、再登録は4〜5 SQL、登録済み端末の正規解除は6 SQL（認証とBEGIN/COMMITを除く）。今回の変更によるSQL・通信の追加はない。API内の各SQL時間・プール待ちを個別に分離する計測は追加しておらず、下表のSQL計画時間とAPI合計時間を区別して報告する。

移行は索引構築と30回の更新を並行する。制約削除は別に、既存更新のトランザクションを保持してDDLの`AccessExclusiveLock`待ちと後着更新の`RowExclusiveLock`待ちを実際に確認し、既存更新のCOMMIT後に両方が完了することを検証する。意図的に作った待ち時間と、保持終了後の時間は別に記録する。無制限の更新を並行すると規模ごとにHOTチェーンの長さが変わるため、更新回数は固定する。

再実行は開発DBの`DATABASE_URL`を設定して行う。テストが作ったschemaは成功・失敗時に回収する。

```sh
ZOO_APNS_KIND_BUDGET_OUTPUT=/tmp/apns-kind-budget.json \
ZOO_APNS_KIND_BUDGET_MACHINE='CPU・メモリ・OSを記入' \
cargo test --manifest-path backend/Cargo.toml --test apns_kind_test \
  registration_kind_write_budget -- --ignored --nocapture
```
