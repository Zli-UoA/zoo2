# 電話セッションとPBX参照の探索上限

`backend/tests/phone_query_budget_test.rs` は本番SQLをソースから読み取り、実PostgreSQLで `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` を実行する。返却件数だけでなく、走査行×loops・除外行・ソートのディスク退避を検査する。書き込みも実行する。親EXPLAINにFK内部のバッファは含まれないため、各測定接続でauto_explainをLOADし、実際のRI/CASCADE内部SQLの計画をNOTICE経由で収集する。親と内部計画の走査・論理ブロックを合算して比較し、CASCADE計画が取得できなければ失敗させる。各計画はトランザクションをrollbackし、最初の計画をartifactへ残す。

## 変数と上限

Nは全回線・電話機・セッション数、Lは閲覧可能な回線数、Pは回線内電話機数（最大100）、Mは回線メンバー数（最大100）、Sはユーザーのセッション数（最大4）。セッション予約はuser → line → sessionの順でロックする。接続前の読み取りトランザクションを確定してから予約し、権限と更新版を再検証する。ネットワークI/O中はDBロックを保持しない。

| SQLの用途 | 探索・ソートの上限 |
| --- | --- |
| セッションの所有権・更新版・会員資格 | session PK → line PK・user PK・membership PK。O(log N)、各キー最大1行 |
| 同時接続数・期限切れ回収 | `(user_id,expires_at)` で対象ユーザーのみ。O(log N + S)、S≤4 |
| リース取得・更新・削除・内部ID保存 | session PK最大1行。UPDATE/DELETEの対象とFK参照先も定数 |
| PBX endpoint/auth/AOR | line PK、またはphone PK → line PK → user PK。O(log N)、各キー最大1行 |
| PBX内線の解決 | line PK確認後 `(line_id,extension)` で検索。該当最大P≤100。任意の全endpoint列挙は提供しない |
| 回線更新時の電話機ID検証 | `line_id` を索引の先頭にした検索で既存IDを一括取得。O(log N + P)、P≤100。電話機ごとの読み直しなし |
| 作成者の回線数上限 | `sip_lines_created_by_idx` で対象ユーザーの最大50回線のみ |
| ディレクトリー | owner索引・membership user索引から可視IDをUNIONし、line PKへ結合。一般利用者は無関係な共有回線を列挙しない。管理者は全共有回線がLに含まれる。O(L log N + L×(P+M))、可視L件の並び替えO(L log L)。ページ/OFFSET・履歴展開なし |

ユーザー・回線・membershipの一意索引と、`phone_sessions_user_expiry`・`phone_sessions_line_idx`・`sip_phones_line_extension_idx`・`sip_lines_created_by_idx` を使用する。phone_sessionsは通話履歴ではなく期限付き登録で、同じユーザーが再接続する際に期限切れを回収する。

管理者のLには全共有回線が含まれ、作成者ごとの50件制限は共有回線の総数を制限しない。したがって管理者一覧の処理量・応答サイズはLに比例して増える。黙って欠落するLIMITは追加せず、現時点では全可視回線を返す。大規模運用に向けて件数を制限する場合は、全クライアントでカーソルと続きを扱うページングAPIを別途導入する必要がある。

### 回線管理SQLの入力と探索上限

`routes/sip.rs` のSQL文字列を読み書きとも除外せず抽出する。新しいSQLが既存の引数分類に一致しなければテストを失敗させ、全プレースホルダー番号を解析する。作成SQLの9引数とboolean型も扱う。実際のSQL・引数・計画はartifactの `query_definitions` と初回sampleへ残す。

| SQL | API内の発行回数 | 入力・探索上限 |
| --- | ---: | --- |
| active / メンバー有効性確認 | 1 / M | user PK各1、O(log N)。M≤100 |
| user `FOR NO KEY UPDATE` | 保存ごと1 | user PK1。予約と同じロック順 |
| line `FOR UPDATE` | 更新・削除ごと1 | line PK1 |
| creator count | 作成ごと1 | created_by索引、対象作成者の最大50行。50行の条件も測定 |
| INSERT sip_lines | 作成ごと1 | 新規PK・所有者/作成者FK各1、O(log N) |
| UPDATE sip_lines | 更新ごと1 | line PK1、更新索引も含むO(log N) |
| DELETE sip_line_members | 保存ごと1 | line_id先頭のPKでM≤100行 |
| INSERT sip_line_members | 保存ごとM | PK/FK各1、O(M log N) |
| SELECT sip_phones ID一覧 | 保存ごと1 | line_id索引でP≤100行 |
| DELETE sip_phones | 保存ごと1 | line_id索引でP≤100行 |
| INSERT sip_phones | 保存ごとP | PK・line FK各1、O(P log N) |
| DELETE sip_lines | 削除ごと1 | line PK1、CASCADEは電話機P≤100・会員M≤100・当該回線の全セッションD。子のline_id索引を使用 |
| 接続設定 / authorize | 各1 | line PK1とmembership PK各1 |
| 一覧 | 1 | 上表のL・P・M。一般利用者L=2と管理者L=22/202を区別。EXPLAINのActual Rowsはloop平均を丸めるため、管理者の電話機走査には合計100行にL行までの丸め差を許容 |

Dは当該回線の全セッション数で、期限切れや過去のメンバーの登録も含む。現在の利用者あたり4件という接続上限はDの上限ではない。削除のCASCADEはO(log N + P + M + D)であり、Nだけが増えてDが一定の条件と、Dを増やす条件を分ける。測定はD=3/403。CASCADE内の計画はEXPLAINだけでは展開されないため、親と実際の内部計画の論理ブロックを30万/100万件で比較する。fixture準備の内部計画は測定前に破棄する。各サンプルをrollbackし、削除後の状態を後続サンプルへ持ち越さない。

## リクエストとの関係

接続は認証共通処理のほか、最初のユーザー/回線確認2 SQL、予約5 SQL、内部ID保存1 SQL。外部I/OはJanus create・attach・registerの3回。通常コマンドは所有権確認1 SQLとJanus命令1回、切断は削除が1 SQL加わる。SSEは登録ごとに1本、内部Janus long pollも1本。10秒ごとの権限確認・リース更新は2 SQLとkeepaliveで、切断・失効・遅い受信者で停止する。PBX realtimeは参照ごとに1 SQL、内線解決のみ最大2 SQL。

APIの権限・同時接続・二重SSE・破棄・回線編集との競合は `backend/tests/sip_test.rs` で検証する。SQL単体の時刻をSIP登録や通話開始のAPI応答時間と扱わない。JanusのI/O時間・実回線の呼出時間・実機音声遅延は別の受け入れ項目。

## 測定と再現

各規模で、別ユーザーの回線・電話機・期限切れセッションをそれぞれ30万/100万件、対象に100電話機・100会員・4セッションを用意する。管理者用には追加の共有回線を20/200件とし、可視L=22/202を比較する。可視回線数・作成者件数のfixture変更は測定群の前に確定し、読み取り中にfixture更新ロックを持たず、群の終了後に元へ戻す。無関係なデータを単一所有者・単一回線に集中させ、APIの上限より大きい偏りでも対象検索を維持できるか確認する。所有者違い・存在しないセッション・空の内線・通常読み取り・書き込みを含め、単独30回と8接続×30回を実行する。初回PREPARE・計画・実行を捨てず、準備（BEGIN・PREPARE・fixture準備）、EXPLAIN実行・結果転送・rollbackのSQL往復時間を分けて保存する。auto_explainの計測負荷を含む。再実行用 `PHONE_SCALE_REUSE=1` は同じ使い捨てfixture専用。

```sh
# それぞれ空のDBへ通常のmigrationを適用した後に実行する。
PHONE_SCALE_ROWS=300000 PHONE_SCALE_OUTPUT=/tmp/phone-300k.json cargo test --manifest-path backend/Cargo.toml --test phone_query_budget_test -- --ignored --nocapture
# DATABASE_URLを100万件用の別DBへ変更する。
PHONE_SCALE_ROWS=1000000 PHONE_SCALE_OUTPUT=/tmp/phone-1m.json cargo test --manifest-path backend/Cargo.toml --test phone_query_budget_test -- --ignored --nocapture
python3 infra/db/compare-phone-work.py /tmp/phone-300k.json /tmp/phone-1m.json
python3 infra/db/test-phone-work.py
```

専用CIは各規模のplan・全sample・CPU/メモリ/PostgreSQL設定と比較結果をartifactへ残す。関係ごとの走査上限をRustテストで検査し、規模間比較は論理ブロックが `2×小規模+64`、関係ごとの走査が `2×小規模+8` を超えたら失敗する。索引高・丸め・競合を許し、3.3倍の履歴比例増加は許さない。比較器にはブロック比例増加・走査比例増加・同時実行sample不足を拒否する回帰テストを付ける。時間の100msは参考値で、時間だけでは合否を決めない。

開発環境はPostgreSQL16、cgroup CPU上限4 CPU、メモリ約18GiB。Android/Rust/Webのビルドと共有して測定しており、OSキャッシュは強制破棄していない。CPU待ち・同じ行の書き込み競合を含む外れ値を隠さず、計画/実行/往復を分けて記録する。実運用環境の性能保証ではない。
