# OIDCのユーザーアイコン

認証時に、検証済みのissuer・subと一致するUserInfoの`picture`を`users.avatar_url`へ同期する。同期はバックエンドのレプリカごとに行い、本人のユーザー解決キャッシュ（5分）が切れた後、その本人から次の要求を受けたときに更新する。同じissuer・subの同時要求はユーザー解決を単一実行し、待機後にキャッシュを再確認する。

既存ユーザーは、`profile` scopeがある場合に画像を同期する。画像の省略は削除として反映し、scopeがない場合やUserInfo取得失敗時は保存済みの値を維持する。Discovery・UserInfoの取得と応答のデコードは全体で2秒を上限とし、タイムアウト後も認証を継続する。通常のユーザー名が確定済みで`profile` scopeもない要求は、UserInfoの取得を省略する。旧フォールバック表示名の補正は既存の再試行間隔に従う。

新規作成時は、DiscoveryとUserInfoを合計6秒まで待ち、UserInfoを取得できた場合、または検証済みトークンにユーザー名・メールの候補がある場合にユーザーを作成する。取得障害で名前の候補を確定できない場合は503を返し、同じissuer・subの再試行を5秒間抑止してから受け付ける。トークンの`picture`は`profile` scopeがある新規作成時の初期値として使う。

画像URLは入力と正規化後の両方が2048バイト以内で、認証情報を含まない絶対HTTPS URLを受け付ける。許可されたUserInfoの画像URLが不正な場合は未設定にする。Webの`CSP_AVATAR_SRC`は既定が`https://avater.zliusercontent.com`で、別のIdPでは画像配信元を実行時に指定する。

AuthZで画像を差し替えると旧URLは404になる。Webは保存画像を表示し、同期後の新しいURLへ切り替える。画像未取得時は頭文字を表示する。画像更新の契機は、キャッシュ期限後の本人の要求とする。

AuthZの60回/60秒の制限はIPとパスを単位とするため、送信元IPを共有する利用者間で同じ枠を使う。Zoo2は同一ユーザーの同時要求を集約し、取得失敗後もユーザー解決結果を5分キャッシュする。429も既存ユーザーでは保存値を維持し、新規作成で名前を確定できない場合は503で再試行を受け付ける。実環境での共有IPからの通信量は配備後に確認する。

既存のElectricのusers shapeとReact・Androidの`avatar_url`表示を利用する。TUIの認証も共通バックエンドの同期を利用する。表示名の本人編集状態は画像同期後も維持する。

ActivityPubのActorは`icon`に現在の画像URLを含め、画像を削除すると`icon: null`を返す。画像・連合用表示名・自己紹介の変更はDBの配信待ちにまとめ、ワーカーが最新のActorを署名付き`Update`として承認済みの受信フォロワーへ配信する。送信失敗時は既存の永続キューで順序を保って再送する。画像URLが同じ場合は配信済みの画像変更を重複登録せず、連合配信を待つ間も認証は継続する。

導入時のマイグレーションで、アイコンが保存済みのユーザーも配信待ちに登録する。新しいワーカーの起動後に、既存フォロワーへ現在のアイコンを配信する。

Webでは`avater.zliusercontent.com`の公開画像をService Workerに直近64件まで保存する（1画像2MiB上限）。保存画像を即表示し、5分以上経過した画像を裏で再確認する。画面復帰・通信復帰と表示中の定期確認にも対応し、内容のハッシュが変わるとSWから画面へ通知して画像を差し替える。通信エラー時は保存画像を使い、アプリの更新後も画像キャッシュを引き継ぐ。

R2のGET/HEAD CORSと`CSP_AVATAR_SRC`の`connect-src`許可で、公開画像を資格情報なしで取得する。CORSの適用前は通常の画像読み込みを使う。SWはAPIや認証情報のキャッシュと分けて画像を保存する。アイコンURL自体の変更は、従来どおりElectricのユーザー情報から反映する。
